## Architecture

```text
Browser (visitor, member)          Program (API key)               Assistant (MCP client, API key)
  │ pages, CSV, WebSocket            │ /api/v1/*, or the SDK          │ /mcp
  ▼                                  ▼                                ▼
Worker (Hono): marketing · docs · auth · app · api · mcp route modules, one app
  │   │                                │  operations.ts (REST and MCP share it)
  │   ├── D1 directory "crossfeed" ◄───┤  members, passkeys, sessions, challenges, networks,
  │   │   (directory.ts only)          │  memberships, invites, API keys, wipes
  │   │                                ▼
  │   ├─ /agents/session ──────► CrossfeedAgent  the engine, one per test session (tests only)
  │   ├─ /agents/network/:id ──► NetworkAgent    one per network: roster, CPM, inbox, pitch runs,
  │   │                             │  RPC ▲      launch list                        (ADR 0001)
  │   └─ /agents/launch/:id/:l ─► LaunchAgent    one per launch: runs, ranking, insertion orders
  │                                 │ each runs the Claude tool loop ──► Anthropic Messages API
  │                                 ▼
  └── cron: health, purge, ──► QlooGateway "global"          QLOO_API_KEY, shared cache, global caps,
      guests, wipe retries       QlooGateway "network:<id>"  a network's own key (ADR 0004)
                                   │
                                   ▼
                    https://hackathon.api.qloo.com   (or https://api.qloo.com for a network's own key)
```

### Why this stack

- **Cloudflare Workers** is already scaffolded in [`apps/`](/apps/) with Hono and Vite. Time spent waiting on `fetch()` doesn't count toward CPU time, and HTTP-triggered Workers have no hard duration limit, which suits slow Qloo calls ([Workers limits][cf-limits]).
- **The Cloudflare Agents SDK** (`agents` 0.28.1) is the agent framework the rules ask for ([BRIEF](BRIEF.md#challenge)). Its `Agent` class runs on a Durable Object and gives per-session state synced to clients, embedded SQLite, WebSockets, and schedules ([Agents API][cf-agent]).
- **Claude through the official Anthropic SDK** (`@anthropic-ai/sdk`, which supports Cloudflare Workers). We use the base `Agent` class, not `AIChatAgent`, because `AIChatAgent` runs on the Vercel AI SDK, and the official SDK exposes the Claude features below (effort, adaptive thinking, strict tools) directly.
- **Direct REST to Qloo**, not the hackathon kit's `qloo mcp` harness, which can't run serverless ([CONTEXT](CONTEXT.md#hackathon-kit)).
- **D1 for the directory, Durable Objects for the work.** The product keeps the agent design that already worked per instance, with its replay and its tests, and adds a D1 database only for what has to be looked up across instances ([ADR 0001](/docs/adr/0001-agents-per-network-and-launch.md)). Passkeys are built in-house on `@simplewebauthn/server`, since a magic link, OAuth, or passwords each needed something the project doesn't have ([ADR 0003](/docs/adr/0003-passkeys-built-in-house.md), [platform research](/docs/research/platform.md)).
- **The account stays on its current Cloudflare plan.** This section first required Workers Paid, because Free allows 50 subrequests and 10 ms of CPU per invocation and a cold guest run needs about 50 Qloo calls plus model calls ([Workers limits][cf-limits]). Every flow has since run live on the current plan, so on 2026-10-18 the owner decided not to upgrade ([#21](https://github.com/m1kuorg/qloo/issues/21)).

[cf-limits]: https://developers.cloudflare.com/workers/platform/limits/
[cf-agent]: https://developers.cloudflare.com/agents/runtime/agents-api/

### Components

- **Worker:** one Hono app (`src/index.tsx`) that mounts a route module per surface from `src/routes/`, puts secure headers and the Content-Security-Policy on every answer but an agent's connection, and `X-Robots-Tag: noindex` where search engines mustn't index ([Crawlers](#crawlers)), answers a route's error with the error page or a plain 500, exports the four Durable Object classes, and runs the crons. Each route module routes its own agent connections, which the client reaches with `useAgent`'s `basePath` ([custom routing][cf-routing]). The Worker doesn't use `hono-agents`' `agentsMiddleware`, because its `/agents/<binding>/<name>` routes would let a client open any session, network, or launch, or reach `QlooGateway`.
- **`CrossfeedAgent`:** the engine the two agents of the signed-in product extend. It owns the Claude loop, the roster, launches, runs, insertion orders, pitches, replies, and evidence log. Clients can't write its state; it changes only through actions. It was the retired demo's agent, one per visitor session; it keeps its per-session route, `/agents/session`, for the engine's tests alone, which answers only while the test-only `TEST_SESSIONS` variable is on, so a deployed Worker has no anonymous per-visitor agents outside the guest budget ([ADR 0007](/docs/adr/0007-the-sample-network-is-the-guest-networks-data.md)). A test session is named by a random UUID in a `crossfeed_session` cookie; one that isn't a UUID names no agent. The demo's sessions keep their storage in production, unreached.
- **`NetworkAgent`:** one instance per signed-in network, named by the network's ID. It holds the network's roster, CPM, inbox, booking and pitch runs, and the list of its launches, and refuses launch actions ([Networks and launches](#networks-and-launches)).
- **`LaunchAgent`:** one instance per launch, named `<networkId>:<launchId>`. It holds one launch's runs, rankings, topic baseline, demographics, and insertion orders, copies the network's roster as each run starts, and refuses roster and inbox actions. The three agent kinds are separate Durable Object classes, so no cookie can name a network's or a launch's instance ([ADR 0001](/docs/adr/0001-agents-per-network-and-launch.md)).
- **`QlooGateway`:** the only code that calls Qloo. The `global` instance serves every network without its own Qloo key, and a `network:<id>` instance serves a network that brings one ([ADR 0004](/docs/adr/0004-qloo-key-per-network.md)). Agents reach their gateway over Durable Object RPC. It owns the key, the request shape, retries, the concurrency limit, the response cache, the daily caps and counters, and evidence records. Each method returns its data or its error as a value, together with the call's evidence record, so a failure's evidence survives the RPC hop.
- **Directory:** one D1 database, `crossfeed`, bound as `DB`, for what has to be looked up across agents: members, passkeys, sessions, sign-in challenges, networks, memberships, invite links, API keys, and the agent wipes still due. `src/directory.ts` is the only code that reads or writes it ([Storage](#storage)).
- **Operations:** `src/operations.ts`, what a program can do for a network, shared by the REST API and the MCP server. Each operation takes the network, the caller, and its input, and calls the directory or the network's agents over RPC ([REST API](#rest-api)).
- **UI:** four server-rendered Hono JSX shells: the marketing shell (landing page, privacy, beta terms, developer docs, the 404 page; no island), with the wordmark and its links and no bar; the auth shell (sign-in and invite), with the wordmark and no links; and the app shell, an icon rail beside a top bar, the rail a bottom bar on phones ([DESIGN](DESIGN.md#shells)). The app and auth pages are a React client island that connects through `useAgent` from `agents/react`, the Agents SDK's documented client path, told its page, its agent's path, and its links by data attributes. The island is split into a chunk per page, which the shell preloads ([Client protocol](#client-protocol)).

[cf-routing]: https://developers.cloudflare.com/agents/runtime/communication/routing/

### Routes by surface

Each surface is its own route module, mounted on the one app. While `ACCOUNTS` is off (it's on in production since [#223](https://github.com/m1kuorg/qloo/issues/223)), every route of the auth, app, API, and MCP surfaces answers 404, and no page links to them.

- **Marketing** (`routes/marketing.tsx`): `/` (the landing page), `/privacy`, and `/terms`, and the Worker's 404 and error pages (`notFound` and `serverError`), which a browser asking for a page gets when no route serves it or its route throws; anything else gets a plain `404 Not Found` or `500 Internal Server Error`, and the API answers its own errors. The privacy page and terms say what an account keeps, and give the account limits, only while `ACCOUNTS` is on; the terms read every limit from the Worker's variables and the modules that hold them.
- **Docs** (`routes/docs.tsx`): `/docs`, `/docs/api`, `/docs/sdk`, `/docs/mcp`, `/docs/agents`, each skill's file at `/docs/agents/<skill>/SKILL.md`, and `/llms.txt` ([Skills, plugin, and developer docs](#skills-plugin-and-developer-docs)).
- **The retired demo** (`routes/demo.ts`, [ADR 0007](/docs/adr/0007-the-sample-network-is-the-guest-networks-data.md)): `/demo`, `/demo/inbox`, and `/inbox` redirect to `/sign-in#guest`, the sign-in page's guest panel, while `ACCOUNTS` is on, and are 404s while it's off; and the engine's per-session agent route, `/agents/session`, for tests alone.
- **Auth** (`routes/auth.tsx`): `/sign-in` and `/invite` (island pages), and the JSON routes under `/auth/`: `sign-up/options` and `sign-up`, `sign-in/options` and `sign-in`, `recover`, `verify` (step-up), `passkeys/options` and `passkeys` (adding one), `invite` and `join`, `guest` (signing in as a guest), and `sign-out` ([Members and sign-in](#members-and-sign-in)).
- **App** (`routes/app.tsx`): `/app` (the network opened last, or `/app/new`), `/app/new`, `/app/account` and its routes, and a network's pages, `/app/<id>` (the dashboard), `/app/<id>/launches` (the Launches page), `/app/<id>/roster`, `/app/<id>/inbox` (while `GUEST_PITCHES` is on), `/app/<id>/launches/<launchId>`, and `/app/<id>/settings`, with each settings module's routes, a launch's order export and deletion, and the agent connections `/agents/network/<id>` and `/agents/launch/<id>/<launchId>`. Signed out, a page redirects to `/sign-in?next=<path>`; anything outside the member's networks, or a launch the network doesn't list, answers the same 404 as one that doesn't exist.
- **REST API** (`routes/api.ts`): `/api/v1/networks/<id>/...` and the OpenAPI document at `/api/v1/openapi.json` ([REST API](#rest-api)).
- **MCP** (`routes/mcp.ts`): `/mcp` ([MCP server](#mcp-server)).
- **Crawlers** (`routes/crawlers.ts`): `/robots.txt` and `/sitemap.xml` ([Crawlers](#crawlers)).

Every page under `/app`, `/sign-in`, and `/invite`, every `/auth/*` and `/api/v1/*` answer, is `Cache-Control: no-store`.

### Crawlers

Search engines index production's public pages alone. `SEARCH_INDEXING` decides it: `on` in production's vars, left out of the preview's, so a deployment without it is indexed nowhere, and `off` in tests, which can't leave out a var of `wrangler.jsonc`'s top level.

- **With it on**, `/robots.txt` lets every crawler (`User-agent: *`) fetch everything but `/app`, `/api`, `/mcp`, `/agents`, `/auth`, and `/invite`, each a prefix. `Allow: /apple-touch-icon.png` takes back the one public file `/app` covers, as a search engine may take it for the favicon. It names `/sitemap.xml`, which lists the public pages: the landing page, privacy, the beta terms, each docs page, and `/sign-in` while `ACCOUNTS` is on. Each URL is on `APP_ORIGINS`' first origin, as the pages' canonical addresses are. Every answer under `/app`, and `/invite`, carries `X-Robots-Tag: noindex`, for a crawler that fetches one anyway.
- **With it off**, every answer of the Worker carries `X-Robots-Tag: noindex`, and `/robots.txt` disallows nothing (`Disallow:`), so a crawler can fetch any page and read it. `/sitemap.xml` is a 404. The files in `public/`, which Workers Assets serves before the Worker runs, carry no header, and an agent's connection none, as its answer can't take one.
- **Cloudflare's managed robots.txt:** Cloudflare serves its own `/robots.txt`, the content-signals comments the account's settings give, only where the origin has none: both hosts served it while the Worker answered a 404. With the Worker answering 200, Cloudflare passes the Worker's text through and prepends nothing, as the account's settings give it no rules to prepend. Both hosts showed this after #374 deployed ([managed robots.txt][cf-robots]).

[cf-robots]: https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/

## Qloo integration

Base URL `https://hackathon.api.qloo.com` (`QLOO_BASE_URL`), header `X-Api-Key`. A network's own key is sent to the host its owner chose, Qloo's production API at `https://api.qloo.com` or the hackathon's ([a network's own Qloo key](#a-networks-own-qloo-key)); the calls are the same. The calls below were checked live on 2026-10-17 unless marked _(verify)_; every call returned 200 in 1 to 4 seconds at a concurrency of 3.

### Calls

- **Resolve a show:** `GET /search?query=<name>&types=urn:entity:podcast&take=3`.
- **Resolve a work:** the same, with `take=5` and `types` set by work type: `urn:entity:book`, `urn:entity:movie` for films, `urn:entity:tv_show`, or `urn:entity:podcast`. Each result's `disambiguation` gives its year, plus the author for books. An older work with the same title can come first, such as the 1931 Frankenstein above the 2025 film, so the year decides between same-name results ([demo data](#demo-data)). A book is matched by its author instead: a same-title book credited to someone other than the guest isn't the guest's, because Haiku's recalled years were wrong for 6 of 36 sample works, mostly books, while its film and TV years were right. A podcast's name can add its hosts, as in New Heights with Jason & Travis Kelce; that counts only when a host shares a surname with the guest, so Dinner with Friends isn't Dinner. The guest's name is compared in the session and never sent. Among the guest's books or same-year results, one with no popularity gives way to one that has; without a year, popularity decides nothing. Several matches left go to the booker to confirm with `confirmWork`.
- **Rank a closed list:** `POST /v2/insights` with `filter.type=urn:entity:podcast`, `signal.interests.entities=<anchor IDs>`, `filter.results.entities=<candidate IDs>`, `feature.explainability=true`, and `take=50`. With comps, all of them go in as one comma-separated signal.
- **Rank pitched works:** the same, once per work type, with `filter.type` set to that type and the show plus past guests' works as anchors. Rankings across categories return scores and explainability, as for books ranked against a podcast ([demo data](#demo-data)). If Qloo scores none of a type's works against those anchors, that type is ranked again against only the past guests' works of the same type; with none of that type, it stays unranked with the reason. Each list records which path ran, the anchors it used, and both calls, and each call's evidence holds its anchors.
- **Demographics:** `POST /v2/insights` with `filter.type=urn:demographics` and `signal.interests.entities=<launch or comp IDs, and finalist IDs>`. It returns one entry per entity, by ID only, in no set order.
- **Shared tags:** `GET /v2/analysis/compare?a.signal.interests.entities=<launch or comps>&b.signal.interests.entities=<finalist>&take=50`, once per finalist. Several comps on side `a` go in as one comma-separated signal: on 2026-10-17, three shows on side `a` gave a shared set that was the union of each show's own shared tags, and side `a`'s own tags counted up to 3, so no per-comp call and merge is needed.
- **Find a comp for a roster show:** `GET /search?query=<what the programmer typed>&types=urn:entity:podcast&take=5`.
- **Health check:** `GET /search?query=The%20Rewatchables&types=urn:entity:podcast&take=1`.

POST bodies use flat dotted keys, such as `{"filter.type": "urn:entity:podcast", "take": 50}`; a nested body returns 400 ([BRIEF](BRIEF.md#live-api-checks)).

Not used: `/entities?external.spotify.ids=` is accepted but found no podcast by its Spotify show ID, and only 1 of 200 podcast search results carried a Spotify ID. iTunes IDs are stored on most podcasts but `external.itunes.ids` found none.

### Response fields used

- **Search:** each result's entity ID, name, and popularity, shown as candidates for ambiguous matches. For a work, also its `disambiguation` (year, plus a book's author) and one line from `properties`: the English `short_descriptions` value, a podcast's `short_description`, or `description`, cut to about 200 characters. Qloo can list one film twice, as it does the 2026 Digger, and the description is what tells the entries apart. When nothing does, the picker shows their Qloo IDs and says so.
- **Ranking:** each result's `query.affinity` and its `query.explainability["signal.interests.entities"]`, a list of `{entity_id, score}` per anchor. The top-level `effect_on_top3_recs` through `effect_on_all_recs` summaries are logged but not shown. `query.measurements.audience_growth` was always 0 and is ignored.
- **Demographics:** `results.demographics[]`, one entry per entity, with `query.age` over the buckets `24_and_younger`, `25_to_29`, `30_to_34`, `35_to_44`, `45_to_54`, and `55_and_older`, and `query.gender.male` and `female`. Values are relative to average and ran from −0.95 to +0.95. In every entry seen, `female` was the negative of `male`, so `male` alone gives the gender skew.
- **Compare:** `results.tags[]`, each with `tag_id`, `name`, and `query.score`. Scores sat between 0.700 and 0.731, so tags are used as words, not ranked by score, and generic tags such as "Podcasts" are dropped through a stoplist. A name Qloo lists under two subtypes, such as Engaging as a host and a content tag, is kept once, and a finalist shows its first five remaining tags in Qloo's order. Host and style descriptors such as Insightful and Conversational stay: between podcasts they are most of the shared tags, and dropping them would leave some finalists with none.

### Gateway rules

- **Request shape:** GET for `/search` and compare, POST with flat keys for `/v2/insights`.
- **Timeout and retries:** a 20-second timeout per request. Retry 429, 502, 503, 504, and timeouts at most twice, after about 1 and 3 seconds with jitter. A 400 is never retried; Qloo's message goes back to the caller. A call that fails after retries says how many, such as "Qloo returned 429: Rate limit exceeded, after 2 retries". Its latency runs from its first request, so time spent queued behind other calls isn't blamed on Qloo.
- **Concurrency:** at most 3 Qloo calls in flight across all sessions. The idea's bets report that about 5 concurrent calls trip the rate limit ([IDEA](IDEA.md#bets-to-test)) _(verify)_, and Workers allow six connections per invocation waiting on headers.
- **Unscored signal:** a ranking whose affinities are all null means the anchors didn't resolve, or, for pitched works, that every candidate is too recent to score, so the gateway returns an error, not a result, marked unscored so a pitch ranking can try same-type anchors ([BRIEF](BRIEF.md#gotchas-beyond-the-developer-guide)). Live, Qloo answers it with 200 and no results.
- **Silently ignored parameters:** a ranking that returns an entity outside the candidate list, or no explainability when it was requested, is an error.
- **Unscored candidates:** a ranking silently leaves out any candidate the signal gave no score, which happened to most works released since about May 2025 ([demo data](#demo-data)). The gateway reports each one as unscored.
- **Size:** at most 50 candidates per ranking, since `take` maxes out at 50 and scores from separate calls aren't comparable.
- **Evidence:** every call, cached or not, appends a record to the calling session's evidence log. The gateway builds the record, and the session's one path to the gateway numbers it (`C-01`, in the order calls start) and appends it, success or failure. Its shape is fixed in [`apps/src/evidence.ts`](/apps/src/evidence.ts): call number, run, time, method, endpoint, parameters, status, latency, retries, cache hit, error, and lists of entities, tags, and affinities, which each endpoint fills. A gateway that throws instead of answering, such as one reset by a deploy, still leaves a failed record, which names the request but not its parameters.
- **Rate:** on 2026-10-17 Qloo answered 429 "Rate limit exceeded" to bursts of three searches that each took about 300 ms, with other clients sharing the key, while three calls in flight of about 1 second each passed. The limit is on request rate, not only concurrency, so the gateway paces calls as well as capping them: each request starts at least 400 ms after the last, about 2.5 a second, between the sequential import's 2 a second and the 3 a second that passed. The roster import searches all its shows at once and leaves the pacing to the gateway; on 2026-10-17 the 19 Ringer shows took about 8 seconds with no 429.

### Call budget per run

With a 20-show roster already resolved and an assumed worst case of 8 seconds per call. The ranking runs first, because it picks the finalists; demographics and compares then run together:

- **Launch, released:** 1 ranking, then 1 demographics and 5 compares, so 7 calls in three rounds at a concurrency of 3, about 24 seconds.
- **Launch, three comps:** 3 searches plus the 7 above, so 10 calls.
- **Cold roster:** add 20 searches.
- **Guest inbox of 40 pitches:** 40 searches when it loads, then a pitch run of up to 5 past guests' searches, at most 4 rankings (one per work type, or 8 if every type falls back to same-type anchors), and 5 compares, so about 52 calls and about 2.5 minutes cold. The sample inbox is served warm.

## Agent design

The launch and guest flows follow fixed steps, so the agent works from a short system prompt that lays them out, and from tools that bundle Qloo call chains ([Building effective agents][anthropic-agents]). A launch run takes about five model turns.

[anthropic-agents]: https://www.anthropic.com/engineering/building-effective-agents

### Model settings

- **Model:** `claude-haiku-5-5`, streamed through `client.messages.stream`.
- **Thinking:** adaptive, on by default. A response can start with `thinking` blocks whose text is omitted, and thinking counts toward `max_tokens`, so code reads content blocks by type and passes thinking blocks back unchanged with tool results.
- **Effort:** `output_config.effort` set explicitly to `medium`, this model's default.
- **Output room:** `max_tokens` of 16,000 on every call, so thinking can't use up the answer's budget.
- **Sampling and prefill:** send no sampling parameters and no assistant prefill. A non-default `temperature` or `top_p`, any `top_k`, and any prefill return a 400.
- **Refusals:** safety classifiers can decline with `stop_reason: "refusal"`, and this model has no server-side fallback. Check `stop_reason` before reading content on every call. A refused agent turn stops the run with the refusal shown as a failed step.
- **Tools:** `strict: true` and `additionalProperties: false` on every tool, and `tool_choice` `auto`, because a forced tool choice skips thinking on this model.
- **Parallel calls:** execute every `tool_use` block in a turn concurrently, and return all results in one user message. A failed tool returns `is_error: true` with a message that says what to do next.
- **History is append-only.** Never edit or delete earlier turns, and keep `system` and the tool list fixed for a session. On this model, sending a thinking block back after a change to `system`, `tools`, or earlier messages returns a 400. Stored history keeps every thinking block as returned, including blocks with empty text and only a `signature`.
- **Prompt caching:** a frozen system prompt and a fixed, sorted tool list sit before a `cache_control` breakpoint, above this model's 512-token minimum _(verify)_; session data goes in `messages`, never in `system`.
- **Closing message:** the system prompt caps the run's closing turn at three short sentences, under 60 words, on what the plan covers and what is missing, and forbids restating what the chart shows. On 2026-10-17, "one or two sentences" alone gave about 350 words with a heading per finalist, while the word cap gave 45 to 55 words in three live sample runs. A guest pitch run's closing gives only the verdict counts `draft_replies` returns and the ranking calls, and doesn't list the pitches the lists already name: with the rule in the system prompt alone, one closing in three still listed nine unscored titles in 71 words, so `draft_replies`' last result repeats the instruction, and three more fresh runs on 2026-10-17 gave 42 to 47 words with no pitch IDs. A launch run's closing drifted the same way once the insertion order step was added, to 75 to 113 words naming every finalist. So `draft_insertion_order`'s stored-draft result repeats the instruction too: give the order's total and the ranking call, name no finalist (not even a flagged one), and don't mention flags, tags, slots, or angles. With that, three fresh sample launches on 2026-10-17 closed in 43 to 55 words naming no finalist. The wording must name flagged finalists explicitly, because the demographics step's "say why" otherwise pulls the flag into the closing. The run keeps the closing text as `closing`, in synced state and its snapshot, and the inspector's Run tab shows it under the trace as an agent line whose call numbers open their evidence. A refused, failed, or stopped run has none. The closing is never rewritten: once an edit changes the order's lines or prices after the agent drafted it, the order is marked `edited` (#202), and once a reply's words change or it's discarded or restored, the booking is marked `repliesEdited` (#213). Each mark is sticky, rides into the run's snapshot, and starts unset on a redraft or a new booking. The app shows a help line under the closing line, the API returns `InsertionOrder.edited` and `PitchRun.repliesEdited` as required booleans, and the MCP server's run line adds that the figures are to be taken from the order or the replies.
- **Later, if time allows:** an effort sweep on the demo scenarios, and checking cache reads.

### Tools

Each tool returns names alongside IDs, and errors the model can act on ([Writing effective tools for agents][anthropic-tools]):

- **`resolve_entities(names, type)`:** each name comes back resolved, ambiguous with up to three candidates, or missed.
- **`rank_candidates(anchor_ids, candidate_ids, type)`:** ranks, bands, raw affinities, comp shares, and the evidence ID. The run's first message lists every roster show: the scorable ones with their IDs, a mapped one with its comp's name, and the rest with the reason they can't be ranked, the same reason the chart's Not scored list gives. Listing only the scorable shows led Haiku 5.5 to call a missed show "not on the roster" in its closing message. The roster is the closed list, so the tool ranks every scorable show even when the model leaves one out, refuses an ID that isn't a roster show or an anchor the session never resolved, and leaves an anchor that is itself a roster show out of the candidates.
- **`check_demographics(anchor_ids, candidate_ids)`:** age-band and gender deltas and mismatch flags per finalist, from one demographics call covering the fit ranking's anchors and every finalist. Like the ranking, the lists are closed: it checks every finalist even when the model leaves one out, and refuses an ID that isn't one of the ranking's anchors or finalists. The chart gets each flag's reasons in words; the values stay in the call's evidence, where each entity's buckets are listed under `affinities` as `age.<bucket>` and `gender.<gender>` scores, because the evidence record has no demographics list.
- **`shared_tags(anchor_ids, candidate_ids)`:** the top non-generic shared tags per finalist, from parallel compare calls. The anchors must be the ranking's, and like the ranking it compares every finalist even when the model leaves one out, and refuses an ID that isn't a finalist. In a guest pitch run it compares each top pitch's work, the top band of each pitch list, with the show alone instead: the show's ID is the only anchor it accepts, the candidates are pitch IDs, because the run's messages never give the model a work's entity ID, and it compares every top pitch even when the model leaves one out. The tags go on the pitch's list row.
- **`ask_human(question, kind, options)`:** pauses the run until the human answers in the UI. `kind` is `choice` for a fork answered with one of `options` or free text, or `launch`, `comps`, `confirm_comps`, `budget`, or `exclusions`, whose answer forms code builds.
- **`draft_insertion_order(lines)`:** takes finalists, slot counts, and angles, computes slot values in code, rejects a draft over the slot budget or before the budget and exclusions are answered, so no draft holds a show the programmer leaves out, and stores the rest as a draft for the UI. It refuses to draft until `shared_tags` has compared every finalist, and refuses an angle for a finalist whose compare returned no tags or failed: such a line's angle is `null`, while a tagged finalist needs one (#216). A later exclusions answer drops the lines of the shows it leaves out from the run's draft and prices the rest again, and the tool result says so.
- **`rank_pitches(show_id, past_guest_work_ids, pitch_ids)`:** groups the inbox's pitched works by type and returns one ranked list per type, with each pitch's rank and band and the reason for each one not scored. The run's first message lists the show, the past guests' works that resolved, and the pitches that can be ranked, by ID, without guest names. Like `rank_candidates`, the inbox is the closed list: the tool ranks every pitch whose work matched even when the model leaves one out, refuses an ID the run doesn't list, and never sends a set-aside pitch. A type Qloo leaves unscored falls back to same-type anchors ([calls](#calls)).
- **`draft_replies(replies)`:** stores a draft reply per pitch with its verdict, book, decline, or later, and, for a top pitch, the episode angle with the compare it's built from. It refuses to draft until `shared_tags` has compared every top pitch, and refuses an angle unless the pitch's compare returned tags; a reply keeps its top pitch's compare, angle or not (#216). A call replaces the drafts for the pitches it names and keeps the rest, so 40 replies can go in calls of 20 that stay well inside one turn's output, and its result lists the pitches still without a reply and the run's verdict counts across every call so far, so the closing never adds them up itself. The pitch run's first message lists every pitch, the ones that can't be ranked with why, so every pitch gets a reply. The model never sees a guest's or sender's name, so drafts name only the work and the show, and the booker adds names when editing; this also keeps names out of `resolve_entities`, the one tool that sends free text to Qloo.

[anthropic-tools]: https://www.anthropic.com/engineering/writing-tools-for-agents

### Questions and approvals

- **Questions:** when the model calls `ask_human`, the agent stores the open question in its state and ends the loop. The UI renders the question card. When the human answers, the next user message holds that call's tool result, a neutral "asked the human" notice, followed by the answer as a separate text block, and the loop resumes. The answer never goes inside the tool result, because this model can treat user text there as untrusted and ignore it. The programmer answers one question at a time. When a turn asks more than one, the first is asked, and each other call gets a plain result, not an error, telling the model to ask it again after that answer; it shows no progress note until then. History stays append-only, at the cost of one more model turn per held question. The system prompt requires a question for an ambiguous or missed launch, a missed comp, the comps' matches, comps for an unreleased launch, the slot budget, and exclusions. Pitched works are matched in code when the inbox loads, and the booker confirms an ambiguous one with `confirmWork`; the agent doesn't ask about them.
- **Structured answers:** the launch, when its lookup came back ambiguous, is answered by picking one of its candidates, which code sets as the launch's match, citing the original search, or by giving the name Qloo lists it under, which renames the launch for the agent to look up. A launch whose lookup missed may be unreleased, so the agent asks for comps instead, and a name given in their place renames the launch the same way. Comps, up to three names from `startLaunch({ comps })` or that question, are stored on the launch; the run resolves them, then one `confirm_comps` question offers each comp's match, or an ambiguous comp's candidates, and "None of these". Only a comp the programmer confirmed joins `rank_candidates`' known anchors, so a ranking never anchors on an unconfirmed comp. The slot budget, a count of promo slots or a dollar amount, and the run's exclusions, chosen from the shows the run can score, are answered in forms code builds. Only a `choice` answer, and the name Qloo lists the launch under, are typed; the other forms take no note. Code stores them on the run, where the insertion order is checked against them; the model sees the answer but can't set either. A run's exclusions apply to that run only, apart from the roster's own excluded shows. A turn that asks waits in storage with its other tool results until the answer arrives, so the conversation never ends on an unanswered call, and a run waiting on a question survives a restart.
- **Past guests' works:** matched in code when a pitch run starts, like pitched works. One that doesn't resolve isn't an anchor; the inbox page shows it for the booker to correct before running again, and the agent doesn't ask about it.
- **Roster matches:** settled by the programmer in the roster view, not by the agent's questions. Through `updateShow`, they pick an ambiguous show's candidate, map a missed show to a comp found with `searchComps`, or leave the show out, which marks it excluded. A show still ambiguous, missed, or failed when a launch runs is never scored, and the ranking lists it as not scored, with the reason. Two shows can be mapped to the same comp, so a ranking sends each entity ID once.
- **Approvals:** approving or editing an insertion order and approving, editing, or discarding a reply are client actions handled in code, and no tool can perform them. Export refuses any insertion order that isn't approved.
  - Approval (`approveInsertionOrder`, `approveReply`) needs the page's WebSocket connection: a caller over Durable Object RPC, as the REST API and the MCP server are, is refused on every agent ([ADR 0002](/docs/adr/0002-approval-stays-in-the-app.md)). On a network's or a launch's agent the connection must also carry a member, and the approval records them: an order's `approvedBy` (the member's name) and `approvedAt`, a reply's `approvedBy` (the member's ID). The demo records no one.
  - An order can be edited or approved only once its run has ended, since until then the agent can redraft it. An edit, or a change to the downloads or CPM that changes a price, returns an approved order to draft, so nothing approved changes under the programmer. An edit may leave a line's angle empty only where Qloo returned no shared tags, or give it the programmer's own words.
  - Each run has its own order, kept with what the run ended with as the programmer leaves it, so an earlier run's approved order still exports after a re-run.
  - A reply can be approved, edited, or discarded only once its run has ended, since the agent can redraft it until then. Editing an approved reply returns it to draft, editing a discarded one restores it, and only an approved reply can be copied.
- Runs are short and the human gates sit between turns, so the agent's own SQLite state is enough; the Agents SDK's Workflow approval pattern isn't needed ([human in the loop][cf-hitl]).

[cf-hitl]: https://github.com/cloudflare/agents/blob/main/docs/agents/human-in-the-loop.md

### Other model calls

Single calls with structured outputs (`output_config.format`), on the same model at `low` effort:

- **Topic baseline:** ranks the roster by topic from show names and the network's own one-line descriptions. It gets no Qloo data, because it is the without-Qloo counterfactual. If it's refused, the fit ranking shows without the topic column.
  - It runs once per run, started beside the agent loop, and ranks every roster show but the launch, settled or not, so settling or excluding a show doesn't change its request. The prompt states the count ("Rank all N roster shows"), and code checks for a full permutation, because at `low` effort Haiku 5.5 sometimes returned only its top three. A partial list fails the baseline like a refusal does.
  - The agent caches each full ranking by a SHA-256 hash of its request, so the same launch and roster always rank the same way within a session. The cache is per session, not shared through the gateway, which only serves Qloo.
- **Pitch extraction:** turns each pitch email into a guest name, a work title, a work type, the work's year when the pitch or the model's knowledge gives it, and whether there is a public work. The guest name stays in the session's storage and is never passed to a Qloo tool. A refused extraction sets that pitch aside as unreadable.

### Agent limits

- At most 12 model turns and 60 Qloo calls per run. Past either limit, the run stops as "stopped at a limit", never as completed, and says what it hadn't done.
  - **Turns:** the 12th model call is the last. If it asks for tools, they aren't run, because their results would need a 13th turn, and the run names them as not run.
  - **Qloo calls:** every call the run makes counts, cache hits included, so a warm run and a cold one are bounded the same. The 61st is refused before it reaches the gateway or the evidence log, the tool call that made it is cut off, and the run stops once that turn's other calls finish.
  - The limits live in [`apps/src/limits.ts`](/apps/src/limits.ts), and each run's counts in the agent's `runs` table, so a run paused on a question keeps its count.
- **Model runs a day:** a launch run (with its topic baseline), loading an inbox (its pitch extraction), and a pitch run each count as one model run when they start. A replay, a run that stops at its start, and answering a question don't count. A visitor can start at most `RUN_VISITOR_DAILY_CAP` (10) a UTC day, across sessions, and all visitors together at most `RUN_DAILY_CAP` (200). These replace the session's 10 runs a day (#41), which a visitor reset by clearing the cookie, and which counted replays.
  - **At a limit:** the unchanged sample launch replays its stored run, as when Qloo can't be called. A launch on the visitor's own data stops at once, saying which limit was reached and that it resets at 00:00 UTC. Loading an inbox or starting a pitch run is refused with the same message.
  - **The visitor:** the client's address as Cloudflare's edge sends it (`CF-Connecting-IP`), an IPv6 address by its /64, which one home or phone usually holds whole. It's hashed with the secret `VISITOR_SALT` when the WebSocket connects, and the hash tags the connection. The gateway counts under a hash of that tag and the UTC day, deletes earlier days' counts, and never sees an address. Without the header, as in local tests, the session is the visitor.
  - **Free starts:** a launch start that calls no model, because it replays or stops at once, is a free start. A visitor can make at most `FREE_START_DAILY_CAP` (100) a UTC day, counted the same way. The next one is refused with a message before it keeps anything. Free starts cost no spend, but each keeps a run, its snapshot, and a replay's copied evidence, so the limit bounds the storage a visitor can fill on the account's capped Durable Object storage ([#149](https://github.com/m1kuorg/qloo/issues/149)). A refused inbox load or pitch run keeps nothing, so it isn't counted. The bound is per visitor, not account-wide: each address, or each IPv6 /64, gets its own 100. A cap across all visitors would stop the replay for everyone during a Qloo outage.
  - **Qloo calls:** a visitor's sessions can make at most `QLOO_VISITOR_DAILY_CALL_CAP` (2,000) Qloo calls a UTC day, cache hits included, counted the same way, because each keeps an evidence record ([#151](https://github.com/m1kuorg/qloo/issues/151)).
    - **Refused:** a roster import, a comp search, and the guest network's loads of the sample network and the sample inbox reserve their calls first. One that would pass the limit is refused before anything is numbered or kept. A guest network past it opens with an empty roster, or an empty inbox, until a later start tries the load again.
    - **Counted, never refused:** a run's and an inbox's calls count as they're made; the model run limits bound them. A replay's copied records aren't calls, so the free start limit bounds them instead: 100 a day, of about 27 records each.
    - **Headroom:** a judge's whole path took 91 calls on 2026-10-18: the sample network 19, the sample launch 8, a comps launch 10, the sample inbox 36, and a pitch run 18.
  - **What they bound:** how many model runs start, not dollars. A launch run makes at most 12 model turns plus its topic baseline, and an inbox load one extraction per pitch, up to 50.
  - **A network:** a signed-in network counts as one visitor of its own. `limitKey()` is the one place an agent picks who a Qloo call or model run counts against: an engine session's visitor of the connection (or the session, without one), as in tests, and for a network's agent and each of its launches' agents `network:<networkId>`, from the agent's name, with or without a connection. So a network's members, its API keys, and its launches share its 10 model runs, 100 free starts, and 2,000 Qloo calls a day, and the caps across everyone still apply. A network with its own Qloo key counts its Qloo calls in its own gateway instance, against the same limits, and its model runs with everyone's, since they spend Crossfeed's Anthropic key. Settings and `GET /api/v1/networks/<id>/usage` read the counts (`usage()`). A network on the guest budget, whose ID starts with `guest-`, the guest network or one a guest created (`createNetwork` gives the guest member's `guest-<uuid>`), counts as `network:guest-network` instead (`networkLimitKey`), so every guest shares one set ([ADR 0006](/docs/adr/0006-each-guest-is-a-member.md)), and its refusals and usage module say so; its own gateway instance is still named for the network itself (`ownGatewayName`), so a guest's own Qloo key, cache, and counts stay that network's, and `setKey` counts its test search under the limit key it's given.
  - **The guest network:** every guest's use counts under `network:guest-network`, whichever guest, session, or address it comes from, so everyone who signs in as a guest shares its one budget ([ADR 0005](/docs/adr/0005-guests-share-one-member-and-network.md)). Its refusals say so: guests have used the guest network's limit, shared by everyone who signs in as a guest, and it resets at 00:00 UTC (`whoCounts` in `src/gateway.ts`); a member's network keeps "one network". Its settings' usage module says the same.
- **Re-runs:** starting a run again, after changing comps, the budget, or exclusions, starts a new run with its own conversation. When a run ends, the agent keeps the synced state it ended with, roster included, and `getRun` returns it, so every earlier run stays viewable read-only. Later per-run results in the synced state are kept the same way.

## Derived values

- **Band:** top, middle, or bottom third by rank within one ranking. A null affinity is "unscored".
- **Leading comp:** named only when there are two or more anchors and the top comp's explainability score beats the next one by 0.05 or more on that result. Below that, the UI says the comps contributed evenly.
- **Finalists:** the top five shows by fit after exclusions. A demographic mismatch flags a finalist but doesn't remove it.
- **Slot allocation:** the model proposes slot counts for the finalists. Code rejects a draft whose slots exceed a count budget or whose total exceeds a dollar budget, and a line for a show that isn't a finalist. The budget bounds the agent's draft, not the programmer's edits: an edited order may go over it, and the insertion order shows by how much.
- **Launch profile:** the launch's demographics, or with comps, the mean of the comps' values per age bucket and gender, over the comps Qloo returned demographics for. With comps, a bucket or a skew counts only when more than half the comps share it: a bucket must be above 0 for most comps as well as on average, and a skew must reach 0.2 for most comps as well as on average. So one comp whose listeners differ can't set the profile alone. The Demographics line says where the comps disagree, in words about their listeners: a band the mean alone would have checked, or comps that skew opposite ways by 0.2 or more. A bucket most comps over-index on whose mean is still 0 or below isn't checked, as without comps. Checked on 2026-10-17 against the sample launch, The Watch, which over-indexes only at 35 to 44 (+0.21) and skews male (+0.81), and whose finalists' only flag is The Bill Simmons Podcast, at 35 to 44:
  - **Comps that share an audience:** the film comps Blank Check, Filmspotting, and You Must Remember This average +0.30 at 35 to 44, their only over-indexed bucket on average, where two of the three over-index, and +0.39 male, with two of the three at 0.2 or more. Their profile flags exactly what The Watch's own profile flags, and the line notes no disagreement.
  - **Comps that don't:** Pop Culture Happy Hour, Still Watching, and Culture Gabfest are topical comps for The Watch, but their audiences disagree. Pop Culture Happy Hour skews female (−0.38) and Still Watching male (+0.37), and Still Watching alone over-indexes at 35 to 44 (+0.60). Pop Culture Happy Hour (+0.63) and Culture Gabfest (+0.27) both over-index at 55 and older. The plain mean skews male by only 0.03, and its top buckets are 55 and older (+0.21) and 35 to 44 (+0.09). With the majority rule (#89), only 55 and older counts, and the line says the comps disagree on 35 to 44 and on gender. A comps run on the sample network still flags 3 of its 5 finalists at 55 and older, where two of the three comps' listeners do over-index.
  - So the mean reads sensibly when comps share an audience. When they don't, only what most of them share is checked, and the line says what they disagree on. The evidence shows each comp's own values.
- **Demographic mismatch:** take the launch profile's two most over-indexed age buckets. Flag a candidate that under-indexes, with a value below 0, on either of them, or whose gender skew has the opposite sign to the launch profile's, when both magnitudes are 0.2 or more. Only a bucket above 0 is over-indexed, so a launch like The Watch has one, and no finalist is flagged for being below average where the launch is too. Values are compared at Qloo's three decimal places, past float noise such as 0.20600000000000004. The thresholds, the comps' majority included, are starting values to tune on the demo network, set in one place in [`apps/src/demographics.ts`](/apps/src/demographics.ts).
- **Slot value:** downloads per episode × CPM ÷ 1,000, rounded to whole dollars. The insertion order total is the sum of slot count × slot value. A show without downloads, or a network without a CPM, leaves its lines without a value and the total marked incomplete, never filled with a guess.
- **Topic move:** a show's topic-baseline rank minus its fit rank. A move of three or more places is highlighted. The topic rank counts only the shows on the fit chart, so shows that weren't scored can't inflate a move.

## Networks and launches

A signed-in network keeps the retired demo's per-instance agent design rather than moving its data into a shared database ([ADR 0001](/docs/adr/0001-agents-per-network-and-launch.md)): its roster and inbox live in its `NetworkAgent`, each launch in its own `LaunchAgent`, and D1 holds only the directory. Both classes extend `CrossfeedAgent`, so a network's roster, a launch's run, and a pitch run behave as the engine does, and the engine's suite, on its own test sessions, still covers that code.

### The network's agent

- **What it holds:** the roster, the CPM, the inbox, the booking and its pitch runs, and, in synced state, `launches`, the list of its launches with each one's summary, and `checklistDismissed`, the members who dismissed the setup checklist.
- **How it differs from the engine's:** it opens empty, never on the sample network but for the guest network. Its imports keep each show already on the roster as it was settled (match, candidates, comp search, and exclusion) and update only the figures the file brings; only new shows and failed lookups are looked up. They leave the CPM, and its sample label, as they were. It refuses what only a launch does (`startLaunch`, `editInsertionOrder`, `approveInsertionOrder`), and refuses `setCpm` on a page's own connection: owners change the CPM in settings, whose route calls it over RPC.
- **Launches:** `createLaunch` (a name, or up to three comps) plans the launch on its own agent and lists it, newest first, with a new ID. It refuses with code `limit` once the launches listed and those still being planned reach `LAUNCHES_PER_NETWORK`; the check and the count happen before its first `await`, so creates sent at once can't pass the cap together. The guest network's sample launches are listed the same way, each seeded on its own agent instead of planned (`listLaunch`, [Demo data](#demo-data)). `dropLaunch` takes a deleted launch off the list.
- **The roster for a run:** `rosterForLaunch` answers a launch's agent with the roster, the CPM, whether the CPM is labelled the sample's, for every launch, the evidence records the roster cites, and whether the network has its own Qloo key. It refuses with code `not_found` a launch its list no longer has, and with code `conflict` while any show is still being looked up.
- **The roster changed since:** after each settled change to the roster, it tells every launch how the roster now stands (`rosterKey`, sent to `noteNetworkRoster` and kept in its storage, so waking up sends nothing new), and a launch says when that differs from its latest run's copy (`rosterChanged`).

### A launch's agent

- **What it holds:** the launch, its runs, the ranking, the topic baseline, demographics, and the insertion order, and refuses roster and inbox actions.
- **A run:** `startLaunch` asks its network's agent for the roster over RPC, then copies the evidence records the roster cites into its own log under new call numbers, each marked `copiedFrom` the network's call, never `replayed`. The copy carries whether the CPM is labelled the sample's for every launch, which the run keeps as it keeps the CPM, so a run of any launch of the guest network priced at the sample CPM says so ([#333](https://github.com/m1kuorg/qloo/issues/333)); it carries the sample marker only for the guest network's sample launch ([ADR 0007](/docs/adr/0007-the-sample-network-is-the-guest-networks-data.md)), so no other launch stores or replays the sample run. It then runs as the demo's does. The roster stays as copied for that run; the next run copies it anew.
- **Once its network lets go of it:** before a start, an answer, an order's edit or approval, and each model turn, a launch's agent asks its network whether it still lists it (`gone` in `src/launch-agent.ts`). Once it doesn't, as after the daily clearing has taken the guest network's launches off its list and left their agents to the hourly retry, or when a deletion's wipe failed, it stops a run under way or waiting on a question, closes its open pages with 4410, and refuses the call with code `not_found`, each saying the reason its wipe was noted with (`launchCloseReason` in `src/wipe.ts`): that the guest network was cleared, or that the launch or its network was deleted. So no answer resumes a run's Claude conversation, and no run takes another model turn, once its launch is gone.
- **The sample launches' runs:** `seed`, over RPC only, seeds a launch's agent with the captured run of one of the guest network's sample launches, as the network lists it, calling neither Qloo nor Claude (`seedRun` in `src/agent.ts`, modelled on the replay): a new run with its `runs` row and snapshot, so `getRun` and its order's export read it; the records it cites copied under new call numbers and marked `fromSample`, in place of a `copiedFrom` or `replayed` mark; its start, and an approved order's approval, moved on by as long as it's been since it was captured, so its row reads as recent, while each record keeps when Qloo answered it; the run marked with when it was captured (`capturedAt`), and its row in the list of runs marked `fromSample`; and an approved order marked `fromSample`, as approved in the sample data rather than by anyone in the network ([ADR 0002](/docs/adr/0002-approval-stays-in-the-app.md)), which any change to the order drops. Its `sample` stays null, so only The Watch replays. A launch already planned or seeded is left as it is. The app says each of these is the sample data's. The API keeps its evidence's shape, without the mark, and its approved order says `fromSample`, as the MCP server's text says it was approved in the sample data.
- **Who started it:** each run records `startedBy`: from a page, the member's name on the connection; from a program, the name the Worker passes to `startLaunchAs`, an RPC-only start the operations module calls, which is the member's name for their session or `API key “<its name>”` for a key (#199). A member's ID is kept beside their name (`startedById`, and `approvedById` on an order), which the API never returns.
- **Its row on the Launches page:** after each change to its status or summary, it reports its row to the network (`reportLaunch`), trying a failed report again, and reports nothing until the network has listed it (#211). The status follows the latest run and then the order: `new`, `running`, `waiting`, `failed`, `stopped`, `ranked`, `order drafted`, or `order approved`; the row also carries the name or comps, finalists, slots, total slot value, who started the last run, and when. The API spells statuses in snake case (`order_drafted`).

### Members on agent connections

- **Who may connect:** `/agents/network/<id>` lets through only a WebSocket upgrade from an `APP_ORIGINS` page, signed in by one of the network's members; `/agents/launch/<id>/<launchId>` checks the same and that the network lists the launch (`listsLaunch`). Anything else is the same 404 as a network that doesn't exist.
- **Naming the member:** the Worker sets `Crossfeed-Member` (and, URI-encoded, `Crossfeed-Member-Name`) on the upgrade, overwriting any copy the browser sent, and the agent's `getConnectionTags` turns it into a `member:<id>` tag. Approval and dismissing the checklist read that tag.
- **Closing a member's pages:** `kick(memberId, reason)` closes every connection with their tag, the network's own and each of its launches', with close code 4403, which the client takes as final and answers with "You're no longer a member of this network." or the reason given. Removing a member, leaving, signing out everywhere, and deleting an account call it once the directory has let go of them. Deleting a launch or a network closes its pages with 4410 ("This launch was deleted.", "This network was deleted."). Vite's dev server drops a close the server starts, so these are seen on the built Worker.

### Deleting launches, networks, and accounts

D1 has no interactive transactions and an agent's storage can't join a D1 batch, so each deletion lets go of the directory first, then wipes the agents, and keeps a note in the `wipes` table until each wipe succeeds, which the instance's own reset after it can say (`awaitWipe` in `src/wipe.ts`, #297):

- **A launch** (any member, from the Launches page; `deleteLaunch` in `src/wipe.ts`): its wipe is noted, the network's list drops it, so its page, agent, and export answer 404, then its agent wipes itself (`destroy`).
- **A network** (an owner, typing its name; `deleteNetwork`): one batch deletes its directory rows, which cascade to memberships, invite links, and API keys, and notes a wipe for each instance it has, its launches' agents, its own agent, and its `network:<id>` gateway instance; then the network's agent lets go of its pages (`letGo`, naming any launch planned meanwhile), and each instance is wiped, launches first.
- **An account** (`deleteAccount`): refused while the member is any network's only owner. One batch deletes the member, whose passkeys, sessions, and memberships cascade, revokes the API keys and open invite links they made, and notes a `NetworkAgent.forgetMember` for each network they're in and each they left or were removed from (`past_memberships`, written by `removeMember` as a membership ends; #228); the pages of their current networks close. Each network then drops the member from its own state, keeping the replies they approved approved but without `approvedBy`, and taking them off `checklistDismissed`; has each of its launches replace their name with "Former member" in its runs and orders, matched by member ID (#206); and finally strips its run records of their copy of the dashboard's launches and checklist, which named people with no ID to match. Memberships that ended before migration 0004 left no record, so those networks keep the name. Each forget is made again by the next cron before it's crossed off, in case a run or approval in flight landed the name after.
- **What guests made** (the daily cron, [ADR 0008](/docs/adr/0008-guests-share-one-guest-member-again.md)): besides the guest network's clearing, two batches of their own, so a failure in one leaves the rest of the clearing done. The first (`removeTemporaryGuests` in `src/wipe.ts`, `dropTemporaryGuests` in `src/directory.ts`) removes the temporary guest members [ADR 0006](/docs/adr/0006-each-guest-is-a-member.md) made, every member marked `guest` but the guest member: it deletes the networks only they own, those with an owner among them and none who isn't, never the guest network, as a deleted network's rows go, with a wipe of each one's agent noted first; deletes the API keys and invite links they made; and deletes them, whose passkeys, sessions, memberships, and past memberships cascade. Nothing is forgotten in the networks they were in. A network's launches are listed only in its agent, so its wipe notes theirs when the retry makes it. It logs `guests_removed` with how many members and networks it removed. The second (`clearGuests` in `src/wipe.ts`, `clearGuestMember` in `src/directory.ts`) lists the networks only the guest member owns besides the guest network, at most `NETWORKS_PER_MEMBER` (`guestOwnedNetworks`); each lets go of its open pages (`letGo`) and names the launches it lists. Then one batch notes a wipe of each of their instances and deletes them, while the guest member is still their only owner; takes the guest member out of every other network but the guest network, unless it's that network's only owner; deletes the API keys and invite links it made, so the guest network's setup checklist starts over; and sets `created_by` to null on the networks it created that stay, so its networks-per-member count frees. Guests' open pages of the networks it left close (`kickMember`), and the next hourly runs' retry wipes the deleted networks' instances. It logs `guest_member_cleared` with how many networks it deleted and left.
- **The cron's retry** (every hour but 12:00 UTC): `retryWipes` tries 23 noted wipes or forgets again (`WIPES_PER_RUN`) once each is a minute old, the ones that failed and the guest network's launches the daily clearing left to it, and leaves the rest for the next hour's run, so a run makes at most 49 D1 queries (a batch is one), within the 50 D1's limits give a Free plan invocation, though a probe on this account ran 1,000: a wipe makes at most two, and the run's three directory batches three more. A wipe's Durable Object calls, at most four, count toward the Free plan's 1,000 subrequests to Cloudflare services, not its 50 external ones, as the probe showed ([crons](#bindings)). It takes those no run has tried first, oldest first, launches before a network's own gateway instance among those noted together, then those tried before, the least recently tried first. It notes when it last tried each in one batch before it tries them (`wipes.tried`, migration 0013), each a millisecond earlier than the one ahead of it, so the next run takes first those this run reached last, and a wipe that fails, or whose run is cut off as it tries it, as when its instance hangs, goes after those no run has tried and those its run never reached. So wipes that fail every time take turns in what's left of each run and never hold back the rest. It crosses off instead a launch its network still lists while the network is still in the directory, whose deletion stopped before the list let go of it. A network's agent it wipes lets go first, closing its open pages with 4410, and names the launches it lists, whose wipes, and its gateway instance's, are noted in one batch for the next runs; a launch an owner's deletion already wiped is wiped again, empty. Each wipe closes its instance's open pages with the reason it was noted with (`wipes.reason`): that the guest network was cleared, or that it was reset to the sample data, for the launches its clearing left to the retry, or that the launch or its network was deleted. It logs `wipes_retried` with how many it wiped, kept, and failed.

### A network's own Qloo key

- **Choosing a gateway:** an agent reaches Qloo through `gateway()`: an engine session's goes to `global`; a network's or launch's agent goes to `network:<networkId>` while it knows the network has its own key, and to `global` otherwise. Knowing costs no RPC: the network's agent keeps the flag in its own storage (`hasOwnKey`, written by `noteOwnKey`) and tells each launch (`LaunchAgent.noteOwnKey`); a launch that missed a notice catches up when its next run copies the roster (`RosterCopy.ownKey`). A network without a key never has a gateway instance of its own (#197). A network agent from before #197 asks its gateway instance once, as it next starts.
- **Adding it** (owners, `POST /app/<id>/settings/qloo-key` with the host and key): the network's instance tests the key with one search before saving it, refuses one Qloo answers 401 with Qloo's words, and keeps it sealed with AES-GCM under a key derived with HKDF from the Worker secret `QLOO_KEY_SECRET`, with its host, its own cache, and its own Qloo counts. Every test counts against the instance's daily cap, which bounds key tests, and a saved key's test also counts among the network's Qloo calls, as a call made on its key that its usage shows; a refused one's doesn't, since nothing reads the instance's counts until a key is saved. The key is never returned, logged, or put in a page: settings show its host and last four characters to owners, and only whether one is set to members. A second key is refused (409) until the first is removed.
- **Removing it:** the agents are told first, then the instance is wiped; if the wipe fails, they're told the key is back and the route answers 500, so it can be removed again. A wiped instance fails any call still out with `WIPED` ("The network's own Qloo key was removed, or the network deleted, while this call was out, so it was cut off. …"). Its reset says `WIPED` too, or `WIPE_FAILED` when the wipe fails, which the route answers 500 for. Deleting the network wipes the instance too.
- **What stays global:** model runs, free starts, and the sample run, which spend or protect Crossfeed's own keys.

## Members and sign-in

Members sign in with passkeys only, built in-house ([ADR 0003](/docs/adr/0003-passkeys-built-in-house.md)), except the guest member, whom everyone who signs in as a guest is signed in as, without one ([ADR 0008](/docs/adr/0008-guests-share-one-guest-member-again.md)); `src/routes/auth.tsx` serves the ceremonies and `src/auth.ts` holds the cookie and the guards every accounts route shares. The relying party ID and the allowed origins are configuration per environment, `RP_ID` and `APP_ORIGINS`, never read from the request.

### Passkeys and sessions

- **Ceremonies:** `@simplewebauthn/server` on the Worker and `@simplewebauthn/browser` on the sign-in page, each ceremony two requests: options, then the browser's answer. A challenge is kept in the directory for five minutes and taken back once (`DELETE … RETURNING`), so a replayed or late answer is refused. Passkeys are discoverable (`residentKey: 'required'`), user verification is required, attestation is `none`, and a signature counter of 0 is accepted for synced passkeys.
- **Sign-up** asks for a name only. The member's random ID is the passkey's user handle, and the member's row is written only after the registration verifies, in one batch with the passkey and the session. Each passkey is labelled with the browser it was added from.
- **Sign-in** asks for nothing but the passkey (no `allowCredentials`).
- **Guest sign-in** (`POST /auth/guest`, [ADR 0008](/docs/adr/0008-guests-share-one-guest-member-again.md)) asks for nothing: it signs in as the guest member and answers `{ next }`: `?next` under the sign-in's rules, or else `/app`, which opens the guest network's dashboard. It also takes a plain form's post from Crossfeed's public pages, whose guest buttons work with no script ([ADR 0007](/docs/adr/0007-the-sample-network-is-the-guest-networks-data.md)), and answers it with a 303 redirect to `next`, or, refused, back to the sign-in page's guest panel (`/sign-in?guest=minute` or `day`, `#guest`), which says why. Under the app's `Referrer-Policy: no-referrer`, browsers send a form post's `Origin` as `null`, so the route takes a form post whose `Sec-Fetch-Site` is `same-origin` (`fromAppForm`), never a bare `null` or a missing header; CSP's `form-action 'self'` keeps the form's action the app's own. A GET never signs in. One batch (`guestSignIn` in `src/directory.ts`) writes, first, a session of the guest member's, under the fixed ID `guest-member` (`GUEST_MEMBER`), for a day, which never proves its member was there (`verified` stays null) and isn't extended; then, each only where that session was written, its row in `guest_signins`; the guest network's row again if it's gone, under the fixed ID `guest-network` (`GUEST_NETWORK`), which holds no `:`, since an agent's name splits on it; the guest member's row again if it's gone, "Guest", with the `guest` mark (migration `0006_guest_members.sql`), no passkey, and a recovery code hash that no SHA-256 output is, so no code names it; and its membership of the guest network, made an owner's. The session names the guest member before the batch makes its row again, so the batch defers its foreign keys to its end (`PRAGMA defer_foreign_keys`). A browser that holds a live session, a member's or a guest's, isn't signed in again: it's answered its `next`. Each sign-in logs `guest_sign_in`. Migration `0009_shared_guest_member.sql` made the guest member again, as migration 0005 had before 0006 retired it ([ADR 0005](/docs/adr/0005-guests-share-one-member-and-network.md)), and the guest network's owner; it deletes nothing, so code from before it can run beside it, and the temporary guest members [ADR 0006](/docs/adr/0006-each-guest-is-a-member.md) made stay until the daily clearing removes them. The guest network's agent sets its CPM to the sample network's (`sampleCpm`) whenever it starts with none, and leaves its roster as guests left it.
- **Sessions:** a random token in the `__Host-crossfeed_member` cookie, HttpOnly, Secure, and SameSite=Lax, valid 30 days from last use and extended at most once a minute, or, for a guest, a day from sign-in and never extended, its cookie too; the directory keeps only its SHA-256 hash. Sign-out deletes it, and "Sign out everywhere" deletes every session of the member and closes their open agent connections. `?next` is followed only when its parsed path is on this site and doesn't start `//`.
- **The guest member** ([ADR 0008](/docs/adr/0008-guests-share-one-guest-member-again.md)): an owner of the guest network, and of every network a guest creates, so a guest takes every owner action there: settings and CPM, invites, members, API keys, a Qloo key, deleting the network, and creating networks. Opening `/app` makes it an owner of the guest network again, making the network's row again if it's gone (`restoreGuestOwner`), and opens the guest network, since the network the guest member opened last is any guest's. The guest network has no exemption from the last-owner rule (`ONLY_OWNER` and `KEEPS_OWNER` in `src/directory.ts`), so the guest member owns it while it's the only owner. One guard (`guestRefused` in `src/auth.ts`) refuses a member marked `guest` every change to the account every guest shares, with one 403 that names it and points to "Sign out and create an account": adding a passkey (both requests) and a new recovery code, first in `stepUpRefused`, so no challenge is written; renaming it; signing out everywhere; deleting it; joining a network by invite (`/auth/join`); and its own leaving, removal, or role change in any network. The directory's statements for renaming, a new recovery code, adding a passkey, deleting a member, and signing out everywhere refuse `guest = 1` too. The daily cron clears the guest network (`resetGuestNetwork` in `src/wipe.ts`): its agent lets go and names the launches it lists, then one batch restores its name to "Guest network" and notes a wipe of each launch, of its agent, and of its own Qloo gateway instance; then its agent is wiped, which takes the launches off its list, so their pages and agents answer 404, then its gateway instance, with any key a guest added. The launches' own agents are left to the hourly retry, which closes any page of one still open, and until then each takes no more work ([A launch's agent](#a-launchs-agent)). Its directory rows stay, so guests keep their sessions; its open pages close with 4410, "The guest network was cleared, as it is every day at 12:00 UTC.", and its agent's next start loads the sample network, and the sample inbox, again ([ADR 0007](/docs/adr/0007-the-sample-network-is-the-guest-networks-data.md)). The clearing starts the agent, if it isn't running, with `CLEARING` (`src/network-agent.ts`), as every wipe of a network's agent does, so a start then loads no sample to wipe. A wipe that fails stays noted for the next hour's retry and fails the cron's run. Its daily caps are counted in the global gateway, so the clearing leaves them as they are. An owner resets the guest network the same way from its settings, within the limits [Resetting the sample data](#demo-data) gives. The same cron clears what guests made beyond it ([Deleting launches, networks, and accounts](#deleting-launches-networks-and-accounts)). The app shell shows a guest a notice on every page that they're signed in as Guest, the one account every guest shares, that every guest works in the guest network and the networks guests create, which are cleared daily, and that every guest's limits are shared, with "Sign out and create an account", the account menu's Sign out. A guest's account page says only why no guest can change the account, and offers signing out, reading none of its passkeys or sessions; the invite page tells a guest to sign out and create an account to join; the members module offers the guest member nothing on its own row; and the Qloo key module tells a guest that every guest shares a key added there.
- **The account page** (`/app/account`) renames the member, adds a passkey (`/auth/passkeys/options` and `/auth/passkeys`, which exclude the passkeys they have, so one device adds no second), removes one (never the last), issues a new recovery code, signs out everywhere, lists their networks to leave, and deletes the account.

### Recovery codes and step-up

- **Recovery code:** random, shown once at sign-up and whenever it's used or a new one is asked for, and stored only as a hash. Signing in with it (`/auth/recover`) replaces it in the batch that starts the session and lands on `/app/account?recovered`, which asks for a passkey for that device.
- **Step-up (#217):** adding a passkey (both requests), a new recovery code, and deleting the account need the session to have proved its member was there in the last five minutes: a sign-up, a passkey sign-in, a recovery, or `POST /auth/verify`. Each session keeps when (`verified`) and whether it signed in with a recovery code (`recovered`), from migration `0002_step_up.sql`. Past five minutes, `stepUpRefused` answers 403 with `stepUp: 'passkey'` and a challenge for the member's own passkeys, or, for a recovered session, `stepUp: 'code'`. `/auth/verify` takes either the passkey's answer or `{ code }`, which it only checks and doesn't use up. The account page answers the step-up in place and sends the change again (`sendConfirmed`). A guest is refused before any of it, as above.

### Invites and members

- **Invite links:** an owner makes one in settings and sees it once. Its token rides in the link's fragment (`/invite#<token>`), so the browser never sends it in a path, query, or referrer; the invite page posts it to `/auth/invite`, which answers the network's name, and whether the daily clearing clears it (`clearedDaily`), as the guest network, whoever else owns it, or a network only guest members own, so the page says it's cleared every day at 12:00 UTC ([ADR 0008](/docs/adr/0008-guests-share-one-guest-member-again.md)); or why the link can't be used (404 unknown, 410 used, revoked, or expired). A signed-in person joins with `/auth/join`; a new one signs up with the invite, in one batch that writes the account, uses the invite, and adds the membership, or nothing. A link works once, expires after seven days, can be revoked while unused, and is kept as a hash.
- **Roles:** owner or member. Each guard is one conditional statement or one `batch()`: using an invite, the networks-per-member cap, and the last owner, whom no demotion, removal, or leaving can take away (409). The guest member is an owner of the guest network ([ADR 0008](/docs/adr/0008-guests-share-one-guest-member-again.md)), so a guest takes every owner-only action in it, but for its own leaving, removal, or role change.
- **Former owners:** an owner who leaves, is removed, is made a member, or deletes their account loses the API keys and open invite links they made there, in the batch that changes their membership (`revokeUnowned`); migration `0003_revoke_unowned.sql` revoked, once, those already held by a non-owner.

### Request guards

- **The switch:** `accountsOn` answers 404 on every auth, app, API, and MCP route while `ACCOUNTS` is off, and no page links to them.
- **Cross-site requests:** every state-changing request authenticated by the session cookie, and every agent WebSocket upgrade, must carry an `Origin` in `APP_ORIGINS`; a missing `Origin` is refused, and so is `null`. API-key requests carry no cookie and skip the check. Pages write with `fetch`, never an HTML form: under `Referrer-Policy: no-referrer`, Chrome sends a form POST's `Origin` as `null`.
- **Headers:** every answer but an agent's connection gets Hono's secure headers with `Referrer-Policy: no-referrer` and a Content-Security-Policy of `default-src 'self'; script-src 'self'; style-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. In development only, `script-src` adds the request's nonce for Vite's React refresh preamble and `style-src` adds `'unsafe-inline'` for Vite's injected styles. No server-rendered page has an inline script or a `style` attribute, so the landing page's re-rank moves each row by its two ranks, set as data attributes (`data-l`, `data-t`) that the stylesheet reads; the island sets the styles it computes through the DOM, which the policy doesn't govern.
- **Body limits:** 64 KB of JSON under `/auth/*` and `/app/*` (`jsonLimit`, a 413 with its words), and 5 MB plus 64 KB under `/api/v1/*` and `/mcp` (`uploadLimit`, a 413 `too_large`), whether the body states its length or streams in without one.
- **Rate limits:** the Workers rate limiting binding, in fixed one-minute windows: `API_LIMITER` allows 120 requests a minute per API key, on the API and the MCP server together, `AUTH_LIMITER` 20 a minute per visitor on the routes that write before anyone signs in (`/auth/sign-up/options`, `/auth/sign-up`, `/auth/sign-in/options`, `/auth/recover`), and `CREATE_LIMITER` 30 a minute per member on creating API keys and invite links, the two together, across their networks (`POST /app/:networkId/settings/api-keys` and `.../members/invites`). Past any, a 429 says to wait, with `Retry-After: 60`.
- **Creating keys and invite links:** the caps count only keys in use and links open, so revoking makes room at once, and `CREATE_LIMITER` alone slows a script that creates and revokes in a loop. It's counted by member ID, once the member is known to own the network and before the name or the cap is checked, so a 403 or a 404 doesn't count, and an attempt refused for its name or at the cap does; revoking is never limited. Every guest is the one guest member, so guests share one count, as the binding keeps it, per Cloudflare location: one guest looping at 30 a minute refuses every guest's keys and links for the rest of that minute, as the guest sign-in limits and the guest network's daily caps hold for every guest at once. It slows such a loop and doesn't stop it: at 30 passes a minute, each writing about 6 rows for a key or 7 for a link, counting indexes, a loop still writes D1's free 100,000 rows a day in about 8 to 9 hours ([#350](https://github.com/m1kuorg/qloo/issues/350)).
- **Guest sign-ins:** `/auth/guest` is under none of the bindings, whose counts are kept per Cloudflare location, nor any per-visitor count. All guest sign-ins together get `GUEST_SIGNINS_PER_MINUTE` (30) a minute and `GUEST_SIGNINS_PER_DAY` (1,000) a UTC day, from any address or none, counted in `guest_signins` (`created`, indexed), a log that deleting sessions or accounts can't shrink: the statement that writes a guest's session writes it only while fewer sign-ins than each were logged in the last minute and since 00:00 UTC, and the rest of the batch follows the session, so D1 counts every request exactly. Past the minute's, a 429 says guest sign-ins are busy for everyone, with `Retry-After: 60`; past the day's, a 429 says so, with `Retry-After` the seconds to 00:00 UTC. The day's keeps the rows guest sign-ins add inside D1's free daily writes. The hourly cron's purge deletes the rows neither counts any more, those from before both 00:00 UTC and the last minute.

### Limits on sign-ups, networks, and launches

- **Sign-ups:** at most `SIGNUP_VISITOR_DAILY_CAP` (5) per visitor per UTC day, counted in the global gateway under the visitor's salted hash; joining through an invite doesn't count. In its place, one member's invite links bring in at most `INVITED_SIGNUP_DAILY_CAP` (20) new accounts a UTC day, refused at both sign-up steps. Every guest's links count as one member's: an invite a guest makes is marked `guest` (migration `0007_guest_invites.sql`), and its sign-ups count with every guest-made link's, whoever made it and whether or not they or its network are still there, from `guest_invited_signups` (`created`, indexed; migration `0008_guest_invited_signups.sql`), which the sign-up's batch writes as it uses a guest's link, and the hourly cron's purge prunes to the UTC day.
- **Networks:** a member creates at most `NETWORKS_PER_MEMBER` (3), counted by who created them, whoever owns them now.
- **Launches:** a network keeps at most `LAUNCHES_PER_NETWORK` (100) at once; deleting one makes room, and only a member's session can delete.
- **Invite links:** a network keeps at most `INVITES_PER_NETWORK` (20) open at once.
- **API keys:** a network keeps at most `API_KEYS_PER_NETWORK` (10) in use at once, as each key has its own `API_LIMITER` count. A revoked key doesn't count, however it was revoked, so revoking one makes room at once.
- **Text:** names at most 64 characters (`MAX_NAME`), titles, launch names, comps, and past guests at most 200 (`MAX_TITLE`), typed answers at most 2,000 (`MAX_ANSWER`), and angles at most 500 (`MAX_ANGLE`), checked in the agent and in the API's schemas, so the MCP server too.
- **Daily caps:** each network counts as a visitor of its own ([agent limits](#agent-limits)).

A variable left unset refuses everything it limits, as `Number(...) || 0` reads it, so each must be set in both environments.

## Uploads

One module, `src/upload.ts`, turns files into what the agents already take, for the browser and the API alike. The files themselves are never kept; the pitches they hold live in the inbox like pasted ones.

- **Roster:** `readRosterUpload` reads one `.csv` (a `name` column, with optional `downloads`, `status`, and `description`) or one `.txt` with a show name per line into roster text and its format. It refuses another type, more than one file, an empty file, or one over 5 MB (`MAX_UPLOAD_BYTES`) before reading it; the roster parser then refuses a CSV without a `name` column, or more than 50 shows.
- **Pitches:** `readPitchUpload` reads `.eml` files with `postal-mime` (from their bytes, so each part keeps its charset; HTML-only mail is read as its text), an `.mbox` export split into its emails, or a `.txt` split on lines of `---`, where `From:` and `Subject:` lines atop a pitch give its sender and subject, as they do a pasted pitch's (`headed` in `src/inbox.ts`), into pitches of sender, subject, and plain-text body. It refuses another type, an empty or oversized file, or a file with no pitch in it. `loadInbox({ pitches })` keeps the 50-pitch limit, and skips and names an uploaded pitch with no text or over 10,000 characters (`inbox.skipped`) rather than refusing the load; a pasted pitch over the limit, or with no text after its `From:` or `Subject:` lines, is still refused.
- **Reading HTML:** the HTML-to-text reader runs in one pass, so a broken tag, comment, or dropped element runs to the end and is dropped, and the check for an email address in a title is a linear scan, so no crafted email or title takes quadratic time (#217).
- **In the browser:** the roster and inbox pages take a file from a picker or dropped anywhere on the window (`useFileDrop`). `postal-mime` is imported as the first email is read, so pages that take only a roster file never load it.
- **Over the API:** a request body is wrapped as a file named by its `Content-Type` (`text/csv`, `text/plain`, `message/rfc822`, `application/mbox`), sized by its `Content-Length` when it sends one, so an oversized one is refused unread; the inbox also takes `application/json` pitches.
- **Refusals** are `Refusal`s: `too_large` (413) for the size, `unreadable` (422) for the rest.

## REST API

`src/routes/api.ts` is an `OpenAPIHono` sub-app from `@hono/zod-openapi` under `/api/v1`, so each route's zod schemas validate its request and make its part of the OpenAPI 3.1 document served at `/api/v1/openapi.json`. Each route is a thin adapter over `src/operations.ts`, which the MCP server shares.

- **Callers:** an API key in `Authorization: Bearer cf_live_…`, found by its secret's hash, refused once revoked (401), counted against `API_LIMITER`, and reaching only its own network; or a member's session cookie, reaching the member's networks, whose writes need an `APP_ORIGINS` `Origin`. Any network the caller can't reach answers 404, the same as one that doesn't exist. Owner-only changes check the caller in the operation.
- **Resources:** the network (read, rename, CPM, usage), the roster (read, import a CSV or text body, update a show, search comps), launches (list, create, read, delete with a member's session only), runs (start, read, answer), insertion orders (edit a draft, export an approved one as CSV), a launch's evidence, the inbox (read, load emails, text, or JSON, confirm a work), pitch runs (list, start, read, answer), and replies (edit, discard). Members, invites, API keys, the Qloo key, and deleting the network are the app's.
- **No approve route** ([ADR 0002](/docs/adr/0002-approval-stays-in-the-app.md)): `.../approve` is a 404 and a `status` field is a 400. Exporting a draft answers 409.
- **Long work** (an import, an inbox load, a run) answers 202 with the resource's current status, and the client polls the resource. Importing over a roster that has shows, or loading over an inbox that has pitches, needs `?replace=true` or answers 409.
- **Errors** are `{ "error": { "code", "message" } }`, with the code's status: `invalid` 400, `unauthorized` 401, `forbidden` 403, `not_found` 404, `conflict` 409, `too_large` 413, `unreadable` 422, and `limit` or `rate_limited` 429 (`REFUSALS` in `src/refusal.ts`). An agent's refusal the API must tell apart throws a `Refusal`, whose `code` is an own property that workerd keeps across Durable Object RPC; anything else is a 500 `internal`.
- **Costs:** each operation in the document carries what it costs as `x-crossfeed-cost`, one of "Reads", "Changes", "Deletes", "Spends a model run" and "Calls Qloo", from one table beside the routes, `COSTS`. A route with no row there fails at startup, and a test checks the labels. Deleting a launch, which only a member's session sends, has the session alone as its `security`, and so `x-crossfeed-session-only: true`. Two routes do more with `replace=true` than their label says: importing a roster over one that has shows changes the figures the file brings, and loading the inbox over one that has pitches deletes them, with the last pitch run's lists and replies, and ends a pitch run waiting on a question. `/docs/api` shows the labels under a legend that says so.
- **Gates:** the inbox and pitch run routes answer 404 while `GUEST_PITCHES` is off; the document lists them either way. Everything answers 404 while `ACCOUNTS` is off.
- **Examples** in the document, the docs, and the SDK's tests use made-up shows and scores, never a Qloo response; a test checks the document names nothing the sample network looks up.

## SDK

`@crossfeed/sdk`, in [`packages/sdk`](/packages/sdk/README.md), is a typed client of the REST API with no runtime dependency beyond `fetch`, so it runs in Node, Bun, Deno, and Workers. It's `private: true` until publishing is approved in [#63](https://github.com/m1kuorg/qloo/issues/63).

- **Client:** `new Crossfeed({ apiKey, networkId, baseUrl?, fetch? })`; `baseUrl` defaults to the production Worker. Its namespaces mirror the API: `network`, `roster`, `launches`, `runs`, `insertionOrders`, `evidence`, `inbox`, `pitchRuns`, and `replies`.
- **Waiting:** `waitForRoster`, `waitForInbox`, and `waitForRun` poll until the work settles or a question is open, reject a failed or stopped run, and take a timeout and an `AbortSignal`.
- **Errors:** a `CrossfeedError` carrying the API's `code`, `message`, and `status`.
- **Types:** generated from the Worker's OpenAPI document with `openapi-typescript`, which runs with the repo root's TypeScript 5 because `apps/`' TypeScript 7 dropped the compiler API it needs. `bun run generate` in `packages/sdk` refreshes `openapi.json` and `src/openapi.ts`; `apps/test/sdk.test.ts` fails while either is stale, or while a documented route has no method.

## MCP server

`/mcp` (`src/routes/mcp.ts`) is `createMcpHandler` from `agents/mcp/server` with `@modelcontextprotocol/server`, over Streamable HTTP and stateless, created once; each request gets its own `McpServer` for the network its key reaches.

- **Auth:** the route checks the API key with the REST API's own `keyFor` (401, or 429 past `API_LIMITER`) before the handler runs, and passes the key's ID, name, and network through `authInfo`, never its secret; keys don't expire, so there's no OAuth. The handler's Origin check allows localhost-class origins and the hostnames of `APP_ORIGINS`; clients that send no `Origin`, as Claude Code doesn't, pass.
- **Tools:** each is a thin adapter over `operations.ts` that takes its input through the REST API's zod schemas: `get_network`, `get_roster`, `import_roster`, `update_show`, `search_comps`, `list_launches`, `create_launch`, `start_launch_run`, `get_launch`, `answer_launch_question`, `edit_order`, and `get_evidence`, plus, while `GUEST_PITCHES` is on, `get_inbox`, `load_pitches`, `confirm_work`, `start_pitch_run`, `list_pitch_runs`, `get_pitch_run`, and `answer_pitch_question` (12 or 19 tools). Each carries `readOnlyHint` and `destructiveHint`. There is no approve tool.
- **Relaying questions:** every tool's description ends by telling the assistant to ask the human each open question as it is and answer with their words, never its own.
- **Results:** concise text that says what's next (the question and how to answer it, the next tool, the app page where a member approves), and the operation's result as structured content with that text as `summary`, since Claude Code gives its model only the structured content. A refusal is a tool error carrying `{ error: { code, message } }`.

## Skills, plugin, and developer docs

- **Agent Skills:** `plugins/crossfeed/skills/plan-launch-promos` and `triage-guest-pitches`, written to the Agent Skills spec with only its frontmatter fields. Each relays the agent's questions word for word, never approves, keeps guest names and sender details out of every field but the ones made for them, and reads the evidence before saying why something ranks.
- **Claude Code plugin:** `plugins/crossfeed`, with `.claude-plugin/plugin.json`, `.mcp.json` declaring the `http` server at `${CROSSFEED_URL:-https://crossfeed.m1kuorg.workers.dev}/mcp` with `Authorization: Bearer ${CROSSFEED_API_KEY}`, and the two skills. The repo root's `.claude-plugin/marketplace.json` lists it, so it installs from a clone now and from the repo once it's public.
- **Developer docs:** `/docs` (what a program can and can't do, API keys, long work, limits, errors), `/docs/api`, `/docs/sdk`, `/docs/mcp`, and `/docs/agents`, server-rendered on the marketing shell, with `/llms.txt` linking every page and each skill's `SKILL.md` served as it is. What could drift is read from its owner: the API reference from the OpenAPI document, the MCP page from the server's own `tools/list`, the error codes from `REFUSALS`, the limits from the Worker's variables and the modules that hold them, and the skills and `.mcp.json` from `plugins/crossfeed`. While `ACCOUNTS` is off the pages still describe the API and the MCP server, say they answer 404 on that deployment, and link neither.

## Storage

What a network works on is Durable Object SQLite: strongly consistent, private to each instance, and up to 10 GB per object ([Durable Object limits][cf-do-limits]). What has to be looked up across instances is D1.

- **`CrossfeedAgent`:** the synced state the UI renders, which the Agents SDK persists: the roster with each show's resolution and figures, the launch and its comps, the latest run with its notes, question, budget, and exclusions, the session's run list, the fit ranking with the topic baseline and demographics, the insertion order, the inbox, and the booking with its lists and replies. Beside it, SQL tables for the evidence log (`evidence`), each run's conversation with Claude (`conversation`), each run's limit counts and the state it ended with (`runs`), a turn paused on a question (`paused`), and the topic baselines by request hash (`topic_baselines`).
- **`NetworkAgent` and `LaunchAgent`:** the same state and tables, each holding its own part ([Networks and launches](#networks-and-launches)): a network's agent its roster, inbox, booking, `launches`, and `checklistDismissed`, plus, in its key-value storage, whether the network has its own Qloo key (`crossfeed_own_qloo_key`) and the roster key it last sent its launches; a launch's agent its runs, rankings, and orders, with the evidence records it copied from the roster, and the own-key flag it was last told.
- **`QlooGateway`:** in each instance, the response cache, keyed by a hash of the method, path, and sorted parameters, the daily Qloo call counter, the latest failure after retries, and today's model run, free start, Qloo call, and sign-up counts (`model_runs`, `free_starts`, `visitor_calls`, `signups`), keyed by a hash of the visitor, or `network:<id>`, and the day. The `global` instance also keeps the stored sample run; a `network:<id>` instance keeps its network's sealed key and host (`own_key`).
- **D1 directory** (`crossfeed`, and `crossfeed-preview` on the preview), with its schema in `apps/migrations/`: `members` (ID, name, the recovery code's hash, and the `guest` mark), `passkeys` (credential ID, member, public key, counter, transports, label, created, last used), `sessions` (token hash, member, created, expires, last seen, `verified`, `recovered`), `challenges` (a ceremony's challenge, its kind, and the name or member it's for, for five minutes), `networks` (ID, name, who created it), `memberships` (network, member, role `owner` or `member`, joined, last opened), `past_memberships` (a network a member left or was removed from, kept so deleting their account forgets them there), `invites` (ID, token hash, network, maker, created, expires, used, used by, revoked), `api_keys` (ID, network, name, prefix, secret hash, maker, created, last used, revoked), `wipes` (agent instances still to wipe, each with the reason its open pages are told and when the hourly retry last tried it, and networks still to forget a deleted member), `sample_launches` (the guest network's sample launches, each as JSON in chunks under 100 KB, D1's limit on one statement, [Demo data](#demo-data)), `sample_resets` (when an owner last reset the guest network to the sample data, and how many times that UTC day, one row), and the logs `guest_signins` and `guest_invited_signups` (when each guest sign-in, and each sign-up through a guest's link, was). Times are epoch milliseconds. Tokens, recovery codes, and API key secrets are random, handed out once, and kept only as SHA-256 hashes; an API key is `cf_live_` and 32 random bytes, with its first 12 characters kept as its prefix. `created_by` and `used_by` columns go null when their member is deleted, and a network's memberships, invites, and keys cascade with it. `last_seen` and `last_used` are written at most once a minute. The hourly cron purges expired sessions, challenges, and invites, and the two logs' rows no limit counts any more; the daily cron removes the temporary guest members. Migrations: `0001_directory.sql` (every table), `0002_step_up.sql` (the sessions' step-up columns), `0003_revoke_unowned.sql` (a one-time revocation, [Invites and members](#invites-and-members)), `0004_past_memberships.sql` (memberships that ended), `0005_guest_network.sql` (the guest member, the guest network, and its membership, and the sessions' index by member and creation, [Passkeys and sessions](#passkeys-and-sessions)), `0006_guest_members.sql` (a guest member per guest sign-in, and their log), `0007_guest_invites.sql` (guests' invite links marked), `0008_guest_invited_signups.sql` (the log of sign-ups through guests' links, and an index removing expired guest members read), `0009_shared_guest_member.sql` (the guest member again, the guest network's owner, and that index dropped), `0010_sample_launches.sql` (the sample launches' table, empty: its rows are Qloo data, loaded into each environment by hand), `0011_wipe_reasons.sql` (each wipe's reason), `0012_sample_resets.sql` (the sample data's resets, one row), and `0013_wipe_tries.sql` (when the hourly retry last tried each wipe); an applied migration is never edited.

KV is a poor fit because writes take 60 seconds or more to propagate, and the Cache API doesn't replicate beyond its data center ([KV][cf-kv], [Cache API][cf-cache]). D1 suits the directory because it's small, read by the Worker before any agent is reached, and needs uniqueness and foreign keys across networks; every guard on it is one conditional statement or one `batch()`, since D1 has no interactive transactions.

## Client protocol

- **State:** the agent's synced state carries what the UI renders: the roster with resolution states, the current run's status and the progress notes code writes for each tool call, such as "Scoring 16 shows against The Big Picture", the session's Qloo calls still waiting past `QLOO_SLOW_MS`, the open question, rankings with the topic baseline, the insertion order draft, the inbox, and draft replies. The evidence log is fetched on demand, not synced.
- **Actions:** `@callable` methods on the agent: `importRoster` (pasted names, or a CSV with `name` and optional `downloads`, `status`, and `description` columns), `updateShow`, `searchComps`, `setCpm`, `startLaunch`, `answer`, `editInsertionOrder`, `approveInsertionOrder`, `loadInbox` (pasted pitches separated by lines of `---`, up to 50, where a pitch's leading `From:` and `Subject:` lines give its sender and subject, as a `.txt`'s do; the sample inbox only comes with the guest network), `confirmWork` (one of an ambiguous work's candidates), `startPitches` (a roster show matched in Qloo and up to five past guests, each with a public work), `editReply`, `approveReply`, `discardReply`, `getEvidence`, and `getRun` (what an earlier run ended with). The guide through the sample launch, and clearing the sample network, went with the demo, and their actions with them. `@callable` needs the `agents/vite` plugin ([configuration][cf-config]).
- **Call timeout:** `useAgent` rejects a call after 30 seconds, but one Qloo call can take about 64 seconds when Qloo hangs (three 20-second attempts plus backoff). An action that waits on Qloo returns early and reports progress in synced state instead. `importRoster` sets every show to `pending`, citing the call it waits on, and returns; each show fills in as its search settles. A second import is refused until the first has settled, and a show still pending when the agent restarts is marked failed as interrupted. `loadInbox` works the same way: each pitch fills in as Claude reads it and its work's search settles. `startPitches` starts a run and returns at once; the run looks up the past guests' works before its first model turn. `searchComps` sets the show's comp search to `pending` the same way, then fills in its results, or its failure with the reason; only the show's latest comp search lands.
- **Network and launch actions:** a network's agent adds `createLaunch` and `dismissChecklist` to the page's actions, and refuses the launch actions; a launch's agent refuses the roster and inbox actions ([Networks and launches](#networks-and-launches)). Calls with no connection, such as `rosterForLaunch`, `reportLaunch`, `kick`, `startLaunchAs`, `noteOwnKey`, `forgetMember`, and `destroy`, are RPC from the Worker or another agent, never `@callable`, so a page can't make them. Two members' pages on one agent see each other's changes through its synced state as they're made.
- **HTTP:** a launch's approved order exports at `GET /app/<id>/launches/<launchId>/insertion-orders/:id.csv`, for the network's members, and answers 409 for a draft. Settings, account, and launch deletion are JSON routes the page calls with `fetch` and the page's `Origin`.
- **The island:** `src/client/main.tsx` reads the root's `data-page` and loads that page's module with a dynamic `import()` before rendering it, so the build splits the island into a chunk per page (#209), and a page whose code fails to load says so ("This page didn't load (…). Reload to try again.") instead of staying blank. Page modules import only shared modules, never each other, so a page loads only its own code; `postal-mime` loads with the first email read. The server-rendered shell's `Island` writes `#root` and a `<link rel="modulepreload" fetchpriority="low">` for each chunk of the page's code, read from the client build's manifest that vite-ssr-components inlines into the Worker, so the page's code downloads beside `main.js` rather than after it runs (#218). A new page goes in both `main.tsx`'s `pages` and `shell.tsx`'s `pageModules`. When the island was split (#209, #218), the old dashboard, now the Launches page, loaded about 100 KB of gzipped script on the build and `/sign-in` about 78 KB, against 159 KB for every page before the split; mobile Lighthouse scored the old dashboard 98 and `/sign-in` 99 on `wrangler dev` of the build.

## Caching, caps, and replay

- **Cache:** Qloo responses are cached privately with no expiry, which the hackathon allows ([BRIEF](BRIEF.md#implications-for-our-entry)). The `global` gateway's cache is shared by every network without its own Qloo key, so a cache hit can show that another network looked up the same name; a network with its own key has a cache of its own. An answer is cached only once it reads as its method expects, and read again on a hit (#182). The sample network, its launch, and the sample inbox are warmed before submission.
- **Caps:** a daily cap on Qloo calls (`QLOO_DAILY_CALL_CAP`, default 1,000, counted in UTC days, retries included and cache hits not), plus the per-run limits and the daily model run limits under [Agent limits](#agent-limits), which count each signed-in network as a visitor of its own. A network's own gateway instance applies the same Qloo caps to its own calls. The default is a guess, because the Qloo quota is unknown ([CONTEXT](CONTEXT.md#unverified)). Model spend is bounded in code, by the daily model run limits, not by a spend limit on the Anthropic account (owner's decision, 2026-10-18, [#21](https://github.com/m1kuorg/qloo/issues/21)).
- **Replay:** the sample launch's completed run is stored server-side. When a cap or a model run limit is hit, or Qloo keeps failing, sample runs replay from storage with a visible "replayed" label, and runs on anyone's own data stop with a clear message. Only the guest network's sample launch, and an engine session in tests, replay or store the sample run: the guest network's agent notes which launch it planned as its sample launch, and only that launch's roster copy carries the sample marker, as the network then holds it, so the replay test runs on the copy before the run is admitted. Any other launch, such as one on a network that started from the sample roster, runs, or stops, like any other, the guest network's sample launches included: they carry no sample marker, so a guest's run of one of them is a model run on the guest budget.
  - **What's stored:** the latest completed run of the sample launch on the unchanged sample network, answered with the sample answers, whose every cited Qloo call was answered: its synced state, less the visitor's inbox, and the evidence records it cites. Unchanged means no figure edited, no show left out or mapped to a comp, no comps, and no answer the visitor typed, since any visitor's run can become what every judge sees; a comp search's query is dropped from the stored roster for the same reason. A topic baseline that lands after the run ended is added to the stored copy, not taken from the run's snapshot, where the programmer may have edited the order since; the gateway writes it only while the stored copy is still that run's, so a run stored meanwhile is kept. The latest replaces the last, so the stored run keeps up with what later code adds to a run.
  - **When it replays:** decided when the run starts, so a replay makes no Qloo or model call and isn't counted as a model run. It replays once a daily model run limit is reached for the visitor or for all visitors. Qloo can't be called once the day's cap is reached, or for five minutes after a request fails after its retries (any failure but a 400), unless a request succeeds since. Cache hits don't count either way.
  - **How:** the stored evidence is copied into the session's log under new call numbers, labelled replayed, and the stored state, renumbered to match, replaces the session's, roster included. A run that starts while Qloo can't be called, or past a model run limit, on anything but the unchanged sample launch, ends at once: stopped at the cap or the limit, or failed while Qloo fails.
- **Health check:** a daily cron at 12:00 UTC makes the health-check call past the cache, then checks from the cache alone, without calling Qloo, that the sample launch's ranking is cached: The Watch against the other 15 resolved shows with nothing settled, as a new session ranks it from the sample network's cached searches. Each check logs one `health_check` line, at error level naming the check when it fails. A session that settles Binge Mode or maps a miss before starting sends a different ranking, so the warm-up starts the sample launch before settling anything.

## Security, privacy, and safe use

- **Secrets:** `QLOO_API_KEY`, `ANTHROPIC_API_KEY`, `VISITOR_SALT`, and `QLOO_KEY_SECRET` are set with `wrangler secret put` on each Worker, and locally in `.dev.vars`, which [`apps/.gitignore`](/apps/.gitignore) already ignores ([secrets][cf-secrets]). Keys are never logged or sent to the client, a network's own Qloo key included, which is kept sealed and shown only by its last four characters.
- **Qloo data:** never committed, exported, or sent to the browser beyond what the UI shows. Evidence shows parameters, names, tags, and scores, not raw response bodies. Test fixtures are synthetic.
- **No personal data to Qloo:** gateway calls take entity IDs, show names, and work titles, never pitch text. A work title holding an email address, or the whole name of the guest or the pitch's sender, as Claude may read one into it, is never sent: the pitch is set aside as unreadable, and such a past guest's work is refused. A name is read with any honorific or suffix dropped ("Dr. Ada Quill, PhD"), "Quill, Ada" turned around, and a couple's shared surname given to each ("Jason and Travis Kelce"); a name of one word, such as a first name alone, isn't checked, so it never sets a title aside. Tests check every recorded Qloo request against the sample inbox's guest names and email addresses.
- **Pitch text goes to Anthropic** for extraction and drafting, uploaded emails included; the files themselves are never kept, and a pitch's sender and subject stay inside Crossfeed. The sample inbox is synthetic; a network that loads its own pitches does so under the privacy page's terms.
- **Safe-use wording:** fit describes listener overlap, never a probability about a person, and nothing infers politics, health, or eligibility ([kit safe use][kit-safe]).
- **Spend:** trying Crossfeed needs no passkey, as a guest, so the daily model run limits and the Qloo cap bound what guests can spend, all of them on one guest budget; a signed-in network counts as a visitor of its own, and the limits on sign-ups, guest sign-ins, networks, and launches stop the beta being used to multiply them ([limits](#limits-on-sign-ups-networks-and-launches)).
- **Networks kept apart:** every page, agent route, and API route checks the member's membership, or the API key's network, before it reads anything, and answers a network the caller can't reach with the same 404 as one that doesn't exist. Agents of different kinds are different classes, so a test session's cookie could never name a network's or a launch's instance. Sessions, invites, recovery codes, and API keys are stored only as hashes ([members and sign-in](#members-and-sign-in)).
- **Visitor addresses:** never stored by Crossfeed or written to its own logs. The daily limits key a visitor by a salted hash of their address, kept only for the connection and, hashed again with the day, until the day ends ([agent limits](#agent-limits)); the per-minute limit on sign-in requests counts under the salted hash for a minute. Cloudflare, which runs the Worker, records each request in its own logs, as the privacy page says.
- **Trademarks:** the sample network uses public show names, with a notice that Crossfeed isn't affiliated with The Ringer: in the landing page's fine print under "Open the sample network", and in the roster the API and the MCP server read. The app's pages label each sample figure instead.

## Deployment and configuration

One Worker, `crossfeed`, in the `m1kuorg` Cloudflare account, serves production at <https://crossfeed.m1kuorg.workers.dev>; the `preview` environment deploys a separate Worker, `crossfeed-preview`, at <https://crossfeed-preview.m1kuorg.workers.dev>, with its own D1 database, Durable Objects, rate limit namespaces, and secrets, for checking the product before production. `apps/wrangler.jsonc` holds both. Wrangler doesn't inherit `vars`, secrets, or bindings into an environment, so each is repeated under `env.preview`, which differs only in `ACCOUNTS`, `SEARCH_INDEXING`, which it leaves out, the host in `RP_ID` and `APP_ORIGINS`, the D1 database, and the rate limits' namespace IDs. After changing it, `bun run cf-typegen` regenerates `Env` in `worker-configuration.d.ts`. The [apps README](/apps/README.md#deploy) is the how-to.

### Variables and secrets

- **Qloo gateway:** `QLOO_BASE_URL` (`https://hackathon.api.qloo.com`), `QLOO_DAILY_CALL_CAP` (1000), `QLOO_TIMEOUT_MS` (20000), `QLOO_RETRY_DELAYS_MS` (`1000,3000`, one delay per retry), `QLOO_MIN_INTERVAL_MS` (400, the pacing), and `QLOO_SLOW_MS` (8000, the worst case per call), when the UI calls a Qloo call slow and names it. The session times only its 3 oldest waiting calls, as many as the gateway sends at once, so a call queued behind the session's own isn't called slow.
- **Model:** `ANTHROPIC_BASE_URL` (`https://api.anthropic.com`).
- **Daily limits** ([agent limits](#agent-limits)): `RUN_VISITOR_DAILY_CAP` (10) and `RUN_DAILY_CAP` (200) model runs, `FREE_START_DAILY_CAP` (100) free starts, and `QLOO_VISITOR_DAILY_CALL_CAP` (2000) Qloo calls, per visitor or network.
- **Switches:** `ACCOUNTS` (`on` in production since [#223](https://github.com/m1kuorg/qloo/issues/223), on the preview, and in tests) turns accounts and every route behind them on, every way in included, since trying Crossfeed is signing in as a guest; `GUEST_PITCHES` (`on` since #57's live check) serves the inbox pages and the API's inbox and pitch run routes, links them, allows the inbox actions, and lists the MCP server's pitch tools; `SAMPLE_NETWORK` (`on`; tests turn it off) loads the sample network into the guest network, and opens a new engine session on it; `SEARCH_INDEXING` (`on` in production alone; tests turn it off) lets search engines index the public pages ([Crawlers](#crawlers)); `TEST_SESSIONS`, set only in `vitest.config.ts`, opens the engine's per-session route to tests.
- **Sign-in and its limits:** `RP_ID` (the passkey relying party, each environment's host) and `APP_ORIGINS` (the comma-separated origins a member's browser may send from), and the limits `SIGNUP_VISITOR_DAILY_CAP` (5), `NETWORKS_PER_MEMBER` (3), `LAUNCHES_PER_NETWORK` (100), `INVITES_PER_NETWORK` (20), `API_KEYS_PER_NETWORK` (10), and `INVITED_SIGNUP_DAILY_CAP` (20) ([limits](#limits-on-sign-ups-networks-and-launches)), `GUEST_SIGNINS_PER_MINUTE` (30) and `GUEST_SIGNINS_PER_DAY` (1,000) ([request guards](#request-guards)), and `SAMPLE_RESETS_PER_DAY` (20) ([demo data](#demo-data)).
- **Secrets**, required in both environments (`secrets.required`, so a deploy fails without them): `QLOO_API_KEY`, `ANTHROPIC_API_KEY`, `VISITOR_SALT` (salts the visitor hash; changing it restarts every visitor's count), and `QLOO_KEY_SECRET` (seals each network's own Qloo key; changing it makes every saved key unreadable, so each owner adds theirs again).

A limit that isn't a number refuses everything it limits.

### Bindings

- **Durable Objects:** `CrossfeedAgent`, `QlooGateway`, `NetworkAgent`, and `LaunchAgent`, from migrations `v1` (`CrossfeedAgent`, `QlooGateway`) and `v2` (`NetworkAgent`, `LaunchAgent`), all `new_sqlite_classes`. Removing a class would need a `deleted_classes` migration.
- **D1:** `DB`, the database `crossfeed` (`crossfeed-preview` on the preview), with `migrations_dir` `migrations`.
- **Rate limits:** `API_LIMITER` (120 a minute), `AUTH_LIMITER` (20 a minute), and `CREATE_LIMITER` (30 a minute), each environment with its own namespace IDs.
- **Crons:** `0 0-11,13-23 * * *`, every hour but 12:00 UTC: the directory's purge and the wipes' retry; and `0 12 * * *`, which runs the purge too, then the daily health check, the guest network's clearing, and the clearing of what guests made beyond it, leaving the wipes they note to the next hour's retry ([cron triggers][cf-cron]). Two schedules that fire in one minute run as two invocations, so the hourly one skips 12:00. The handler tells them apart by `controller.cron`, and runs the daily work for any schedule but the hourly one. The preview inherits both. Each run stays within the Free plan's subrequest limits, which count D1 queries (a batch is one) and Durable Object calls, an agent's start included, apart ([#275](https://github.com/m1kuorg/qloo/issues/275), [#336](https://github.com/m1kuorg/qloo/issues/336)): D1 queries within 50, the most [D1's limits][cf-d1-limits] give a Free plan invocation, though a probe on this account ran 1,000; and D1 queries and Durable Object calls together within the 1,000 subrequests to Cloudflare services the [Workers limits][cf-limits] give it beside 50 external ones, which the probe showed Durable Object calls count toward instead of the 50. The hourly run makes at most 49 D1 queries and 92 Durable Object calls, 184 if every agent's start takes its three tries ([deleting](#deleting-launches-networks-and-accounts)), which `test/wipe-retry.test.ts` counts with a full run of launch wipes that each fail as they're crossed off; the 12:00 run makes 40 at most, the two together, however many launches the guest network lists: the purge 1, the health check 22, the guest network's clearing 8 (its agent's start and letting go, one batch, and two wipes, its agent's and its gateway instance's, each with its crossing off), the temporary guest members' removal 1, and the guest member's clearing 8 (its list of networks, a start and a letting go, or a kick, for each of its three at most, and one batch). `test/sample-launches.test.tsx` counts them, with the sample launches, guests' own launches, the guest member's three networks, and a full queue of wipes. CPU time, not subrequests, is what a larger batch of wipes would meet first: Free gives a Cron Trigger 10 ms ([Workers limits][cf-limits]), which Cloudflare enforced loosely on an hourly run of 7 wipes, which used 23 ms in production and 41 ms on the preview and ended `ok` ([#336](https://github.com/m1kuorg/qloo/issues/336)).
- **Build:** `vite.config.ts` runs the `agents/vite` plugin (which `@callable` needs, [configuration][cf-config]), React, the Cloudflare Vite plugin, and vite-ssr-components, which inlines the client build's manifest into the Worker for the shell's preloads. `"compatibility_flags": ["nodejs_compat"]` is set, which the Agents SDK requires.
- **Dependencies:** `agents` (pinned, since it ships minor releases every few days), `@anthropic-ai/sdk`, `hono`, `@hono/zod-openapi` and `zod`, `@modelcontextprotocol/server` (pinned to match `agents`' peer), `@simplewebauthn/server` and `@simplewebauthn/browser`, `postal-mime`, `react`, and `react-dom`; for tests, `vitest`, `@cloudflare/vitest-plugin`, `msw`, and `@msw/cloudflare`.
- **Plan:** the account stays on its current plan ([why this stack](#why-this-stack)).

### Deploying production and the preview

Deploys are manual, one at a time, from an up-to-date `main` in a detached checkout, and never from a feature branch:

- **Production:** `bun run deploy` in `apps/` builds, applies the directory's new migrations to `crossfeed` (`wrangler d1 migrations apply DB --remote`), then runs `wrangler deploy`.
- **Sample launches:** each environment's D1 holds its own copy of the guest network's sample launches, loaded by hand with `wrangler d1 execute DB --remote [--env preview] --file`, from the SQL `scripts/capture-sample-launches.ts` writes outside the repo, and loaded again whenever they're captured again, as after a change to the run state's shape. A new field needs no capture when it's optional and the seed sets it, as with the CPM's sample label, which runs captured before it lack: the seed sets it on each run captured at the sample CPM ([#333](https://github.com/m1kuorg/qloo/issues/333)). A deploy doesn't load them; an environment without them opens the guest network with The Watch alone ([apps README](/apps/README.md#sample-launches)).
- **Preview:** `bun run deploy:preview` builds with `CLOUDFLARE_ENV=preview`, applies migrations to `crossfeed-preview`, then runs `wrangler deploy --env preview`. The Vite plugin picks the environment when it builds, so a plain `bun run build` followed by `wrangler deploy --env preview` would deploy production's config; only the script is safe. Wrangler can't set secrets on a Worker that doesn't exist yet, so a first preview deploy takes them from a file, as the [apps README](/apps/README.md#deploy-the-preview) says.
- **Migrations** are applied before the Worker that needs them deploys; an applied migration is never edited, and a new one is added instead.
- **Order of release:** merged work is checked on the preview first, with `ACCOUNTS` on; production turns `ACCOUNTS` on only once the whole product passes there ([PRD release plan](PRD.md#release-plan)).

## Observability

- One structured log line per Qloo call with the endpoint, status, latency, retries, and cache hit (`"event":"qloo_call"`), and one per model call with the run, turn, stop reason, input and output tokens, cache reads and writes, and latency (`"event":"model_call"`), in Workers Logs.
- One summary line per run (`"event":"run_summary"`): turns, Qloo calls, cache hits, wall time, and outcome (completed, paused on a question, stopped at a limit, or failed). It's written when the run ends; a run paused on a question writes it with outcome `paused`. A run's topic baseline logs `topic_baseline`, with whether it came from the cache, and a stored sample run `sample_run`.
- Every hour the cron logs `directory_purged` with the sessions, challenges, invites, `guestSignIns`, and `guestInvitedSignUps` rows it deleted, and `wipes_retried` with how many wipes it made, kept, and failed; at 12:00 UTC also one `health_check` line per check (at error level, naming the check, when it fails), `guest_network_reset` with how many launches the guest network's clearing noted for the retry and how many wipes failed (logged too as an owner resets the sample data), `guests_removed` with the temporary guest members and networks it removed, and `guest_member_cleared` with the networks the guest member's clearing deleted and left; a wipe or forget that fails as it's made logs `wipe_failed`.
- The product's agents log what they couldn't tell each other, each then retried or caught up later: `launch_report` (a launch's row the network didn't take), `roster_notice` (a launch not told the roster changed), and `own_key_notice`, `own_key_restore`, and `own_key_lookup` (a network's own Qloo key: a launch not told of it, a failed wipe's rollback, and an old network agent's one-time lookup).
- Elsewhere: `guest_sign_in` for each guest sign-in, `qloo_key_test` with the status of a network's key test (never the key), `passkey_refused` with the ceremony and why, `api_error` and `mcp_error` for an error with no refusal code (answered as a 500, or a tool error, saying to try again), `request_error` with the method, path and Ray ID (`cf-ray`) for an error any other route throws (answered with the error page or a plain 500), and `error_page_failed` when the error page fails too, and `preload_missing` for an island page whose chunk the client manifest lacks.

## Testing

Per the [PRD](PRD.md#testing-decisions), tests drive the public interface with Qloo and Anthropic replaced at the network boundary. The [apps README](/apps/README.md#test) says how to use each helper.

- **Seam:** `QLOO_BASE_URL` and `ANTHROPIC_BASE_URL` are configuration, and the Anthropic SDK takes a `baseURL`. Tests point both at fake hosts served by an in-process fake that serves synthetic Qloo responses, replays scripted model turns, and records every request. The Qloo fakes also serve both hosts a network's own key can be for, and can refuse keys they don't know, as Qloo does.
- **Runner:** Vitest with Cloudflare's Workers integration, `@cloudflare/vitest-plugin` (the renamed `@cloudflare/vitest-pool-workers`). The Worker, its four Durable Object classes, D1, and the rate limiters run in the same isolate as the tests ([test APIs][cf-test-apis]). Tests run with `ACCOUNTS` on, `SAMPLE_NETWORK` and `SEARCH_INDEXING` off, `RP_ID` `crossfeed.test`, and `APP_ORIGINS` `https://crossfeed.test`.
- **How the fake is reached:** settled on 2026-10-17. The fake runs inside the Workers runtime as [`@msw/cloudflare`][cf-msw] handlers, Cloudflare's documented way to mock outbound requests with the plugin. It patches `fetch` in the tests' isolate, so it sees every call the gateway makes, and each test file gets its own fake and request log. A request no handler serves fails the test. Two alternatives lost: a Node HTTP server started in Vitest's `globalSetup` and passed by port, whose one shared memory would need every request keyed to a test, though a Qloo request carries no session or test ID; and an auxiliary Worker, which must be prebuilt JavaScript and can't share the tests' fixtures. The Anthropic SDK captures `fetch` when its client is built, so build it with `fetch: (...args) => fetch(...args)` to let the patched `fetch` reach it.
- **D1 for real:** `vitest.config.ts` reads `migrations/` with `readD1Migrations` into a test-only binding, and `test/session.ts` applies them with `applyD1Migrations` before each test, since the per-test storage reset wipes D1 with the Durable Objects. Only storage tests read D1 directly; every other test reaches the directory through the Worker's routes.
- **Passkeys for real:** `test/authenticator.ts` is a software authenticator that makes ES256 passkeys with "none" attestation and signs challenges as a browser's platform authenticator does, user present and verified, at counter 0, so every ceremony runs the real verification.
- **Through the interface:** `openSession` is a session of the engine, on a cookie it makes, connected to the agent as the UI is. `openMember` is a member signed up through the real ceremony, with `fetch` (their cookie, and the app's `Origin` on writes), `connect` (a network's or a launch's agent), and `invite`; `openGuest` is someone signed in as a guest, with the same `fetch` and `connect`. `api(secret)` is a program with an API key, the SDK's tests drive the real Worker through the SDK's injected `fetch`, and `assistant(secret)` is an MCP client. View tests render the island's pages with `renderToStaticMarkup` from the data attributes the server gave them, and `test/csp.test.ts` crawls every page for what the policy forbids and for each page's preloads.
- **What's covered** beyond the engine's suite: sign-up, sign-in, recovery, step-up, sign-out, refused or replayed challenges, and the caps; guest sign-in, its session's day, and its limit a minute; membership isolation across pages, agents, and the API; invites; two members' edits seen live; two launches at once; a launch's roster copy and evidence; uploads and each refusal; API keys and approval refused over RPC; the SDK's methods and waits; the MCP server's tools; deleting launches, networks, and accounts; the body limits and the Origin checks.
- **Live check:** each feature is done only after it runs in the app against the real Qloo and Anthropic APIs, checked by hand: locally, then on the preview for the signed-in product, and on production for the landing page and the guest network.

## Demo data

- **Sample network:** The Ringer, from public show names. On 2026-10-17, `/search` resolved 16 of 19 Ringer shows, against 11 of 15 for Exactly Right and 8 of 16 for Pushkin. Of The Ringer's 19, The Zach Lowe Show and The Press Box missed, and Binge Mode was ambiguous with a "Binge Mode: Marvel" feed. The misses and the ambiguous match demonstrate the mapping and disambiguation questions.
- **Sample inputs:** [`apps/src/sample-network.json`](/apps/src/sample-network.json) holds the 19 shows with downloads per episode, status, and a one-line description paraphrased from each show's public description, plus a $20 CPM and the sample launch. These are ours, chosen at build time, flagged `sample` in the file, labelled as arbitrary sample figures the visitor can edit, and not The Ringer's.
- **Choosing the launch:** on 2026-10-17, [`scripts/choose-demo-launch.ts`](/scripts/choose-demo-launch.ts) ran each of the 16 resolved shows as a leave-one-out launch against the other 15, plus three-comp film, music, and football launches against all 16, and compared Qloo fit with three samples of a topic-only Haiku ranking made from show names and descriptions. Its output stays out of the repo. Across launches, shows that climbed three or more places shared mostly host and style tags with the launch, such as Insightful and Conversational, and topical tags were rare. The three-comp launches gave no move into the top five: the film comps (Blank Check, Filmspotting, and You Must Remember This) and the music comps moved no show three places, because their fit order nearly matched topic order.
- **Opening on the sample network:** an engine session's first start opens it on the sample network when the `SAMPLE_NETWORK` Worker variable is `on`, as tests that turn it on do; the retired demo opened every visitor's session this way. The 19 shows are looked up as an import is, through the gateway, so they resolve from the shared cache once any network has looked them up. Nothing is settled: Binge Mode stays ambiguous and the misses stay missed. State flags which sample figures each show still holds and whether the CPM is still the sample's, so each keeps its sample label until someone changes it. Importing a roster leaves it: the roster is replaced, and the sample CPM goes too, because a real network's CPM has no default.
- **Loading the guest network:** with `SAMPLE_NETWORK` on, the guest network's agent loads the sample network on its first start, each day after the daily cron clears it (`loadSample` in `src/network-agent.ts`): the 19 shows with their sample labels, looked up as the demo's are, with their calls reserved on the guest budget; the sample CPM, labelled sample until a guest changes it, which an import keeps, label and all, whatever it imports; and the sample launch, The Watch, planned with the sample, which calls neither Qloo nor Claude. Then it lists the sample launches beside it (`loadSampleLaunches`), below. The CPM and the plan call nothing, so they land first, whatever the lookups do: refused lookups leave the roster empty beside the labelled sample CPM and The Watch, planned, until a later start looks it up. An empty roster isn't the unchanged sample network, so The Watch on it neither replays nor stores the sample run. Once a guest's import leaves no show holding a sample figure, the roster is the guest's own: the roster page carries no "sample" badge, and the roster the API and the MCP server read no notice, though the dashboard and settings still label the CPM the sample's. Once nothing of the sample is left, no show holding a sample figure and the CPM an owner's, whether an import, a CPM change or a show edit leaves it so, the network no longer holds the sample: the dashboard and settings lose their "sample" badge, The Watch's next run copies no sample, and only the daily clearing or a reset of the sample data loads it again. While refused lookups leave the roster empty, an owner's CPM keeps the sample, and a later start loads the sample roster under it. The agent notes in its storage once a start finds the roster settled and the launch planned, or the sample replaced by a guest's import and edits, which leave no sample figure; until then, each start tries again what didn't land: an empty roster, the lookups that failed, and the plan. A lookup a deploy interrupted then says "The lookup was interrupted. Crossfeed tries it again later.", and the roster page's line of failed shows says Crossfeed tries them again later, rather than to import the roster again. With `GUEST_PITCHES` on too, it loads the sample inbox beside it (`loadSampleInbox`): The Big Picture and its three past guests, and the 40 pitches already read from each one's `expected` guest and work, so no model is called and no model run counted. The 36 works are looked up as the roster's shows are, their calls reserved on the guest budget and numbered in inbox order, each keeping its evidence, and the 4 pitches with no work are set aside. Its own note in storage is kept once a start finds every lookup settled, a pitch run started on it, whose lists and replies name its pitches as they were then, or a guest's own pitches, which it never replaces or looks up again; until then, each start tries again an inbox the guest budget refused and the lookups Qloo failed or a deploy interrupted, which say "The lookup was interrupted. Crossfeed tries it again later." rather than to load the inbox again. A program loading pitches over it through the API sends `replace=true`, as over any inbox with pitches.
- **Sample launches** ([ADR 0007](/docs/adr/0007-the-sample-network-is-the-guest-networks-data.md), [#289](https://github.com/m1kuorg/qloo/issues/289)): beside The Watch, not run yet, the guest network lists a launch in each status a guest can't reach in a moment: an insertion order approved, one drafted, a run ranked with no order, and a run stopped at once. Each is one real run of a launch from the sample roster's world, released or from comps, captured on a development guest network as the [apps README](/apps/README.md#sample-launches) says: three run to their end, one approved by the guest member, one ranked with a dollar budget no slot fits, so its closing says honestly why there's no order, and one stopped at once by the guest budget's day of model runs, its text reworded by the capture as the sample's, with the UTC day it was captured. Running and waiting runs aren't seeded: a running run fails as its agent restarts, and a seeded question would let guests resume a Claude conversation outside the model-run count. `scripts/capture-sample-launches.ts` reads each launch through its page's agent connection, trims it as the stored sample run is (`keptRun` in `src/sample-launches.ts`, `capturedRunOf` in `apps/test/capture.ts`, which the test shares), its one run's state less the guest pitch flow's fields and comp searches, with every record it cites, and writes the SQL for `sample_launches`, the launch's JSON in ASCII chunks of 40,000 characters, outside the repo, since it's Qloo data. On the guest network's start, after the sample, `loadSampleLaunches` reads the table in one D1 query and seeds each launch on its own agent (`LaunchAgent.seed`), listing it as a planned launch is, under the cap, with an ID kept in its storage from the first try, so a try again lists it once. Until every row is noted as listed, each start tries again the ones that failed or the cap refused; one a guest deletes stays deleted. The daily clearing takes them off the list with the rest, their agents taking no more work until the hourly retry wipes them, and the next start seeds them again, with new IDs. With no rows, as in an environment not loaded yet and in tests that load none, the guest network has The Watch alone, and each start reads the table again, so rows loaded since are listed as it next starts. Its load logs `sample_launches_load` for a launch it couldn't list, or a table it couldn't read.
- **Resetting the sample data** ([#283](https://github.com/m1kuorg/qloo/issues/283)): the guest network's settings, and no other network's, have a Sample data module, whose owners, every guest among them, reset the guest network to the sample data on demand after the app's confirm (`POST /app/guest-network/settings/sample-data/reset`). It's the daily clearing (`resetGuestNetwork`) with its own reason: the guest network's open pages close with 4410, "The guest network was reset to the sample data.", whoever reset it, a guest or a member who owns it, and the launches it leaves to the hourly retry are noted with that reason, which their pages are told as they close. The owner who reset goes to the dashboard, whose agent's start loads the sample again, its lookups reserved on the guest budget as each day's are: 19 shows and, with `GUEST_PITCHES` on, 36 works, 55 in all (`sampleLookups` in `src/network-agent.ts`). Networks guests created, and the guest network's API keys, invite links, and members, wait for the daily clearing. Its limits come first below, each for everyone at once, from any guest or address, and each refusing with a 429 that says why and a `Retry-After`, before anything closes; when more than one holds, the refusal names the one that holds longest, so its `Retry-After` is never too soon. Then its other answers:
  - **The guest budget:** while the guest network's Qloo calls left today, read from the global gateway under its limit key (`network:guest-network`), are fewer than the sample's next load reserves, it's refused until 00:00 UTC, since the load would be refused and the guest network open without the sample. It reads the global gateway even while a guest's Qloo key is on the guest network, where `getUsage` would read that key's instance instead, because the reset wipes the key, so the load goes through the global gateway. It's read before the reset is taken, and refusing takes nothing.
  - **The rest, in one statement:** the route takes the reset in the statement that notes it, an upsert of the one `sample_resets` row, with when the last was taken and how many were that UTC day (migration 0012, `takeSampleReset` in `src/directory.ts`), only while each of the three below allows it, so D1 counts every request exactly, and two at once, the last of the day's included, leave one refused. In the order a refusal names them:
    - **`SAMPLE_RESETS_PER_DAY` (20) a UTC day:** past it, until 00:00 UTC.
    - **The hourly retry:** while more than 23 of the guest network's launch wipes wait in `wipes` (`GUEST_LAUNCH_WIPES` in `src/wipe.ts`), as many as one run of the [cron's retry](#deleting-launches-networks-and-accounts) wipes, until that retry next runs, the next hour's start but 13:00 UTC for 12:00's (`nextRetry`), so resets can't pile up wipes faster than the retry clears them. Each reset leaves one per launch the guest network listed: The Watch, the four [sample launches](/apps/README.md#sample-launches) where they're loaded, and any a guest planned, so with nothing else planned, the sixth reset before the retry next runs is refused here.
    - **One a minute:** inside a minute of the last, the seconds to wait.
  - **Who and where:** any other network answers 404, a member of the guest network who isn't an owner 403, and a write from another origin 403.
  - **A wipe that fails** is logged and left for the hourly retry, as the clearing leaves it, and the route answers 202, `{ pending: true }`; the owner who reset lands on the dashboard all the same, at `?reset=pending`, which says under its header that the reset may take a moment to finish, as only the guest network's does.
  - **Its cost:** the clearing's 8 subrequests, however many launches the guest network lists, the route's own few D1 queries, and the one call that reads the guest budget. The settings page that resets keeps what it shows while the reset closes its own connection (`leaving` in `NetworkGate`), so it goes straight to the dashboard.
- **Sample answers:** a slot budget of 20 slots and no run exclusions, in `sample-network.json` and in synced state while the roster is the sample network's. The replay and the warm-up reuse them. They are suggested, never filled in: the programmer still answers.
- **Sample launch:** The Watch, a released show, ranked against the other 15 resolved roster shows. When the launch is a roster show, the fit ranking and topic baseline leave it out of its own candidates. The Ryen Russillo Podcast moves most among the finalists, up six places from topic rank 11 to fit rank 5, but shares only host and style tags with The Watch. The demo leads with The Bill Simmons Podcast, up five or six places from topic rank 9 or 10 to fit rank 4, because its shared tags explain the move: Pop Culture, plus Conversational and Insightful. Meanwhile the topic ranking's two music shows, Every Single Album and 60 Songs That Explain the '90s, fall from topic ranks 3 to 7 to fit ranks 14 and 13. Below the finalists, The Ringer NFL Show climbs five to seven places, to fit rank 7. A second run with three fresh topic samples gave the same ranks within one place.
- **Mapped shows:** a show Qloo missed, mapped to a comp, is scored by the comp's listeners, and ranks sensibly beside resolved shows when the comp shares the show's audience. On 2026-10-17, on the deployed Worker, The Watch's ranking with The Zach Lowe Show mapped to The Lowe Post and The Press Box mapped to Sports Media with Richard Deitsch kept the 15 resolved shows in the order they took without the two, with the same raw affinities for the 13 compared. The Lowe Post, Zach Lowe's earlier show, came 8th of 17, among the network's sports shows. Sports Media with Richard Deitsch, from outside the network, came last, so a comp's own audience sets the mapped show's place, which is why the chart says "Mapped to" beside it.
- **Sample show for pitches:** The Big Picture, with three past guests from its public episode feed: Paul Thomas Anderson for One Battle After Another (episode of 2025-09-26), Rian Johnson for Wake Up Dead Man: A Knives Out Mystery (2025-12-16), and Josh Safdie for Marty Supreme (2025-12-24). All three films resolve. They're too recent to score as candidates, but they still work as anchors: each book, TV, and podcast result's explainability lists all four anchors, while film results list only the show and Wake Up Dead Man.
- **Sample inbox:** [`apps/src/sample-inbox.json`](/apps/src/sample-inbox.json), flagged `sample`, holds the show, its past guests, and 40 synthetic pitches from fictional publicists at `example.com` addresses: 15 books, 11 films, 6 TV shows, 4 podcasts, and 4 from fictional people with no public work. Most works came out before May 2025 so that they score; 10 of the 36 miss in search or go unscored, to show those paths.
