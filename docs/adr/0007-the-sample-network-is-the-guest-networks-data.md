# The sample network is the guest network's data

The sample network stops being a demo of its own and becomes data: The Ringer's public show names with their labelled sample figures, the sample CPM, the sample launch, The Watch, and the sample inbox are loaded into the guest network when its agent first starts, each day after the daily cron clears it. Anyone who wants to try Crossfeed signs in as a guest, in one click, and lands in the guest network with the sample already there. The standalone demo's pages go; `/demo` sends people to guest sign-in, so links to it keep working. No other network starts from the sample: a member's network starts from its own roster and pitches.

The guest network's sample launch keeps the demo's safety net ([ADR 0004](/docs/adr/0004-qloo-key-per-network.md)): while its roster and launch are still the sample's, a run of it that Qloo or a daily cap refuses replays the stored sample run, as the demo did. Since every guest owns the one guest network, any guest's change to its roster or launch turns that off for everyone until the daily clearing; the sample isn't loaded into a network of each guest's own, which would have kept the replay for each, because the guest network is the one shared place guests try the product together.

We chose this over keeping the demo beside guest sign-in because two ways to try the product split the people trying it between a session no one else sees and the shared network everyone does, and the demo couldn't do what the product does: invite, keep a launch, or approve for a team.

Amended by [#289](https://github.com/m1kuorg/qloo/issues/289): beside The Watch, not run yet, the guest network also opens with sample launches, one in each status a guest can't reach in a moment: an insertion order approved, one drafted, a run ranked with no order, and a run stopped at once. Each is one real run, captured once in development and trimmed as the stored sample run is, then seeded into its launch's agent as the guest network starts, with no call to Qloo or Claude, and listed as a planned launch is; the daily clearing takes them with the rest, and the next start seeds them again. Their data is Qloo data, which may not sit in a public repository, so it lives only in each environment's D1, loaded there by hand from what the capture script writes outside the repo, never in the repo itself; an environment without it opens with The Watch alone. Only The Watch, the sample launch, replays: the sample launches carry no sample, so a guest's run of one of them counts on the guest budget like any other. No running or waiting run is seeded: a running run fails as its agent restarts, and a seeded question would let guests resume a Claude conversation outside the model-run count. We chose seeded runs over running the launches each day, which would spend the guest budget on runs no guest asked for, and over the replay, which has the one run of The Watch.

## Consequences

- `CrossfeedAgent` stays as the engine the network and launch agents extend, and its per-session route stays for its own tests, answering only while a test-only variable is on, so production keeps no anonymous per-visitor agents outside the guest budget.
- Trying Crossfeed needs accounts on; with `ACCOUNTS` off, the public pages offer no way in.
- All guests share 10 model runs a day; past that, only the unchanged sample launch runs, by replaying.
- The sample inbox is pre-loaded too, its pitches already read from their answer key, so loading it calls no model and counts no model run: only its 36 works' searches, reserved on the guest budget. No inbox offers to load it, and the engine refuses to.
- The run each of the sample launches is seeded with says it's the sample data's, with the day it was captured, and so does each record it cites; its approved order says it was approved in the sample data, not by anyone in the network ([ADR 0002](/docs/adr/0002-approval-stays-in-the-app.md)).
- A change to the run state's shape means capturing the sample launches again and loading them into each environment, since a deploy doesn't, unless the seed fills in what's new, as it does the CPM's sample label ([#333](https://github.com/m1kuorg/qloo/issues/333)).
- The daily clearing notes the guest network's launches' wipes in one batch and leaves their agents to the hourly retry, so its run stays within the Free plan's subrequests however many launches the guest network lists. Until the retry wipes one, its agent takes no more work: it checks that the network still lists it before a start, an answer, an order's edit or approval, and each model turn, and once it doesn't, it stops its run and closes its pages saying the guest network was cleared.
