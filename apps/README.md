# Crossfeed app

The Crossfeed Worker: a Hono app with a route module per surface (the landing page and docs, accounts, the app, the REST API, and the MCP server) and a React island, `CrossfeedAgent`, the engine the other agents extend, a `NetworkAgent` per network and a `LaunchAgent` per launch, a global `QlooGateway` (and one per network that brings its own Qloo key), and the D1 directory of members and networks, on Cloudflare Workers. It's deployed at <https://crossfeed.m1kuorg.workers.dev>, and its preview, with accounts on, at <https://crossfeed-preview.m1kuorg.workers.dev>. This is the how-to every ticket follows; [TRD.md](/docs/TRD.md) holds the design.

## Set up

Run these in `apps/`, with `QLOO_API_KEY` and `ANTHROPIC_API_KEY` in your environment:

```sh
bun install
printf 'QLOO_API_KEY=%s\nANTHROPIC_API_KEY=%s\nVISITOR_SALT=%s\nQLOO_KEY_SECRET=%s\nGUEST_PITCHES=on\nRP_ID=localhost\nAPP_ORIGINS=http://localhost:5128\n' "$QLOO_API_KEY" "$ANTHROPIC_API_KEY" "$(openssl rand -hex 16)" "$(openssl rand -base64 32)" > .dev.vars
bunx wrangler d1 migrations apply DB --local
```

`.dev.vars` is git-ignored. Never commit it, a key, or a Qloo response. `VISITOR_SALT` salts the hash that keys a visitor's model run count; any random value works locally. `QLOO_KEY_SECRET` encrypts each network's own Qloo key in its gateway instance (ADR 0004); any random value works locally too, but a key saved under one value can't be read under another, so changing it means each owner adds their network's key again. `GUEST_PITCHES=on` shows the guest pitch flow, as `wrangler.jsonc` does in production since #57; `off` hides it. Tests run with it off, and a test of the flow sets `env.GUEST_PITCHES = 'on'` itself. `ACCOUNTS` is `on` in `wrangler.jsonc` since #223; `off` hides accounts and every way in, such as "Open the sample network", which signs in as a guest, in one switch. Add `ACCOUNTS=on` to `.dev.vars` to work on them locally. The landing page offers "Create your network" and "Sign in" only while it's on. Tests run with it on, and a test without accounts sets `env.ACCOUNTS = 'off'` itself. `RP_ID` is the passkey relying party's ID and `APP_ORIGINS` the comma-separated origins a member's browser may send from. `wrangler.jsonc` sets them to each environment's host, so locally they're `localhost` and the dev server's origin: use the port you run it on.

A member's session cookie is `__Host-crossfeed_member`, which is always `Secure`. Chrome keeps a `Secure` cookie from `http://localhost`, as it treats localhost as a secure origin, so signing in works on the dev server over plain HTTP, checked in Chrome 155. Other browsers weren't checked, so check accounts locally in Chrome.

`bunx wrangler d1 migrations apply DB --local` creates the D1 directory's tables, from `migrations/`, in the dev server's local copy of the database under `.wrangler/state`. Run it again after pulling a new migration.

After changing `wrangler.jsonc`, run `bun run cf-typegen` to regenerate `Env` in `worker-configuration.d.ts`.

The rate limits (`ratelimits` in `wrangler.jsonc`: `API_LIMITER`, 120 requests a minute per API key, `AUTH_LIMITER`, 20 a minute per visitor on the auth routes that write before anyone signs in, and `CREATE_LIMITER`, 30 API keys and invite links together a minute per member) run in the dev server and the tests too, simulated by Miniflare with the same limits and fixed one-minute windows. A request with no `CF-Connecting-IP`, as in the tests unless one sends it, isn't counted per visitor; `CREATE_LIMITER` counts by member ID, so it always counts, and every guest, the one guest member, shares its count. Revoking a key or a link is never limited. Guest sign-ins (`/auth/guest`) are under none of them: `GUEST_SIGNINS_PER_MINUTE` (30) a minute and `GUEST_SIGNINS_PER_DAY` (1,000) a UTC day for everyone together are counted in the D1 directory's log of guest sign-ins as each guest's session is written, so they hold in the dev server and the tests exactly as deployed. So are resets of the guest network's sample data, one a minute and `SAMPLE_RESETS_PER_DAY` (20) a UTC day for everyone, in the `sample_resets` row each is taken in.

## Run locally

```sh
bun run dev -- --port 5128 --strictPort
```

Ticket `#n` uses port `5100 + n`, so parallel worktrees don't collide. The dev server calls the real Qloo API with the key in `.dev.vars`. Stop the server when you're done.

## Test

```sh
bun run test
```

Tests run in the Workers runtime through `@cloudflare/vitest-plugin`, configured in `vitest.config.ts`. The Worker, its Durable Objects, and D1 run in the tests' isolate. Tests drive the public interface only: the Worker's HTTP routes, the agents' client protocol, the REST API, the SDK, and the MCP endpoint, asserting on synced state and responses. On a loaded machine, run them with `bunx vitest run --maxWorkers=2`, and a single file while iterating.

### The fake HTTP seam

Outbound HTTP is the one seam. `test/fake.ts` holds the fakes, which [`@msw/cloudflare`][msw-cf] serves by intercepting `fetch` inside the runtime. `QLOO_BASE_URL` points at `https://qloo.test` and `ANTHROPIC_BASE_URL` at `https://anthropic.test` in tests, and a request no fake serves fails the test.

- `fakeQloo({ search })` serves `/search` from hand-written results keyed by query. A number in place of results answers with that HTTP status, `{ status, body }` answers with that raw body, such as a proxy's HTML error page, and `'hang'` never answers, so the gateway times out.
- `fakeQloo({ search, first: { 'Deep Cuts': [503, 503] } })` answers a query's first requests from `first`, in order, then from `search`. `latencyMs` delays every answer. `held` holds every answer until its promise settles, so a test sees lookups still pending until it lets them go, as long as that's within the gateway's timeout and retries (about 3 s in tests). `keys` lists the API keys it takes: a search with any other `X-Api-Key` gets a 401, as Qloo answers a key it doesn't know, so a network's own key can be refused (`test/qloo-key.test.ts`).
- Every Qloo fake serves `QLOO_BASE_URL` and both hosts a network's own Qloo key can be for (`QLOO_HOSTS` in `src/gateway.ts`: `https://api.qloo.com` and `https://hackathon.api.qloo.com`), so a test reads which host and key each request went with from `requests` (`url.origin`, `headers.get('X-Api-Key')`).
- `fakeInsights(answer)` serves `POST /v2/insights` rankings: a list of `{ entity_id, name, affinity, explainability }`, an HTTP status, or a function of the request's flat-key body that returns either, or a promise of either, to hold one ranking while the test looks, as `test/roster-overlap.test.ts` holds one anchor's. Left out, `explainability` splits each score evenly across the request's anchors; `null` leaves it off the result.
- `fakeQlooDown(status)` answers every Qloo request, on any endpoint, with that status, as when Qloo is down. Registered after the other Qloo fakes, it overrides them; register them again to bring Qloo back.
- `fakeCompare(answer)` serves `GET /v2/analysis/compare` from shared tags keyed by side `b`'s entity ID: a list of `{ tag_id, name, score }` in Qloo's order, or an HTTP status. A side `b` with no entry shares no tags, and `{ latencyMs }` delays every answer.
- `fakeDemographics(answer)` serves `POST /v2/insights` demographics requests, those with `filter.type=urn:demographics`: the entries of a list of `{ entity_id, age, gender }` whose entity the request names, in the list's order as Qloo answers in no set order, or an HTTP status, or a function returning a promise of either, to hold the answer while the test looks, as `test/roster-listeners.test.ts` holds a profile's. `fakeInsights` leaves those requests to it, so the two can be registered in either order.
- `requests` records every request a fake served, in order, with the time it arrived (`at`) and how many Qloo requests were in flight (`inFlight`). `test/setup.ts` clears it after each test.
- `test/session.ts` wipes every Durable Object after each test, so the gateway's shared cache and daily count start empty. Keep `cloudflare:test` out of `test/setup.ts`: imported there, it crashes the next test file's worker when files share one, as on CI.
- The wipe takes D1 with it, so `test/session.ts` applies the directory's migrations again before each test, with `applyD1Migrations` on `env.DB`. `vitest.config.ts` reads them from `migrations/` with `readD1Migrations` into the test-only `TEST_MIGRATIONS` binding. A test file that uses D1 imports `./session`. Only storage tests read D1 directly: `test/directory.test.ts` checks the schema, and runs migrations 0003's, 0008's, and 0009's statements over rows it sets up, 0009's over a temporary guest member it writes as ADR 0006's sign-in did, `test/auth.test.ts` checks that only hashes of tokens and codes are kept and that the cron purges expired rows, `test/api-keys.test.ts` that only an API key's hash and prefix are, and `test/qloo-key.test.ts` that a network's gateway instance never stores its own Qloo key in plain text (with `runInDurableObject` from `cloudflare:test`) and that a network without a key has no gateway instance at all (with `listDurableObjectIds`), `test/guest.test.ts` that refusing a guest a passkey or a new recovery code writes no challenge, and that a guest sign-in makes the guest member's row again once it's gone, and `test/guest-cleanup.test.ts` that the cron prunes the log of guest sign-ins and the log of sign-ups through guests' invite links. Every other test reaches the directory through the Worker's routes.
- Tests run with `RP_ID` `crossfeed.test` and `APP_ORIGINS` `https://crossfeed.test`, the origin `test/session.ts` sends from, and with the sign-up, network, launch, invite, and API key caps and the guest sign-ins a minute at `wrangler.jsonc`'s values, whatever `.dev.vars` says. A test of the launch cap lowers `LAUNCHES_PER_NETWORK` on `env` and restores it (`test/api-launches.test.ts`).
- Tests run with a 1-second Qloo timeout, retry delays of 10 and 30 ms, and no pacing (`vitest.config.ts`). A test that needs another value assigns it to `env` from `cloudflare:workers` and restores it afterwards, as `configure()` in `test/gateway.test.ts` does.
- Tests run with `SAMPLE_NETWORK` off, so a new engine session and the guest network start with an empty roster and make no Qloo calls of their own. `test/sample.test.ts` turns it on to test the sample network, `test/guest.test.ts` to test the guest network's loading of it, and of the sample inbox with `GUEST_PITCHES` on too, `test/launches.test.tsx` to test the guest network's sample launch and its replay, and `test/sample-launches.test.tsx` to test its sample launches: it runs them on the guest network against the fakes, captures them with `test/capture.ts`, as the capture script does, loads their SQL into D1 with `env.DB.exec`, and clears the guest network with the daily cron so it seeds them. It also counts the daily cron's subrequests, its D1 queries and Durable Object calls each apart, through the bindings it passes the Worker's `scheduled` handler, which `test/counting.ts` makes, as `test/wipe-retry.test.ts` counts the hourly retry's. To restart an agent, as after an idle eviction, a test calls `evictAllDurableObjects` from `cloudflare:test`. It waits for the Qloo calls still out, so it can't interrupt a lookup, and with Qloo's answers `held` it never returns: to stand in for an agent a deploy stopped mid-load, `test/guest.test.ts` sets the guest network's inbox back to reading, or its roster's shows back to pending, with `runInDurableObject`, then restarts it, as `test/network-roster.test.tsx` does for a member's import. It stands in for a guest network an import left with no CPM before #287 the same way, setting `cpm` to `null`. A gateway left evicted as a test ends keeps its daily counts through the per-test reset, into the next test, so a test that ends on a restart reads the guest budget after it, as `test/guest.test.ts`'s do.
- `fakeClaude(script)` is the scripted model. Each Messages API request gets the next turn, streamed as the API streams it, after an empty thinking block like Haiku 5.5's. Build turns with `turn(toolUse(name, input), text(...))`, which ends in tool calls if it has any, or `refusal(category)`. Tool use IDs are `toolu_<turn>_<block>`. A script entry can be an async function of the request, to hold a turn while the test looks at a running run. A request past the end of the script gets a 400.
- `modelRequests()` returns the body of every request the scripted model got, to check model settings and history.
- `fakeReader(count, answer)` scripts the model's reading of `count` pitches, each answer (`{ guest, work }`) chosen by `answer` from the pitch's text, so pitches read at once can be answered in any order. `test/emails.ts` holds synthetic pitch emails, one per kind a mail client sends (plain, HTML-only, multipart with an attachment), and an `.mbox` of them, for the app's upload and the API alike.
- `qlooRequests()` returns each request Qloo got as Qloo reads it, its path, every decoded parameter, and its body, lowercased, to check that a guest's name or a sender never reaches Qloo (`test/network-inbox.test.tsx`, `test/api-inbox.test.ts`).
- A run's topic baseline request doesn't take a scripted turn, and `modelRequests()` leaves it out. `fakeClaude` answers it from `fakeTopic(answer)`: show names in topic order, a scripted turn such as `refusal(...)`, an HTTP status, or a function of the request, which can hold its answer. By default it ranks the shows in the order the request lists them, `topicNames(request)`. `topicRequests()` returns each baseline request's body.
- A pitch run's pitch ranking request is a ranking request too, known by the pitch IDs it ranks: it takes no scripted turn, `modelRequests()` leaves it out, and `fakeClaude` answers it from `fakePitchRanking(answer)`, which takes what `fakeTopic` does, pitch IDs for names. By default it ranks the pitches in the order the request lists them, inbox order. `pitchRankingRequests()` returns each one's body.
- To run a cron, call the Worker's `scheduled` handler with `createScheduledController({ cron })`, the hourly schedule or the daily one, and `createExecutionContext()` from `cloudflare:test`, as `test/guest-cleanup.test.ts` and `test/health.test.ts` do, and spy on `console.log` and `console.error` for its log lines. Move the clock with `vi.useFakeTimers({ toFake: ['Date'] })` and `vi.setSystemTime`, as a guest's day or a wipe's minute needs: the Worker, its agents, and the directory's queries all read it.
- In the Workers vitest pool and on the dev server, a wipe's answer reaches its caller before its instance's own reset; on Cloudflare the reset comes first (`awaitWipe` in `src/wipe.ts`). `test/wipe-reset.test.ts` has each agent's `destroy` and gateway's `wipe` wait for that reset before answering (`resetFirst()`), and makes a wipe meet a reset for another reason, as a deploy's, with the instance's state from `runInDurableObject`.
- Add a fake for a new endpoint or API to `test/fake.ts` the same way.

Fixtures are synthetic: made-up names, IDs, and scores. Never paste a real Qloo response into a test.

### Driving a session

`openSession()` in `test/session.ts` is a session of the engine, `CrossfeedAgent`, which the network and launch agents extend. It makes a session cookie of its own, a random UUID, then opens the agent's WebSocket at `/agents/session` the way `useAgent` does. That route answers only while `TEST_SESSIONS` is on, as `vitest.config.ts` sets it and `wrangler.jsonc` never does, so a deployed Worker has no per-visitor agents (ADR 0007):

- `call(method, ...args)` calls a `@callable` action and resolves with its result, after the state it set has arrived.
- `importRoster(text, format?)` imports a roster and resolves once every show's search has settled. `call('importRoster', ...)` resolves as soon as the shows are pending, before any search returns.
- `searchComps(name, query)` searches for a comp and resolves once the search has settled; `call('searchComps', ...)` resolves while it's still pending.
- `state()` is the latest synced state, and `until(ready)` waits for synced state that passes `ready`, such as a finished run.
- `frames()` is every raw frame the server sent, which is everything the visitor's browser receives.
- `openSession(cookie)` reconnects to the same session, like a reload; `openSession()` is a new one.

A test that renders a page of the island from a session's state passes it what the server would: `LaunchWorkspace` from `src/client/Launch.tsx` takes `launchPage` from `test/session.ts`, a launch's network and where its orders export; `NetworkRoster` from `src/client/Roster.tsx` takes the network's agent alone; and `InboxWorkspace` takes `links`. A page's form dialog, New launch, the roster's import (`RosterImport`) and the inbox's load (`InboxLoad`), is kept mounted while it's closed, but a portal renders nothing on the server, so `test/page-forms.test.tsx` mocks the dialog fork's `DialogContent` to render a dialog kept mounted in place, and reads each form from its page. Every other test file renders pages without it, so their words leave the dialogs out.

### Driving a member

`openMember()` in `test/session.ts` is a member, signed up the way the sign-in page does it: it asks `/auth/sign-up/options` for a new passkey's options, has the software authenticator make the passkey, and sends it to `/auth/sign-up`.

- `openMember({ name, ip })` signs up a new member, named `Ada Programmer` unless you name them. `ip` is their address, as `CF-Connecting-IP`; without one, the sign-up cap doesn't apply. A sign-up through an invite counts against its maker's `INVITED_SIGNUP_DAILY_CAP` instead, whatever the address; `test/members.test.ts` lowers it on `env`.
- `openMember({ name, invite })` signs up through an invite link instead, as its invite page does, joining the link's network in the same step; `network` is the network they joined, null without an invite.
- `cookie` is their session cookie as the browser sends it back, and `recoveryCode` the code shown at sign-up.
- `id` is their member ID, read from the passkey's user handle in the sign-up options.
- `fetch(path, init)` is a request from the member's browser: it carries their cookie, and on a write the app's `Origin`, which every cookie-authenticated write needs.
- `connect(path, headers)` opens an agent's WebSocket from one of the app's pages, such as a network's at `/agents/network/<id>`, with their cookie and the app's `Origin`, and returns the same `call`, `state`, `until`, and `importRoster` as a session, plus `closed()`, which resolves with the close code and reason once the server closes it.
- `invite(network)` makes an invite link to a network the member owns, as its settings do, and returns the link, with its token in the fragment.
- `authenticator` holds the member's passkey, to sign in again through `/auth/sign-in/options` and `/auth/sign-in`.

A member's account is theirs to change through `/app/account`'s routes, as `test/account.test.ts` does: `POST /app/account/name`, `/app/account/recovery-code`, `/app/account/sign-out-everywhere`, `/app/account/delete`, and `/app/account/passkeys/<id>/remove`. A passkey is added through the ceremony's two requests, `/auth/passkeys/options` and `/auth/passkeys`, answered by another `softwareAuthenticator()`, as another device would; the account page's `data-passkeys` lists them. Adding a passkey, a new recovery code, and deleting the account need a proof that it's the member from the last five minutes (step-up): a sign-up, a passkey sign-in, a recovery, or `POST /auth/verify`. Past five minutes each answers 403 with `stepUp: 'passkey'` and the ceremony's `challenge` and `options`, which the member's own `authenticator` answers to `/auth/verify`, or, in a browser signed in with a recovery code, `stepUp: 'code'`, answered with `{ code }`. `confirmedFetch(member, path, init)` in `test/session.ts` answers a passkey step-up as the account page does and sends the change again, and `addPasskey` goes through it, so a test that moves `Date` on past five minutes still adds one; `test/step-up.test.ts` drives the step-up itself. `test/account-page.test.tsx` renders the account page from its data attributes. Deleting an account makes each launch of the member's networks, and of those they left or were removed from before (noted in `past_memberships` as the membership ends), forget their name; `test/launches.test.tsx` reads them from another member's launch pages, and makes a launch unreachable by mocking `LaunchAgent.prototype.forgetMember` once. Each network's own agent drops them from the replies they approved and its checklist, and `test/network-inbox.test.tsx` reads that from another member's inbox and `getRun`. Deleting a network is an owner's `POST /app/<id>/settings/delete` with its `name`; `test/delete-network.test.ts` reads its agents over RPC to check they were wiped, and makes a wipe fail by mocking `NetworkAgent.prototype.destroy` or `LaunchAgent.prototype.destroy` once.

An owner adds the network's own Qloo key by posting `{ host, key }` to `/app/<id>/settings/qloo-key`, and removes it with `.../qloo-key/remove`, as `test/qloo-key.test.ts` does; register `fakeQloo` with the key among its `keys` first, since saving it makes one search. From then on the network's and its launches' Qloo calls go to that host with that key, which `requests` shows. To read a network's gateway instance as the Worker would, call `env.QlooGateway.getByName('network:<id>')` (`ownKey()`, `usage('network:<id>')`), with a new stub for each read after a wipe. Reading it creates it, so to check that a network without a key has none, list the instances that have stored anything with `listDurableObjectIds(env.QlooGateway)` from `cloudflare:test` and look for `idFromName('network:<id>')`: the list keeps a wiped instance, and earlier tests' ones, since the local runtime keeps each emptied database. To land a call in the moment between a wipe and the instance's reset, hold Qloo's answers, remove the key under `vi.useFakeTimers({ toFake: ['setTimeout'] })`, then let them go; don't run the held timer, which would reset the instance from the test's context, but return to real timers and leave the instance to the per-test reset. `test/qloo-key.test.ts` makes a removal's wipe fail by mocking `QlooGateway.prototype.wipe` once, and a launch miss the network's notice of a key by mocking `LaunchAgent.prototype.noteOwnKey` once, which also stands in for the launch's own call as a run copies the roster. To stand in for a network agent from before #197, which never kept whether the network has a key, delete `crossfeed_own_qloo_key` from its storage with `runInDurableObject`, then restart it with `evictDurableObject`.

`openGuest()` in `test/session.ts` is someone who signed in as a guest, as the sign-in page's "Sign in as a guest" does, with one `POST /auth/guest` (`guestSignIn`, for the raw answer). `guestFormSignIn({ cookie, next, site })` posts as a public page's guest button does, a plain form with `Origin: null` and `Sec-Fetch-Site: site` (`same-origin` unless given), and leaves its redirect unfollowed. `openGuest({ ip, cookie, next })` signs in from that address, from a browser holding that session cookie, which, while it's live, isn't signed in again, and with that `?next`. It returns the guest's `cookie`, the `next` the route answered, and the same `fetch` and `connect` as a member's: every guest is the one guest member, `guest-member`, an owner of the guest network, `/app/guest-network` ([ADR 0008](/docs/adr/0008-guests-share-one-guest-member-again.md)), with a session of their own. `test/guest.test.ts` drives guest sign-in, a guest session's day under fake `Date` timers, the limits a minute and a day, the guest network's one daily budget, spent by guests from different addresses and none over their connections to the guest network's agents (sent with `CF-Connecting-IP`, as `connect`'s `headers`), the guest network's clearing by the daily cron, and its reset to the sample data from its settings, once a minute for everyone, what a guest changes as an owner, what no guest can change of the account every guest shares, each refused with one reason, the guest member made an owner of the guest network again as a guest signs in or opens `/app`, the guest budget across the guest network and the networks guests create, with an own Qloo key's calls kept apart, and invited sign-ups through every guest's links counted together. It renders the invite page as a guest sees it, telling them to sign out and create an account to join, `Invite` from `src/client/Account.tsx`, from the page's data attributes and `/auth/invite`'s answer, as the page has them once it has posted the link's token.

A member creates a network by posting its name to `/app/new`, as `test/networks.test.ts` does. A second member joins it through the real invite flow: `await openMember({ name: 'Grace Booker', invite: await ada.invite(network) })` for a new person, or a signed-in member posting the link's token to `/auth/join`, as `test/members.test.ts` does. Nothing reads or writes D1 outside the directory module. `test/dashboard.test.tsx` renders the dashboard, the Launches page and settings from a network agent's synced state and the data attributes the server gave the page, and `test/network-roster.test.tsx` the roster page.

A launch is planned on the network's agent, as the Launches page's "New launch" does: `call('createLaunch', { name })` or `{ comps }` returns its `{ id }` and adds it to the synced `launches` list. Its page's agent is then `connect('/agents/launch/<networkId>/<launchId>')`, with the same `call`, `state`, and `until`; a run started there copies the network's roster, so import and settle the roster on the network's agent first. `test/launches.test.tsx` drives launches this way, and renders the Launches page and a launch's page (`LaunchWorkspace` in `src/client/Launch.tsx`) from their agents' synced state.

Approving an insertion order takes the page's connection: a test calls `approveInsertionOrder` over `connect`, and checks that an RPC call, as the API would make, is refused. On a launch's agent the connection must carry a member, so a connection sent straight to its stub with `connect(path, {}, via)` is refused too (`test/launches.test.tsx`). Deleting a launch is a member's `POST /app/<id>/launches/<launchId>/delete`; `test/launches.test.tsx` makes a wipe fail by mocking `LaunchAgent.prototype.destroy` once (the agents run in the tests' isolate) and runs the cron with fake `Date` timers a few minutes on. A wiped instance, an agent's or a gateway's, is reset a moment after its wipe, later on a loaded machine, and until then each call to it throws: read it with `readAfterReset(read)` from `test/session.ts`, which tries `read` again until it answers, bounded only by the test's timeout, then assert on what it returns. A time-bounded wait such as `vi.waitFor` fails when the reset outlasts it.

Some of a network agent's callers have no connection, such as the API and a launch's agent asking its network for the roster as a run starts (`rosterForLaunch`) and reporting its summary back (`reportLaunch`). A test calls the agent as they will, over RPC, with `(await getAgentByName(env.NetworkAgent, networkId)).importRoster(...)` (`getAgentByName` from `agents`), as `test/network-roster.test.tsx` does to check such calls count against the network. Wrap an RPC call in an `async` function before `expect(...).rejects`, as `test/network-inbox.test.tsx` does: Vitest can't read the RPC promise itself. To read a roster file as the roster page does, pass `File`s to `readRosterUpload` from `src/upload.ts` and import its result over the agent; for pitch files, pass them to `readPitchUpload` and load `{ pitches }` with `loadInbox`. A launch's `summary`, which the network asks a launch whose row predates its promo inventory for as it starts (#406), is RPC too: `test/launches.test.tsx` stands in for a network from before then by setting its rows without the inventory and deleting `crossfeed_inventory_asked` from its storage with `runInDurableObject`, restarts it with `evictDurableObject`, and makes a launch fail to answer by mocking `LaunchAgent.prototype.summary` once.

`connect(path, headers, via)` in `test/session.ts` opens an agent's connection the way `useAgent` does. Its upgrade goes to the Worker unless `via` sends it elsewhere: `test/network-inbox.test.tsx` sends it straight to a network agent's stub, as a Worker route that let it through unchecked would, to check that a connection with no member can't approve a reply.

`softwareAuthenticator()` in `test/authenticator.ts` stands in for a browser's platform authenticator. `register(options)` answers `navigator.credentials.create()` with an ES256 passkey and "none" attestation. `authenticate(options)` answers `navigator.credentials.get()` with a discoverable passkey it holds for the relying party, flagged user present and user verified, with a signature counter of 0, as synced passkeys send. Both answer from `https://crossfeed.test` unless a test passes another origin. `softwareAuthenticator({ userVerified: false })` can't verify the person, as a security key without a PIN. `test/auth.test.ts` drives each ceremony step by step, for tests of the ceremonies themselves.

### Driving the API

`api(secret)` in `test/session.ts` is a program with an API key: it sends `Authorization: Bearer <secret>` and no cookie or `Origin`, as `curl` does, and returns a `fetch(path, init)`. An owner makes the key the way the settings page does, by posting `{ name }` to `/app/<id>/settings/api-keys` with `member.fetch`, which answers the secret once (`test/api-keys.test.ts`, `test/api.test.ts`). `networkWithKey(member?)` does both for a new network and returns `{ ada, network, secret, call }`, `call` being the key's `fetch`. `member.fetch('/api/v1/...')` is the same member's session instead, with the app's `Origin` on writes.

- Long work answers 202 with the resource's current status, so a test polls the resource until it settles, as a program does: `poll(call, path, ready)` in `test/session.ts` reads `path` until its JSON passes `ready` (`settled` in `test/api.test.ts` predates it). A fake answering at once may settle before the 202 is written, and one answering a little later may settle before a test's next request when the machine is loaded, so a test that needs the work still pending holds Qloo's answers and lets them go once it has looked: `const lookups = Promise.withResolvers<void>()`, `fakeQloo({ search, held: lookups.promise })`, then `lookups.resolve()` (`test/api.test.ts`). Don't use `latencyMs` for this.
- Every refusal is `{ error: { code, message } }`; assert both. A new endpoint goes in `src/routes/api.ts` with its zod schemas, and `test/api.test.ts`'s OpenAPI test fails until it's in the document. Its examples must use made-up shows: the same test checks the document names nothing the sample network looks up in Qloo.
- A run started through the API, such as a pitch run (`test/api-inbox.test.ts`), is polled the same way until it's done or waiting on its question. To see a run's 202 while it's still running, hold its first scripted turn with a promise the test releases once it has read the answer: `() => held.then(() => turn(...))`.
- A launch's run through the API (`test/api-launches.test.ts`) ranks a roster the test first imports, settles, and prices through the API too. Approval stays the app's: the test approves an order over the member's own launch connection, `ada.connect('/agents/launch/<networkId>/<launchId>')`, then exports it through the API. Deleting a launch through the API takes the member's session (`ada.fetch`); `ada.fetch` always sends the app's `Origin`, so a cross-site write is sent with `exports.default.fetch` and the cookie by hand.
- The inbox and pitch run routes need `GUEST_PITCHES` on, as the page does: a test turns it on in `beforeEach` and off again after.
- Every route that reads a body stops at its limit and answers 413: 64 KB of JSON under `/auth/*` and `/app/*` (`jsonLimit` in `src/auth.ts`), and the 5 MB upload limit plus 64 KB under `/api/v1/*` and `/mcp` (`uploadLimit` in `src/routes/api.ts`), whether the body says its `Content-Length` or streams in with none. `test/body-limits.test.ts` sends a streamed body as a `ReadableStream` that stays open past the limit, so a route that doesn't stop reading never answers.
- The rate limits count in fixed one-minute windows that the per-test reset clears. A test of a limit sends requests until one is refused, up to twice the limit and two more, since a window can roll over mid-test (`untilRefused(send, limit)` in `test/session.ts`).

### Driving the MCP server

`assistant(secret)` in `test/mcp.test.ts` is an assistant's MCP client, as Claude Code connects one with the key in `Authorization: Bearer`: each JSON-RPC request is a POST to `/mcp`, in the 2025 protocol's shape with no `_meta` envelope, which the handler serves statelessly and answers as a server-sent event. `initialize()` and `tools()` read the server, `call(name, args)` returns `{ text, structured, isError }`, the concise text, the structured content (the operation's result plus `summary`, the same text), and whether it was refused, and `until(name, args, ready)` polls a read tool, as an assistant does, until its structured result passes `ready`. A refusal is a tool result with `isError` and `{ error: { code, message } }`, not a JSON-RPC error; only the key check before the handler answers with an HTTP status (401, 404 with `ACCOUNTS` off, 429). Script the agent's turns with `fakeClaude` as for the API, and assert what the assistant reads: each question's text, how to answer it, and where a member approves.

### Driving the SDK

`test/sdk.test.ts` drives the Worker through the TypeScript SDK in [`packages/sdk`](/packages/sdk/README.md), imported from its source, as a program using it would. `client()` there makes a network and its key with `networkWithKey` and returns `crossfeed`, a `Crossfeed` client whose `fetch` is `exports.default.fetch`, so its requests reach the Worker in the tests' isolate. Its wait helpers poll as they do for a program; give them `{ interval: 10 }` so a test doesn't wait a second between reads. Approval stays the app's, through the member's launch connection, as in the API's tests.

- A refusal rejects as a `CrossfeedError`; `refusal(call)` there returns its `code`, `status`, and `message` to assert, failing the test if the call succeeds.
- "reach every route the OpenAPI document describes" calls each of the SDK's methods once and fails while a documented route has no method. A new API route needs its method in `packages/sdk/src/index.ts` and a call there.
- "match the OpenAPI document the Worker serves" fails once the API's document differs from `packages/sdk/openapi.json`, and "are generated from that document" once the SDK's types weren't generated from it. After changing the API, run `bun run generate` in `packages/sdk`, which writes the document and regenerates the types, then commit both.

## CI

[`.github/workflows/ci.yml`](/.github/workflows/ci.yml) is written for every pull request, including a retitle, and every push to `main`, but GitHub's hosted runners don't run this repo's workflows (#368), so it runs on your machine instead, with [act](https://github.com/nektos/act) (below). One job installs the repo root, `apps/`, and `packages/sdk` with `bun install --frozen-lockfile` (the SDK without its build script), then runs these steps. Each step runs even when an earlier one fails, so one run reports every failure:

1.  **Format:** `bun run lint` at the repo root, Prettier's check.
1.  **Typecheck:** `bun run typecheck` in `apps/`.
1.  **Typecheck SDK:** `bun run typecheck` in `packages/sdk`. Format covers its files with the rest of the repo, but for its generated `openapi.json` and `src/openapi.ts`.
1.  **Test:** `bun run test` in `apps/`.
1.  **PR title:** the title through `bunx commitlint`, on pull requests only.
1.  **Secrets:** `gitleaks git` on the commits the pull request or push adds.

Before merging, run the job with `scripts/ci.sh <pr>` at the repo root, and wait for act's "Job succeeded". The pull request's own GitHub check fails within seconds, before its first step; ignore it. The script needs `gh`, `jq`, `act`, and Docker running. It tests the commit GitHub would, the pull request merged into its base branch's tip, which it makes itself rather than read GitHub's merge ref, since that can lag the base by minutes. So rebase a pull request that conflicts first: the script refuses one. It clones the repo afresh into a scratch folder, since a worktree's `.git` is a file the job's container can't follow. It gives act the pull request's number, title, and base and head commits, and runs the job as amd64, the build the Secrets step downloads, on 4 of Docker's CPUs in 6 GB. It takes about 12 minutes, about 5 of them setting up Bun and its cache, and it's heavy, so run it while nothing else runs the suite. Runs go one at a time, from any session: a run waits for the one before it to end. Each run also names its copy of the workflow after the pull request and its own process, since act names the job's container and volumes after the workflow, so a run never joins another's, and it removes them when it ends. Post its result on the pull request with `gh pr comment`.

While you work, run the listed commands where they're listed, check a title with `echo '<title>' | bunx commitlint` at the repo root, and check your commits with `gitleaks git --log-opts="origin/main..HEAD"`.

## Deploy

Deploy only from an up-to-date `main`, and only one deploy at a time:

```sh
git fetch origin main && git checkout --detach origin/main
cd apps && bun install && bun run deploy
```

`bun run deploy` builds, applies the directory's new migrations to the `crossfeed` D1 database (`wrangler d1 migrations apply DB --remote`, which lists them and asks before applying), then deploys the `crossfeed` Worker. It doesn't load the guest network's sample launches, which each environment's database holds by hand: see [Sample launches](#sample-launches).

Wrangler takes the Cloudflare account from `account_id` in `wrangler.jsonc`, the `m1kuorg` account, so a login that can see several accounts deploys to the right one. One command ignores it, in Wrangler 4.151 and 4.153: `wrangler d1 migrations list --remote` fails with "More than one account available" when it can't ask which, so give it the same account: `CLOUDFLARE_ACCOUNT_ID=f0621d6622ac79af0e8e6f3520f78063 bunx wrangler d1 migrations list DB --remote` lists the migrations not yet applied to production's database.

Secrets live on the `crossfeed` Worker in the `m1kuorg` Cloudflare account, and are set once with `bunx wrangler secret put QLOO_API_KEY`, `ANTHROPIC_API_KEY`, `VISITOR_SALT` (a random value, such as `openssl rand -hex 32`; changing it restarts every visitor's count), and `QLOO_KEY_SECRET` (a random value, such as `openssl rand -base64 32`, which encrypts each network's own Qloo key; changing it makes every saved key unreadable, so each owner adds theirs again). List them with `bunx wrangler secret list`.

### Deploy the preview

The `preview` environment in `wrangler.jsonc` is a separate Worker, `crossfeed-preview`, at <https://crossfeed-preview.m1kuorg.workers.dev>, with its own D1 database (`crossfeed-preview`), Durable Objects, and secrets, and with `ACCOUNTS` on. Merged work is checked there before it reaches production. Deploy it the same way, from an up-to-date `main`:

```sh
cd apps && bun install && bun run deploy:preview
```

`bun run deploy:preview` builds with `CLOUDFLARE_ENV=preview`, applies migrations to `crossfeed-preview`, and runs `wrangler deploy --env preview`. Don't run `bunx wrangler deploy --env preview` by hand after `bun run build`: the Vite plugin picks the environment when it builds, and Wrangler deploys whatever the build was for, production included. `bunx wrangler deploy --env preview --dry-run` after `CLOUDFLARE_ENV=preview bun run build` shows what would deploy without deploying. `wrangler secret` and `wrangler d1` read `wrangler.jsonc` itself, whatever was built, so `--env preview` is enough for them.

Wrangler can't set secrets on a Worker that doesn't exist yet, so the first deploy takes them from a file: write `QLOO_API_KEY`, `ANTHROPIC_API_KEY`, a new `VISITOR_SALT`, and a new `QLOO_KEY_SECRET` as `NAME=value` lines to a file outside the repo, run `bun run deploy:preview --secrets-file <file>`, and delete the file. Afterwards, set and list them with `bunx wrangler secret put <NAME> --env preview` and `bunx wrangler secret list --env preview`. `CLOUDFLARE_ACCOUNT_ID=f0621d6622ac79af0e8e6f3520f78063 bunx wrangler d1 migrations list crossfeed-preview --env preview --remote` lists the migrations not yet applied to the preview's.

To cap the deployed Worker without a code change, deploy from up-to-date `main` with `bunx wrangler deploy --var QLOO_DAILY_CALL_CAP:0` (after `bun run build`), check, then `bun run deploy` again to restore `wrangler.jsonc`'s cap. `--var RUN_VISITOR_DAILY_CAP:n`, `--var RUN_DAILY_CAP:n`, `--var FREE_START_DAILY_CAP:n`, and `--var QLOO_VISITOR_DAILY_CALL_CAP:n` lower the per-visitor and daily limits the same way.

Gateway log lines (`"event":"qloo_call"`) show each Qloo call's endpoint, status, latency, retries, and cache hit, in the dev server's output, in Workers Logs, and live with `bunx wrangler tail --format json`. To see failures in the running app, add `QLOO_TIMEOUT_MS=1` or a low `QLOO_DAILY_CALL_CAP` to `.dev.vars` and restart the dev server. To see a slow call named, add a low `QLOO_SLOW_MS`, such as `500`, so a normal call passes it.

The crons (`triggers.crons` in `wrangler.jsonc`) run every hour. The hourly one, `0 0-11,13-23 * * *`, purges the directory's expired sessions, challenges, and invites, and the guest logs' rows no limit counts any more, and logs how many (`"event":"directory_purged"`); and tries again 23 agent wipes noted over a minute before, those no run has tried first, oldest first, then those tried before, the least recently tried first, leaving the rest for the next hour, so it makes at most 49 D1 queries and 92 Durable Object calls, 184 if agent starts retry ([TRD](/docs/TRD.md#bindings)), and logs how many it wiped, kept, and failed (`retryWipes`, `"event":"wipes_retried"`). The daily one, `0 12 * * *`, purges the directory as the hourly one does, the hourly one skipping 12:00, but leaves the wipes it notes to the next hour's retry, so it makes 40 subrequests at most, D1 queries and Durable Object calls together, however many launches the guest network lists, within the Free plan's limits ([TRD](/docs/TRD.md#deployment-and-configuration)). It clears the guest network, noting each launch's wipe in one batch and wiping its agent and gateway instance, and logs how many launches it noted and how many wipes failed (`resetGuestNetwork`, `"event":"guest_network_reset"`); the next hour's retry wipes the launches' agents, closing any of their pages still open. Until then each launch's agent takes no more work: a start, an answer, or an order's edit or approval from one of those pages, or its run's next model turn, stops its run and closes its pages saying the guest network was cleared. It clears what guests made beyond it, each in a batch of its own: removes the temporary guest members ADR 0006 made, with the networks only they own, and deletes the API keys and invite links they made, logging how many members and networks (`removeTemporaryGuests`, `"event":"guests_removed"`), and deletes the networks only the guest member owns, closing their pages and noting their wipes, takes it out of the rest but the guest network, deletes the API keys and invite links it made, and frees its networks-per-member count, logging how many networks it deleted and left (`clearGuests`, `"event":"guest_member_cleared"`), and runs the health check, which logs one `"event":"health_check"` line per check, at error level with the reason when it fails:

- `qloo_search`: the TRD's health-check search, sent to Qloo past the cache. A 401 means the key stopped working.
- `sample_ranking_cached`: the sample launch, The Watch against the other 15 resolved sample shows with nothing settled, answers from the cache. It reads the cache only and never calls Qloo, so it fails until a fresh session has started the sample launch before settling anything. Settling Binge Mode or mapping a miss first sends a different ranking.

Run them locally with `curl 'http://localhost:5128/cdn-cgi/local/scheduled?cron=0+0-11,13-23+*+*+*'` (hourly) or `curl 'http://localhost:5128/cdn-cgi/local/scheduled?cron=0+12+*+*+*'` (daily) against the dev server, which prints `ok` and logs the lines in the server's output. To see what guests made cleared, sign in as a guest, create a network, and make an API key and an invite link, then run the daily cron: it logs `guest_member_cleared` with the network, whose page answers 404, the key answers 401, and the guest network's setup checklist starts over. Its agent's wipe is noted for the next run, which retries a wipe once it's a minute old: run the hourly cron a minute later. To see a guest network launch stop, start a run on its page and leave it at a question, then run the daily cron: the page stays open until you answer, then closes saying the guest network was cleared, with no `model_call`, and the run says the same; the hourly cron a minute later wipes its agent. On the Worker, `bunx wrangler deploy` lists `schedule: 0 0-11,13-23 * * *` and `schedule: 0 12 * * *`, and `bunx wrangler tail --format json` across the hour shows a run.

Wrangler can't run the deployed cron on demand, but a temporary per-minute schedule can, through the schedules API that `bunx wrangler deploy` uses. The cron handler runs the daily cron's work for every schedule but the hourly one, so every tick runs the health check, and clears the guest network. Treat it as a deploy, one at a time: a deploy puts `wrangler.jsonc`'s schedule back. In `apps/`:

```sh
SCHEDULES=https://api.cloudflare.com/client/v4/accounts/f0621d6622ac79af0e8e6f3520f78063/workers/scripts/crossfeed/schedules
TOKEN=$(bunx wrangler auth token --json | jq -r .token)
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data '[{"cron":"0 0-11,13-23 * * *"},{"cron":"0 12 * * *"},{"cron":"* * * * *"}]' "$SCHEDULES"
bunx wrangler tail crossfeed --format json
```

The tick is the tail event with an `.event.cron`, and its `logs` hold the two `health_check` lines. Then put the schedules back, and check that they're only `0 0-11,13-23 * * *` and `0 12 * * *`:

```sh
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data '[{"cron":"0 0-11,13-23 * * *"},{"cron":"0 12 * * *"}]' "$SCHEDULES"
curl -H "Authorization: Bearer $TOKEN" "$SCHEDULES"
```

Each change takes about five minutes to reach the Worker: the first tick comes about five minutes after the first `PUT`, and ticks go on for about five minutes after the second. Each tick spends one Qloo call on its search, so budget about 15.

Agent log lines show each model call's tokens and cache reads (`"event":"model_call"`), each run's topic baseline with its status and whether it came from the cache (`"event":"topic_baseline"`), each pitch run's pitch ranking the same way (`"event":"pitch_ranking"`), and one summary per run with its outcome (`"event":"run_summary"`). ### Production CSP check

The dev server lets Vite inject `<style>` elements and runs React's refresh script under a nonce, so it hides what the Content-Security-Policy refuses in production. Check UI work, above all a floating component (a menu, popover, dialog, sheet, select, tooltip, or toast), on the built Worker, which sends the production policy. In `apps/`, with `.dev.vars` and the local database set up:

```sh
bun run build
bunx wrangler dev -c dist/crossfeed/wrangler.json --port 8787 --persist-to .wrangler/state \
  --var ACCOUNTS:on --var GUEST_PITCHES:on --var RP_ID:localhost --var APP_ORIGINS:http://localhost:8787
```

The build copies only the secrets from `.dev.vars`, so the flags set the rest, and `--persist-to .wrangler/state` uses the dev server's local D1 and agents, so don't run the two at once. Open each page you changed, signed-in pages included, at 1440 and 390, in light and dark, with the console open: none may report a refused script, style, or connection (a `securitypolicyviolation` event) or any other error. Rebuild and restart the server to check a change, and stop it when you're done.

## Where things go

- `src/index.tsx`: the Worker. It mounts one route module per surface from `src/routes/` on the one Hono app, and exports the Durable Objects and the cron handler. Every answer but an agent's connection gets the secure headers there, the Content-Security-Policy among them: the app's own origin alone, no inline script or style, and nothing framing a page. In development only, Vite's client needs the React refresh preamble, which `shell.tsx` renders under the request's nonce, and its injected `<style>` elements. A page that needs an inline style or script, or anything from another origin, needs the policy changed with it; `test/csp.test.ts` loads every page and checks it allows what each one loads, and that none has a `style` attribute. A new surface, such as the landing page, accounts, the app, the API, or MCP, gets its own module there, mounted at `/` with its full paths. Whatever none of them serves, or a route refuses with `c.notFound()`, goes to `notFound` from `src/routes/marketing.tsx`, and whatever a route throws outside the API, which answers its own, to `serverError` from the same module. Every answer but an agent's connection also passes `noindex` from `src/routes/crawlers.ts`.
- `src/routes/crawlers.ts`: what search engines read, by `SEARCH_INDEXING` ([TRD](/docs/TRD.md#crawlers)). With it on, as production has it, `/robots.txt` disallows `/app`, `/api`, `/mcp`, `/agents`, `/auth`, and `/invite` and names `/sitemap.xml`, which lists the public pages on `APP_ORIGINS`' first origin, the docs pages from `PAGES` in `src/routes/docs.tsx`; `noindex` marks everything under `/app`, and `/invite`, `X-Robots-Tag: noindex`. With it off or left out, as on the preview and in tests, `/robots.txt` disallows nothing, `/sitemap.xml` is a 404, and every answer is noindex. `test/crawlers.test.ts` checks both.
- `src/routes/demo.ts`: the retired demo (ADR 0007). `/demo`, `/demo/inbox`, and `/inbox` redirect to `/sign-in#guest`, the sign-in page's guest panel, while `ACCOUNTS` is on. `/agents/session`, which answers only while `TEST_SESSIONS` is on, as in tests, connects a `crossfeed_session` cookie's UUID to the `CrossfeedAgent` it names, for the engine's tests (`openSession`); any other value names no agent.
- `src/routes/marketing.tsx`: the marketing pages, server-rendered with no island: the landing page at `/`, whose developers band links the developer docs, the privacy page at `/privacy`, the beta terms at `/terms`, the 404 page, and the error page. `notFound`, the Worker's not-found handler, shows the 404 page, in the marketing shell, only to a `GET` that accepts `text/html` outside `/api`, `/agents`, `/mcp`, and `/auth` and not for a `.csv` (`pageRequest`); everything else, WebSocket upgrades and API callers among them, keeps Hono's plain `404 Not Found`. The page names the address asked for, cut to 80 characters, and ranks the site's own pages against it (`closest`): Home, Developers, each docs page from `DOCS` in `src/shell.tsx`, Privacy, Beta terms, and while `ACCOUNTS` is on Sign in, Create your network, and Your networks, by the Dice coefficient of character pairs with the page's path or name, showing at most three at 0.4 or over, or saying none is close ([DESIGN.md](/docs/DESIGN.md#marketing-shell)). `serverError`, the Worker's error handler, answers an `HTTPException` with its own response, logs any other error as `"event":"request_error"` with the request's `cf-ray`, and shows the same requests the error page with a 500, with one way back (the network's dashboard on a network's page, the networks on another of the app's, home elsewhere), the `cf-ray`, and no card; everything else, and a page whose error page fails too (`"event":"error_page_failed"`), gets a plain `500 Internal Server Error`. Their illustrations use made-up shows and say so where they appear; never put a Qloo response, a sample network show, or an invented customer, quote, figure, or price on them (`test/marketing.test.ts` checks the first two). The terms read the daily limits from `env` and the per-run and inbox limits from `src/limits.ts` and `src/inbox.ts`, so they can't drift from the code.

A tool has a strict definition, the progress note it shows, and `run`, which reaches Qloo through `context.qloo` and returns an error that says what to do next. A tool whose note counts what earlier calls stored, such as `draft_replies`, also has `asIfStored`, for the notes of the calls the turn limit skips.
- `src/gateway.ts`: `QlooGateway`, the only code that calls Qloo: the global instance (`globalGateway(env)`) on `QLOO_API_KEY` and `QLOO_BASE_URL`, and an instance per network that brings its own key, `network:<networkId>` (ADR 0004), which keeps the key sealed with AES-GCM under `QLOO_KEY_SECRET` (`setKey`, which tests it with one search first, `ownKey`, which never returns it, and `wipe`), its host, its own cache, and its own Qloo counts. Model runs and the sample run stay in the global instance. The agent reaches its gateway through `gateway()`: the global one on an engine session, and on a network's or launch's agent `networkGateway` (`src/network-agent.ts`), the network's own instance while the agent knows the network has a key (`hasOwnKey`, kept in the agent's own storage), with no call to the gateway to ask, so a network without a key never has an instance. A wiped instance resets, which breaks every stub to it, so take a new stub (`getByName`) for each call after a wipe. From the start of its wipe until it resets, it touches no storage: every call still out, or reaching it, fails saying the key was removed (`WIPED`). Its reset says `WIPED` too, or `WIPE_FAILED` when the wipe fails (`awaitWipe` in `src/wipe.ts`). It also keeps the stored sample run, and `health()` says whether Qloo can be called: not once the day's cap is reached, nor for five minutes after a request fails after its retries, unless one succeeds since. Each method returns its data or error together with an evidence record. Every request goes through `request`, which sends GET parameters in the query string and POST ones as a JSON body of flat dotted keys, serves the shared cache, enforces the daily cap, paces and limits requests to 3 in flight, and retries; a new endpoint goes through it too. A call can skip the cache or read only from it, as the health check does. It also keeps the per-visitor daily counters, sign-ups among them (`admitSignup`, against `SIGNUP_VISITOR_DAILY_CAP`), and `usage(visitor)` reads a visitor's or a network's Qloo calls and model runs today against their limits.
- `src/evidence.ts`: the evidence record's shape. Fill its fields; don't reshape it.
- `src/resolve.ts`: deciding whether a search result is the named entity: a roster show by name, a pitched work by title, then its author or year.
- `src/demographics.ts`: the demographic check's derived values and its thresholds, built from one demographics call: the launch profile and each finalist's mismatches in words. Read `state.demographics`. Its rules (`skewOf`, the thresholds) and the demographic figure's one format (`demographic`, which `src/client/controls.tsx` re-exports for the island) also serve the listener profile.
- `src/order.ts`: the insertion order's pricing, shared by the agent and the UI's live totals: slot values from downloads and CPM, the gaps a missing figure leaves, the line checks, and the CSV export. A line's angle is null for a finalist with no shared tags (#216): `draft_insertion_order` refuses to draft before `shared_tags` has compared the finalists, and refuses an angle for one Qloo returned no tags for, while an edit may leave such a line empty (`angleOptional`) or give it the programmer's own words; a finalist never compared, as one an exclusions answer promoted, needs the programmer's own. The CSV gives a line with no angle `NO_ANGLE`. The `draft_insertion_order` tool stores the run's draft; the `editInsertionOrder` and `approveInsertionOrder` actions are the programmer's alone, and `GET /app/:networkId/launches/:launchId/insertion-orders/:id.csv` calls the launch agent's `exportInsertionOrder` and answers with `csvDownload`. Approval needs the page's connection, so no RPC caller can approve (ADR 0002); on a launch's agent the connection must carry a member, and the order records their name and the time (`approvedBy`, `approvedAt`) until it returns to draft. An edit that changes its lines or prices, or a new figure that prices it anew, marks it `edited`, so the app, the API, and the MCP server say its run's closing line may quote figures it no longer has (#202).
- `src/fit.ts`: the fit ranking's derived values, built from one ranking call: which roster shows are scorable, fit rank, band, leading comp, finalists, and each other show's reason for not being scored. Later tickets read `state.ranking` for finalists and leading comps. It also builds each pitch list, one per work type, which `rank_pitches` puts in `state.booking.lists`, gives its rows their pitch ranks and moves once the pitch ranking is in (`withPitchMoves`, whichever of the two lands last), and words each list's finding (`pitchFinding`). `tagged(sharedTags)` says whether a compare returned tags to build an angle from, and `NO_ANGLE` is what the app, the MCP server, and the CSV say when it didn't; `draft_insertion_order`, `draft_replies`, and the order's line checks all go by `tagged`, and both drafting tools refuse until `shared_tags` has run.
- `src/overlap.ts`: the roster's overlap, what it is and the pure functions every surface reads it through: the roster's distinct matched entities, sorted by ID (`rosterEntities`), the entity-set key and whether it's stale (`isStale`), what a measure asks (`toMeasure`), how many closest shows each show has (`closestCount`), an anchor's closest shows from its ranking (`closestOf`), and the close pairs (`closePairs`), which every later surface that names a pair reads; the roster's shows by entity, in roster order (`entityShows`), the shows among no other's closest (`apart`), an anchor's whole ranking from its call's evidence (`rankingOf`), and what a roster of under four needs (`tooFew`). `NetworkAgent.measureOverlap` measures it, and `src/operations.ts` reads it for programs.
- `src/listeners.ts`: the roster's listener profile, what it is and how every surface reads it: what a profile asks (`toProfile`), each entity's row from the demographics call (`rowsOf`), the roster's shows in its order with what the profile has for each (`rosterRows`, which the Listeners tab and `src/operations.ts` both read), what a show's leans count for by the demographic check's rules (`counted`), what the profile finds and which shows lean differently (`listenerShape`), the finding the Listeners tab and the MCP tools share (`listenerFinding`, naming up to `NAMED_APART` of those shows), and a show's leans in words (`leanWords`). It shares the overlap's entities, entity-set key, staleness, and minimum (`src/overlap.ts`). `NetworkAgent.profileListeners` makes it, and `src/operations.ts` reads it for programs.
- `src/roster.ts`: reading an imported roster, pasted names or a CSV, into rows, and saying which figures it brings.
- `src/upload.ts`: turning uploaded files into what the agent takes, for the browser and the API alike: `readRosterUpload` reads one `.csv` or `.txt` file into roster text and its format, and refuses another type, more than one file, an empty file, or one over `MAX_UPLOAD_BYTES` (5 MB) before reading it. `readPitchUpload` reads `.eml` files (with `postal-mime`, from their bytes, so each part keeps its charset; it's imported as the first email is read, so the island's pages that only take a roster file don't load it), an `.mbox` export, split into its emails, or a `.txt` split on lines of dashes, into pitches of sender, subject, and plain-text body, HTML-only mail as its text, and refuses another type, an empty or oversized file, or a file with no pitch in it. `loadInbox({ pitches })` takes its result. Each refusal is a `Refusal`, `too_large` for the size and `unreadable` for the rest. The API wraps a request body as an `Upload` named by its `Content-Type`; a body that sends `Content-Length` is sized by it, so an oversized one is refused unread, and one that doesn't is read first.
- `src/sample.ts`: the sample network the guest network loads, which any empty roster can start from, read from `src/sample-network.json`, with its suggested answers to the run's questions.
- `src/sample-launches.ts`: the guest network's sample launches (ADR 0007): `keptRun`, what the stored sample run and the run each of the sample launches is seeded with (`CapturedRun`) keep of a run, and `readSampleLaunches`, which reads the captured runs back from `sample_launches`' rows (`sampleLaunchRows` in `src/directory.ts`). Capturing them isn't the Worker's, so it's in `test/capture.ts`, which the capture script and `test/sample-launches.test.tsx` share: `capturedRunOf`, a launch's one run as a captured run, and `sampleLaunchesSql`, the SQL that loads them into `sample_launches`. `NetworkAgent.loadSampleLaunches` lists them on the guest network's start, each seeded with `LaunchAgent.seed`, which `CrossfeedAgent.seedRun` does as the replay does. `scripts/capture-sample-launches.ts`, at the repo's root, captures them ([Sample launches](#sample-launches)).
- `src/inbox.ts`: the inbox's types, the sample inbox already read (`readSampleInbox`), reading pasted pitches or uploaded pitches into rows (`headed` reads the `From:` and `Subject:` lines atop a pasted or `.txt` pitch as its sender and subject, for the paste and `src/upload.ts` alike; an uploaded pitch with no text or over `MAX_PITCH_CHARS` is skipped and named in `inbox.skipped`, the rest load), and reading the past guests a pitch run ranks against. `loadInbox` returns at once and reads the pitches in the background, five at a time.
- `src/extract.ts`: the pitch reader, one structured-output call per pitch. Single model calls beside the agent loop, such as the topic baseline, use `structured` from `src/claude.ts`.
- `src/topic.ts`: the topic baseline, one structured-output call per run that `startLaunch` starts beside the agent loop, cached in the agent by a hash of its request, and the topic moves `withMoves` works out from it and the fit chart, whichever lands last. It and the pitch ranking make their call with `rankNames` from `src/claude.ts`, which checks the answer ranks every name once.
- `src/pitch-ranking.ts`: the pitch ranking, its counterpart for a pitch run: one structured-output call that `startPitches` starts beside the agent loop, from each pitch's subject and opening, never its sender, cached in the agent by a hash of its request. The pitch ranks, moves and findings it gives the lists are `src/fit.ts`'s, so the inbox page imports them without this module's model call.
- `src/client/`: the React island. `main.tsx` renders `Account.tsx`'s sign-in page (`data-page="sign-in"`, with `data-next`, `data-runs`, and `data-guest-refused` when a guest button was refused), `NewNetwork.tsx` (`data-page="new-network"`, with `data-cap`), `Dashboard.tsx` (`data-page="dashboard"`, with `data-invited` for the checklist, `data-usage` and `data-own-key`, today's usage as settings read it, and `data-usage-read`, when the server read it, `data-keys`, the API keys' use, either left out when its read failed, and `data-notice` as a reset of the sample data that's still finishing opens it), `Launches.tsx` (`data-page="launches"`), `Launch.tsx` (`data-page="launch"`, `App.tsx`'s `Workspace` with the network, its roster read-only), `Roster.tsx` (`data-page="network-roster"`), `NetworkInbox.tsx` (`data-page="network-inbox"`), `Developers.tsx` (`data-page="developers"`, with `data-mcp-url` and `data-api-url`, the addresses on the app's own origin, `data-keys`, an owner's keys in use with no secret or prefix, `data-owners`, the owners' names, and `data-tools`, the MCP server's tools by kind; its playground, `Playground.tsx`, reads `/api/v1/openapi.json` once its tab first shows, and builds its requests, their curl commands and the tab's last requests with `requests.ts`, which has no React in it), or `Settings.tsx` (`data-page="settings"`), each told the network, the member's role, whether it's on the guest budget (`data-guest-budget`), and its links by data attributes. `main.tsx` loads each page's module with a dynamic `import()` before it renders it, so the build splits the island into a chunk per page, and a page loads only its own code and the shared chunks, which the shell's `Island` preloads: a new page goes in `main.tsx`'s `pages` and in `shell.tsx`'s `pageModules`.
