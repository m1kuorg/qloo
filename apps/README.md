# Crossfeed app

The Crossfeed Worker: a Hono app with a React island, a `CrossfeedAgent` per visitor session, a global `QlooGateway`, and the D1 directory of members and networks, on Cloudflare Workers. It's deployed at <https://crossfeed.m1kuorg.workers.dev>. This is the how-to every ticket follows; [TRD.md](/docs/TRD.md) holds the design.

## Set up

Run these in `apps/`, with `QLOO_API_KEY` and `ANTHROPIC_API_KEY` in your environment:

```sh
bun install
printf 'QLOO_API_KEY=%s\nANTHROPIC_API_KEY=%s\nVISITOR_SALT=%s\nGUEST_PITCHES=on\nRP_ID=localhost\nAPP_ORIGINS=http://localhost:5128\n' "$QLOO_API_KEY" "$ANTHROPIC_API_KEY" "$(openssl rand -hex 16)" > .dev.vars
bunx wrangler d1 migrations apply DB --local
```

`.dev.vars` is git-ignored. Never commit it, a key, or a Qloo response. `VISITOR_SALT` salts the hash that keys a visitor's model run count; any random value works locally. `GUEST_PITCHES=on` shows the guest pitch flow, as `wrangler.jsonc` does in production since #57; `off` hides it. Tests run with it off, and a test of the flow sets `env.GUEST_PITCHES = 'on'` itself. `ACCOUNTS` is `off` in `wrangler.jsonc`, which hides accounts and every link to them, such as the demo's "Create your network"; add `ACCOUNTS=on` to `.dev.vars` to work on them. The landing page offers "Create your network" and "Sign in" only while it's on. Tests run with it on, and a test of the demo without accounts sets `env.ACCOUNTS = 'off'` itself. `RP_ID` is the passkey relying party's ID and `APP_ORIGINS` the comma-separated origins a member's browser may send from. `wrangler.jsonc` sets them to each environment's host, so locally they're `localhost` and the dev server's origin: use the port you run it on.

A member's session cookie is `__Host-crossfeed_member`, which is always `Secure`. Chrome keeps a `Secure` cookie from `http://localhost`, as it treats localhost as a secure origin, so signing in works on the dev server over plain HTTP, checked in Chrome 155. Other browsers weren't checked, so check accounts locally in Chrome.

`bunx wrangler d1 migrations apply DB --local` creates the D1 directory's tables, from `migrations/`, in the dev server's local copy of the database under `.wrangler/state`. Run it again after pulling a new migration.

After changing `wrangler.jsonc`, run `bun run cf-typegen` to regenerate `Env` in `worker-configuration.d.ts`.

The rate limits (`ratelimits` in `wrangler.jsonc`: `API_LIMITER`, 120 requests a minute per API key, and `AUTH_LIMITER`, 20 a minute per visitor on the auth routes that write before anyone signs in) run in the dev server and the tests too, simulated by Miniflare with the same limits and fixed one-minute windows. A request with no `CF-Connecting-IP`, as in the tests unless one sends it, isn't counted per visitor.

## Run locally

```sh
bun run dev -- --port 5128 --strictPort
```

Ticket `#n` uses port `5100 + n`, so parallel worktrees don't collide. The dev server calls the real Qloo API with the key in `.dev.vars`. Stop the server when you're done.

## Test

```sh
bun run test
```

Tests run in the Workers runtime through `@cloudflare/vitest-plugin`, configured in `vitest.config.ts`. The Worker and its Durable Objects run in the tests' isolate. Tests drive the public interface only: the Worker's HTTP routes and the agent's client protocol, asserting on synced state and responses.

### The fake HTTP seam

Outbound HTTP is the one seam. `test/fake.ts` holds the fakes, which [`@msw/cloudflare`][msw-cf] serves by intercepting `fetch` inside the runtime. `QLOO_BASE_URL` points at `https://qloo.test` and `ANTHROPIC_BASE_URL` at `https://anthropic.test` in tests, and a request no fake serves fails the test.

- `fakeQloo({ search })` serves `/search` from hand-written results keyed by query. A number in place of results answers with that HTTP status, `{ status, body }` answers with that raw body, such as a proxy's HTML error page, and `'hang'` never answers, so the gateway times out.
- `fakeQloo({ search, first: { 'Deep Cuts': [503, 503] } })` answers a query's first requests from `first`, in order, then from `search`. `latencyMs` delays every answer.
- `fakeInsights(answer)` serves `POST /v2/insights` rankings: a list of `{ entity_id, name, affinity, explainability }`, an HTTP status, or a function of the request's flat-key body that returns either. Left out, `explainability` splits each score evenly across the request's anchors; `null` leaves it off the result.
- `fakeQlooDown(status)` answers every Qloo request, on any endpoint, with that status, as when Qloo is down. Registered after the other Qloo fakes, it overrides them; register them again to bring Qloo back.
- `fakeCompare(answer)` serves `GET /v2/analysis/compare` from shared tags keyed by side `b`'s entity ID: a list of `{ tag_id, name, score }` in Qloo's order, or an HTTP status. A side `b` with no entry shares no tags, and `{ latencyMs }` delays every answer.
- `fakeDemographics(answer)` serves `POST /v2/insights` demographics requests, those with `filter.type=urn:demographics`: the entries of a list of `{ entity_id, age, gender }` whose entity the request names, in the list's order as Qloo answers in no set order, or an HTTP status. `fakeInsights` leaves those requests to it, so the two can be registered in either order.
- `requests` records every request a fake served, in order, with the time it arrived (`at`) and how many Qloo requests were in flight (`inFlight`). `test/setup.ts` clears it after each test.
- `test/session.ts` wipes every Durable Object after each test, so the gateway's shared cache and daily count start empty. Keep `cloudflare:test` out of `test/setup.ts`: imported there, it crashes the next test file's worker when files share one, as on CI.
- The wipe takes D1 with it, so `test/session.ts` applies the directory's migrations again before each test, with `applyD1Migrations` on `env.DB`. `vitest.config.ts` reads them from `migrations/` with `readD1Migrations` into the test-only `TEST_MIGRATIONS` binding. A test file that uses D1 imports `./session`. Only storage tests read D1 directly: `test/directory.test.ts` checks the schema, `test/auth.test.ts` checks that only hashes of tokens and codes are kept and that the cron purges expired rows, and `test/api-keys.test.ts` that only an API key's hash and prefix are. Every other test reaches the directory through the Worker's routes.
- Tests run with `RP_ID` `crossfeed.test` and `APP_ORIGINS` `https://crossfeed.test`, the origin `test/session.ts` sends from, and with the sign-up and network caps at `wrangler.jsonc`'s values, whatever `.dev.vars` says.
- Tests run with a 1-second Qloo timeout, retry delays of 10 and 30 ms, and no pacing (`vitest.config.ts`). A test that needs another value assigns it to `env` from `cloudflare:workers` and restores it afterwards, as `configure()` in `test/gateway.test.ts` does.
- Tests run with `SAMPLE_NETWORK` off, so a new session starts with an empty roster and makes no Qloo calls of its own. `test/sample.test.ts` turns it on to test the sample network.
- `fakeClaude(script)` is the scripted model. Each Messages API request gets the next turn, streamed as the API streams it, after an empty thinking block like Haiku 5.5's. Build turns with `turn(toolUse(name, input), text(...))`, which ends in tool calls if it has any, or `refusal(category)`. Tool use IDs are `toolu_<turn>_<block>`. A script entry can be an async function of the request, to hold a turn while the test looks at a running run. A request past the end of the script gets a 400.
- `modelRequests()` returns the body of every request the scripted model got, to check model settings and history.
- `fakeReader(count, answer)` scripts the model's reading of `count` pitches, each answer (`{ guest, work }`) chosen by `answer` from the pitch's text, so pitches read at once can be answered in any order. `test/emails.ts` holds synthetic pitch emails, one per kind a mail client sends (plain, HTML-only, multipart with an attachment), and an `.mbox` of them, for the app's upload and the API alike.
- `qlooRequests()` returns each request Qloo got as Qloo reads it, its path, every decoded parameter, and its body, lowercased, to check that a guest's name or a sender never reaches Qloo (`test/network-inbox.test.tsx`, `test/api-inbox.test.ts`).
- A run's topic baseline request doesn't take a scripted turn, and `modelRequests()` leaves it out. `fakeClaude` answers it from `fakeTopic(answer)`: show names in topic order, a scripted turn such as `refusal(...)`, an HTTP status, or a function of the request, which can hold its answer. By default it ranks the shows in the order the request lists them, `topicNames(request)`. `topicRequests()` returns each baseline request's body.
- To run the daily cron, call the Worker's `scheduled` handler with `createScheduledController()` and `createExecutionContext()` from `cloudflare:test`, as `test/health.test.ts` does, and spy on `console.log` and `console.error` for its log lines.
- Add a fake for a new endpoint or API to `test/fake.ts` the same way.

Fixtures are synthetic: made-up names, IDs, and scores. Never paste a real Qloo response into a test.

[msw-cf]: https://developers.cloudflare.com/workers/testing/vitest-integration/mock-outbound-requests/

### Driving a session

`openSession()` in `test/session.ts` is a visitor. It loads `/demo` for a session cookie, then opens the agent's WebSocket the way `useAgent` does:

- `call(method, ...args)` calls a `@callable` action and resolves with its result, after the state it set has arrived.
- `importRoster(text, format?)` imports a roster and resolves once every show's search has settled. `call('importRoster', ...)` resolves as soon as the shows are pending, before any search returns.
- `searchComps(name, query)` searches for a comp and resolves once the search has settled; `call('searchComps', ...)` resolves while it's still pending.
- `state()` is the latest synced state, and `until(ready)` waits for synced state that passes `ready`, such as a finished run.
- `frames()` is every raw frame the server sent, which is everything the visitor's browser receives.
- `openSession(cookie)` reconnects as the same visitor, like a reload; `openSession()` is a new visitor.

A test that renders a page of the island from a session's state, such as `Workspace` from `src/client/App.tsx`, passes it `links` from `test/session.ts`, the links the demo gives its pages.

### Driving a member

`openMember()` in `test/session.ts` is a member, signed up the way the sign-in page does it: it asks `/auth/sign-up/options` for a new passkey's options, has the software authenticator make the passkey, and sends it to `/auth/sign-up`.

- `openMember({ name, ip })` signs up a new member, named `Ada Programmer` unless you name them. `ip` is their address, as `CF-Connecting-IP`; without one, the sign-up cap doesn't apply.
- `openMember({ name, invite })` signs up through an invite link instead, as its invite page does, joining the link's network in the same step; `network` is the network they joined, null without an invite.
- `cookie` is their session cookie as the browser sends it back, and `recoveryCode` the code shown at sign-up.
- `id` is their member ID, read from the passkey's user handle in the sign-up options.
- `fetch(path, init)` is a request from the member's browser: it carries their cookie, and on a write the app's `Origin`, which every cookie-authenticated write needs.
- `connect(path, headers)` opens an agent's WebSocket from one of the app's pages, such as a network's at `/agents/network/<id>`, with their cookie and the app's `Origin`, and returns the same `call`, `state`, `until`, and `importRoster` as a session, plus `closed()`, which resolves with the close code and reason once the server closes it.
- `invite(network)` makes an invite link to a network the member owns, as its settings do, and returns the link, with its token in the fragment.
- `authenticator` holds the member's passkey, to sign in again through `/auth/sign-in/options` and `/auth/sign-in`.

A member's account is theirs to change through `/app/account`'s routes, as `test/account.test.ts` does: `POST /app/account/name`, `/app/account/recovery-code`, `/app/account/sign-out-everywhere`, `/app/account/delete`, and `/app/account/passkeys/<id>/remove`. A passkey is added through the ceremony's two requests, `/auth/passkeys/options` and `/auth/passkeys`, answered by another `softwareAuthenticator()`, as another device would; the account page's `data-passkeys` lists them. `test/account-page.test.tsx` renders the account page from its data attributes. Deleting a network is an owner's `POST /app/<id>/settings/delete` with its `name`; `test/delete-network.test.ts` reads its agents over RPC to check they were wiped, and makes a wipe fail by mocking `NetworkAgent.prototype.destroy` or `LaunchAgent.prototype.destroy` once.

A member creates a network by posting its name to `/app/new`, as `test/networks.test.ts` does. A second member joins it through the real invite flow: `await openMember({ name: 'Grace Booker', invite: await ada.invite(network) })` for a new person, or a signed-in member posting the link's token to `/auth/join`, as `test/members.test.ts` does. Nothing reads or writes D1 outside the directory module. `test/dashboard.test.tsx` renders the dashboard and settings from a network agent's synced state and the data attributes the server gave the page, and `test/network-roster.test.tsx` the roster page.

A launch is planned on the network's agent, as the dashboard's "New launch" does: `call('createLaunch', { name })` or `{ comps }` returns its `{ id }` and adds it to the synced `launches` list. Its page's agent is then `connect('/agents/launch/<networkId>/<launchId>')`, with the same `call`, `state`, and `until`; a run started there copies the network's roster, so import and settle the roster on the network's agent first. `test/launches.test.tsx` drives launches this way, and renders the dashboard and a launch's page (`LaunchWorkspace` in `src/client/Launch.tsx`) from their agents' synced state.

Approving an insertion order takes the page's connection: a test calls `approveInsertionOrder` over `connect`, and checks that an RPC call, as the API would make, is refused. On a launch's agent the connection must carry a member, so a connection sent straight to its stub with `connect(path, {}, via)` is refused too (`test/launches.test.tsx`). Deleting a launch is a member's `POST /app/<id>/launches/<launchId>/delete`; `test/launches.test.tsx` makes a wipe fail by mocking `LaunchAgent.prototype.destroy` once (the agents run in the tests' isolate) and runs the cron with fake `Date` timers a few minutes on. A wiped agent's instance is reset a moment after its wipe, so read it with `vi.waitFor`.

Some of a network agent's callers have no connection, such as the API and a launch's agent asking its network for the roster as a run starts (`rosterForLaunch`) and reporting its summary back (`reportLaunch`). A test calls the agent as they will, over RPC, with `(await getAgentByName(env.NetworkAgent, networkId)).importRoster(...)` (`getAgentByName` from `agents`), as `test/network-roster.test.tsx` does to check such calls count against the network. Wrap an RPC call in an `async` function before `expect(...).rejects`, as `test/network-inbox.test.tsx` does: Vitest can't read the RPC promise itself. To read a roster file as the roster page does, pass `File`s to `readRosterUpload` from `src/upload.ts` and import its result over the agent; for pitch files, pass them to `readPitchUpload` and load `{ pitches }` with `loadInbox`.

`connect(path, headers, via)` in `test/session.ts` opens an agent's connection the way `useAgent` does. Its upgrade goes to the Worker unless `via` sends it elsewhere: `test/network-inbox.test.tsx` sends it straight to a network agent's stub, as a Worker route that let it through unchecked would, to check that a connection with no member can't approve a reply.

`softwareAuthenticator()` in `test/authenticator.ts` stands in for a browser's platform authenticator. `register(options)` answers `navigator.credentials.create()` with an ES256 passkey and "none" attestation. `authenticate(options)` answers `navigator.credentials.get()` with a discoverable passkey it holds for the relying party, flagged user present and user verified, with a signature counter of 0, as synced passkeys send. Both answer from `https://crossfeed.test` unless a test passes another origin. `softwareAuthenticator({ userVerified: false })` can't verify the person, as a security key without a PIN. `test/auth.test.ts` drives each ceremony step by step, for tests of the ceremonies themselves.

### Driving the API

`api(secret)` in `test/session.ts` is a program with an API key: it sends `Authorization: Bearer <secret>` and no cookie or `Origin`, as `curl` does, and returns a `fetch(path, init)`. An owner makes the key the way the settings page does, by posting `{ name }` to `/app/<id>/settings/api-keys` with `member.fetch`, which answers the secret once (`test/api-keys.test.ts`, `test/api.test.ts`). `networkWithKey(member?)` does both for a new network and returns `{ ada, network, secret, call }`, `call` being the key's `fetch`. `member.fetch('/api/v1/...')` is the same member's session instead, with the app's `Origin` on writes.

- Long work answers 202 with the resource's current status, so a test polls the resource until it settles, as a program does: `poll(call, path, ready)` in `test/session.ts` reads `path` until its JSON passes `ready` (`settled` in `test/api.test.ts` predates it). A fake answering at once may settle before the 202 is written; `fakeQloo({ latencyMs })` keeps the work pending long enough to see it.
- Every refusal is `{ error: { code, message } }`; assert both. A new endpoint goes in `src/routes/api.ts` with its zod schemas, and `test/api.test.ts`'s OpenAPI test fails until it's in the document. Its examples must use made-up shows: the same test checks the document names nothing the demo looks up in Qloo.
- A run started through the API, such as a pitch run (`test/api-inbox.test.ts`), is polled the same way until it's done or waiting on its question. To see a run's 202 while it's still running, hold its first scripted turn with a promise the test releases once it has read the answer: `() => held.then(() => turn(...))`.
- A launch's run through the API (`test/api-launches.test.ts`) ranks a roster the test first imports, settles, and prices through the API too. Approval stays the app's: the test approves an order over the member's own launch connection, `ada.connect('/agents/launch/<networkId>/<launchId>')`, then exports it through the API. Deleting a launch through the API takes the member's session (`ada.fetch`); `ada.fetch` always sends the app's `Origin`, so a cross-site write is sent with `exports.default.fetch` and the cookie by hand.
- The inbox and pitch run routes need `GUEST_PITCHES` on, as the page does: a test turns it on in `beforeEach` and off again after.
- The rate limits count in fixed one-minute windows that the per-test reset clears. A test of a limit sends requests until one is refused, up to twice the limit and two more, since a window can roll over mid-test (`untilRefused` in `test/api-keys.test.ts`).

### Driving the SDK

`test/sdk.test.ts` drives the Worker through the TypeScript SDK in [`packages/sdk`](/packages/sdk/README.md), imported from its source, as a program using it would. `client()` there makes a network and its key with `networkWithKey` and returns `crossfeed`, a `Crossfeed` client whose `fetch` is `exports.default.fetch`, so its requests reach the Worker in the tests' isolate. Its wait helpers poll as they do for a program; give them `{ interval: 10 }` so a test doesn't wait a second between reads. Approval stays the app's, through the member's launch connection, as in the API's tests.

- A refusal rejects as a `CrossfeedError`; `refusal(call)` there returns its `code`, `status`, and `message` to assert, failing the test if the call succeeds.
- "reach every route the OpenAPI document describes" calls each of the SDK's methods once and fails while a documented route has no method. A new API route needs its method in `packages/sdk/src/index.ts` and a call there.
- "match the OpenAPI document the Worker serves" fails once the API's document differs from `packages/sdk/openapi.json`, and "are generated from that document" once the SDK's types weren't generated from it. After changing the API, run `bun run generate` in `packages/sdk`, which writes the document and regenerates the types, then commit both.

## Check types

```sh
bun run typecheck
```

`apps/` typechecks with TypeScript 7. The repo root installs TypeScript 5 for `openapi-typescript`, which needs the compiler API that TypeScript 7 dropped, so run `openapi-typescript` from the root. `packages/sdk` typechecks with its own TypeScript 5: run `bun run typecheck` there. `apps/` typechecks the SDK's source too, as its tests import it.

Client files under `src/client/` use React JSX. Server files that render the HTML shell use Hono JSX and start with `/** @jsxImportSource hono/jsx */`.

## CI

[`.github/workflows/ci.yml`](/.github/workflows/ci.yml) runs on every pull request, including a retitle, and on every push to `main`. One job installs the repo root, `apps/`, and `packages/sdk` with `bun install --frozen-lockfile` (the SDK without its build script), then runs these steps. Each step runs even when an earlier one fails, so one run reports every failure:

1.  **Format:** `bun run lint` at the repo root, Prettier's check.
1.  **Typecheck:** `bun run typecheck` in `apps/`.
1.  **Typecheck SDK:** `bun run typecheck` in `packages/sdk`. Format covers its files with the rest of the repo, but for its generated `openapi.json` and `src/openapi.ts`.
1.  **Test:** `bun run test` in `apps/`.
1.  **PR title:** the title through `bunx commitlint`, on pull requests only.
1.  **Secrets:** `gitleaks git` on the commits the pull request or push adds.

Before merging, wait for green with `gh pr checks <pr> --watch`. Locally, run the listed commands where they're listed, check a title with `echo '<title>' | bunx commitlint` at the repo root, and check your commits with `gitleaks git --log-opts="origin/main..HEAD"`.

## Deploy

Deploy only from an up-to-date `main`, and only one deploy at a time:

```sh
git fetch origin main && git checkout --detach origin/main
cd apps && bun install && bun run deploy
```

`bun run deploy` builds, applies the directory's new migrations to the `crossfeed` D1 database (`wrangler d1 migrations apply DB --remote`, which lists them and asks before applying), then deploys the `crossfeed` Worker.

Secrets live on the `crossfeed` Worker in the `qloo` Cloudflare account, and are set once with `bunx wrangler secret put QLOO_API_KEY`, `ANTHROPIC_API_KEY`, and `VISITOR_SALT` (a random value, such as `openssl rand -hex 32`; changing it restarts every visitor's count). List them with `bunx wrangler secret list`.

### Deploy the preview

The `preview` environment in `wrangler.jsonc` is a separate Worker, `crossfeed-preview`, at <https://crossfeed-preview.m1kuorg.workers.dev>, with its own D1 database (`crossfeed-preview`), Durable Objects, and secrets, and with `ACCOUNTS` on. Merged work is checked there before it reaches production. Deploy it the same way, from an up-to-date `main`:

```sh
cd apps && bun install && bun run deploy:preview
```

`bun run deploy:preview` builds with `CLOUDFLARE_ENV=preview`, applies migrations to `crossfeed-preview`, and runs `wrangler deploy --env preview`. Don't run `bunx wrangler deploy --env preview` by hand after `bun run build`: the Vite plugin picks the environment when it builds, and Wrangler deploys whatever the build was for, production included. `bunx wrangler deploy --env preview --dry-run` after `CLOUDFLARE_ENV=preview bun run build` shows what would deploy without deploying. `wrangler secret` and `wrangler d1` read `wrangler.jsonc` itself, whatever was built, so `--env preview` is enough for them.

Wrangler can't set secrets on a Worker that doesn't exist yet, so the first deploy takes them from a file: write `QLOO_API_KEY`, `ANTHROPIC_API_KEY`, and a new `VISITOR_SALT` as `NAME=value` lines to a file outside the repo, run `bun run deploy:preview --secrets-file <file>`, and delete the file. Afterwards, set and list them with `bunx wrangler secret put <NAME> --env preview` and `bunx wrangler secret list --env preview`. `bunx wrangler d1 migrations list crossfeed-preview --env preview --remote` lists the migrations not yet applied.

## Live check

Done means the behaviour works against the real APIs, first locally and then on <https://crossfeed.m1kuorg.workers.dev>, checked by hand or with `playwright-cli`:

1.  Open `/` in a fresh browser session and select the landing page's first button, "Open the sample network", which opens `/demo`. It opens on the sample network from `src/sample-network.json`: the top bar says "The Ringer · sample network" and "Sample data · not affiliated with The Ringer", every downloads, status, description, and CPM figure has a sample label beside it, and the launch field holds "The Watch", labelled "Sample launch". Every row says "Looking it up in Qloo…", then fills in as its search returns, within a few seconds when the gateway's cache is warm.
1.  Expect 16 resolved, Binge Mode ambiguous with its candidates, and The Zach Lowe Show and The Press Box missed. A "Lookup failed" row means Qloo still failed after the gateway's retries, or the daily cap was reached; its reason is in the row.
1.  Select Binge Mode and pick one of its candidates. Select The Zach Lowe Show, search for a comp such as The Lowe Post, and map it. Leave out The Press Box. Change a show's downloads: that figure loses its sample label.
1.  Reload: the roster and the edits stay. A private window opens on a fresh sample network.
1.  Type "The Big Picture" as the released launch and start a run. The header shows "Running" and "Resolving The Big Picture", then the Qloo match with its call number, and "Completed". The rail's Run module lists the progress notes as done.
1.  The fit chart ranks the other scorable shows by position and band, with the top five marked Finalist. Under "Not scored" it lists The Big Picture as the launch, The Press Box as excluded, and any show still unsettled. Open the chart's call number: the evidence holds the anchor and candidates in its parameters and each show's raw affinity, which the chart never shows.
1.  The run stops at "Waiting on you", and the agent's question, atop the rail, asks for the slot budget. Reload: the question stays. Answer with a slot count or a dollar amount. The next question asks which shows to leave out of this launch, in fit order: tick a finalist and answer. The chart drops its Finalist mark and gives it to the next show by fit, the header shows "Completed", and the Run module lists the budget and the shows left out.
1.  Run the sample launch, The Watch, the same way, leaving no show out. The Run module lists "Checking demographics of 5 finalists against The Watch". Above the chart, the Demographics line cites its call, says The Watch's listeners over-index at ages 35 to 44 and skew male, and says how many finalists' listeners differ, or that there are no mismatches. The Bill Simmons Podcast is marked "Listeners differ", with the reason under its name, and stays a finalist; in a run that leaves it out, The Town with Matthew Belloni is marked instead. Poll `GET .../launches/<launchId>/runs/<runId>` until it's `waiting` on a `question` or done; answer each with `POST .../runs/<runId>/answer` and the fields its kind takes (`{"questionId": …, "slots": 20}` for a budget, `{"exclude": []}` for exclusions, `picks` from the plan's comp `candidates` for `confirm_comps`). `GET .../launches/<launchId>` reads the latest run in full: the chart's ranks, bands, and moves, the topic baseline, the demographics flags, and the draft order, as the launch page shows them. `PATCH .../insertion-orders/<orderId>` with `{"lines": […]}` edits the draft, and `{"status": "approved"}` is a 400. `GET .../insertion-orders/<orderId>/csv` answers 409 `conflict` until a member approves the order on the launch page, then the CSV the page exports. `GET .../launches/<launchId>/evidence` lists a record for every call number the run cites. `DELETE .../launches/<launchId>` with the key answers 403 `forbidden`; deleting is the dashboard's.
1.  Through the SDK: build it with `bun install` in `packages/sdk`, add it to a scratch project outside the repo with `bun add <repo>/packages/sdk`, and run a short Bun script with the key, the network's ID, and `baseUrl: 'http://localhost:<port>'`, as [its README](/packages/sdk/README.md) does: import a roster and `waitForRoster`, create a launch, start a run and answer each question `waitForRun` stops on, until the run is `completed` with a draft order; `insertionOrders.exportCsv` rejects with a `CrossfeedError` `conflict` 409 until a member approves the order on the launch page, then resolves with the page's CSV. Load pitches, `waitForInbox`, start a pitch run on a matched show, and `waitForRun({ pitchRunId })` to its replies. The dashboard, launch, and inbox pages show what the script did.
1.  Another network's ID answers 404 `not_found`, no key 401 `unauthorized`, and past 120 requests in a minute the key answers 429 `rate_limited` with `Retry-After: 60`. "Revoke" asks first; once revoked, the key's next request answers 401. `/api/v1/openapi.json` is the OpenAPI 3.1 document of every route.
1.  `POST /auth/sign-in/options` 21 times in a minute with one `CF-Connecting-IP` answers 429 the 21st time; another address still gets through.

The dev server prints a Local Explorer API; `POST http://localhost:<port>/cdn-cgi/local/explorer/api/d1/database/8c6c6a5e-3f49-46f5-a5d1-32adb53f0cba/raw` with `{"sql": "..."}` runs SQL on the dev server's D1.

To cap the deployed Worker without a code change, deploy from up-to-date `main` with `bunx wrangler deploy --var QLOO_DAILY_CALL_CAP:0` (after `bun run build`), check, then `bun run deploy` again to restore `wrangler.jsonc`'s cap. `--var RUN_VISITOR_DAILY_CAP:n`, `--var RUN_DAILY_CAP:n`, `--var FREE_START_DAILY_CAP:n`, and `--var QLOO_VISITOR_DAILY_CALL_CAP:n` lower the per-visitor and daily limits the same way.

Gateway log lines (`"event":"qloo_call"`) show each Qloo call's endpoint, status, latency, retries, and cache hit, in the dev server's output, in Workers Logs, and live with `bunx wrangler tail --format json`. To see failures in the running app, add `QLOO_TIMEOUT_MS=1` or a low `QLOO_DAILY_CALL_CAP` to `.dev.vars` and restart the dev server. To see a slow call named, add a low `QLOO_SLOW_MS`, such as `500`, so a normal call passes it.

The daily cron (`triggers.crons` in `wrangler.jsonc`, 12:00 UTC) purges the directory's expired sessions, challenges, and invites and logs how many (`"event":"directory_purged"`), tries again each agent wipe that failed over a minute before and logs how many it wiped, kept, and failed (`retryWipes`, `"event":"wipes_retried"`), and runs the health check, which logs one `"event":"health_check"` line per check, at error level with the reason when it fails:

- `qloo_search`: the TRD's health-check search, sent to Qloo past the cache. A 401 means the key stopped working.
- `sample_ranking_cached`: the sample launch, The Watch against the other 15 resolved sample shows with nothing settled, answers from the cache. It reads the cache only and never calls Qloo, so it fails until a fresh session has started the sample launch before settling anything. Settling Binge Mode or mapping a miss first sends a different ranking.

Run it locally with `curl 'http://localhost:5128/cdn-cgi/local/scheduled?cron=0+12+*+*+*'` against the dev server, which prints `ok` and logs the lines in the server's output. On the Worker, `bunx wrangler deploy` lists `schedule: 0 12 * * *`, and `bunx wrangler tail --format json` across 12:00 UTC shows the run.

Wrangler can't run the deployed cron on demand, but a temporary per-minute schedule can, through the schedules API that `bunx wrangler deploy` uses. The cron handler ignores which schedule fired, so every tick runs the health check. Treat it as a deploy, one at a time: a deploy puts `wrangler.jsonc`'s schedule back. In `apps/`:

```sh
SCHEDULES=https://api.cloudflare.com/client/v4/accounts/f0621d6622ac79af0e8e6f3520f78063/workers/scripts/crossfeed/schedules
TOKEN=$(bunx wrangler auth token --json | jq -r .token)
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data '[{"cron":"0 12 * * *"},{"cron":"* * * * *"}]' "$SCHEDULES"
bunx wrangler tail crossfeed --format json
```

The tick is the tail event with an `.event.cron`, and its `logs` hold the two `health_check` lines. Then put the schedule back, and check that it lists only `0 12 * * *`:

```sh
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data '[{"cron":"0 12 * * *"}]' "$SCHEDULES"
curl -H "Authorization: Bearer $TOKEN" "$SCHEDULES"
```

Each change takes about five minutes to reach the Worker: the first tick comes about five minutes after the first `PUT`, and ticks go on for about five minutes after the second. Each tick spends one Qloo call on its search, so budget about 15.

Agent log lines show each model call's tokens and cache reads (`"event":"model_call"`), each run's topic baseline with its status and whether it came from the cache (`"event":"topic_baseline"`), and one summary per run with its outcome (`"event":"run_summary"`). To see a run stopped at a limit, lower a limit in `src/limits.ts` while the dev server runs, and put it back afterwards.

## Where things go

- `src/index.tsx`: the Worker. It mounts one route module per surface from `src/routes/` on the one Hono app, and exports the Durable Objects and the cron handler. A new surface, such as the landing page, accounts, the app, the API, or MCP, gets its own module there, mounted at `/` with its full paths.
- `src/routes/demo.tsx`: the demo, which any visitor opens without signing in. `/demo` is the roster page and `/demo/inbox` the inbox; `/inbox` redirects to it for good. It owns the `crossfeed_session` cookie, a UUID that names the session's `CrossfeedAgent` (any other value is replaced, and names no agent), the agent connection at `/agents/session`, and the insertion order export.
- `src/routes/marketing.tsx`: the marketing pages, server-rendered with no island: the landing page at `/`, the privacy page at `/privacy`, and the beta terms at `/terms`. Their illustrations use made-up shows and say so where they appear; never put a Qloo response, a sample network show, or an invented customer, quote, figure, or price on them (`test/marketing.test.ts` checks the first two). The terms read the daily limits from `env` and the per-run and inbox limits from `src/limits.ts` and `src/inbox.ts`, so they can't drift from the code.
- `src/shell.tsx`: the server-rendered shells. `appShell` reads what the page's handler set (`AppVariables`): with a member, the account menu with Sign out; with their networks, the switcher; with the page's network, its sections (Dashboard, Roster, Inbox while `GUEST_PITCHES` is on, and Settings). The menus are `<details>` that `main.tsx` closes on a click outside or Escape, and wires Sign out, which posts with `fetch`. `marketingShell(title)` is the marketing pages' black top bar (wordmark, Developers, Sample network, and "Sign in" while `ACCOUNTS` is on) and footer (Privacy, Beta terms), with the stylesheet and no island. `demoShell` is the demo's top bar with its sections and, while `ACCOUNTS` is on, "Create your network", then the React island. Every shell ends in the React island but the marketing one, and the two island shells share `IslandHead`.
- `src/routes/auth.tsx`: accounts (ADR 0003). `/sign-in` is an island page, told where to go next as `data-next`, a path on this site or else `/app`; a signed-in member goes straight there. Behind it are the passkey ceremonies, each two requests: `/auth/sign-up/options` and `/auth/sign-up`, and `/auth/sign-in/options` and `/auth/sign-in`. The first keeps a challenge in the directory and the second takes it back once. Then `/auth/recover` and `/auth/sign-out`, and adding a passkey for a signed-in member from their account page, `/auth/passkeys/options` and `/auth/passkeys`, whose options name the passkeys they have, so a device that keeps one adds no second. The two options requests, `/auth/sign-up`, and `/auth/recover` write before anyone is signed in, so each visitor gets 20 of them a minute (`AUTH_LIMITER`), and a 429 says to wait. It also owns joining a network: `/invite` is the invite page, an island page whose link carries its token in the fragment, which the page reads and posts to `/auth/invite` (the network's name, or why the link can't be used), then either to `/auth/join` as the signed-in member, or through the sign-up ceremony with `invite`, which skips the sign-up cap and joins in the same batch that writes the account. The relying party is `RP_ID` and its pages `APP_ORIGINS`, never the request's host. Every route here answers 404 while `ACCOUNTS` is off, and every `/auth/*` answer is `no-store`.
- `src/routes/app.tsx`: `/app` and every page under it, behind the gate, which sends a signed-out request to `/sign-in?next=<path>` and marks every page `no-store`. `/app` opens the network the member opened last, or `/app/new`, where they name one; posting to `/app/new` creates it, refused past `NETWORKS_PER_MEMBER` networks created. `/app/account` is the member's account page, before the network pages so its path isn't read as a network's ID, with `POST /app/account/name`, `/app/account/passkeys/:credentialId/remove` (never the last, 409), `/app/account/recovery-code` (shown once), `/app/account/sign-out-everywhere` (every session ends, and their open pages on every network and launch close, through the network agent's `kick` with its own reason), and `/app/account/delete` (409 while they're any network's only owner; their open pages close); a signed-in recovery lands on `/app/account?recovered`. A network's pages are `/app/:networkId` (the dashboard), `/app/:networkId/roster`, `/app/:networkId/inbox` (a 404 while `GUEST_PITCHES` is off), and `/app/:networkId/settings`, with `POST /app/:networkId/settings/network` for the settings' network module, and the members module's `POST /app/:networkId/settings/members/invites` (a new invite link, shown once), `.../invites/:inviteId/revoke`, `.../:memberId/role`, `.../:memberId/remove`, and `.../leave`, and the API keys module's `POST /app/:networkId/settings/api-keys` (a new key, its secret shown once) and `.../api-keys/:keyId/revoke`, and the danger zone's `POST /app/:networkId/settings/delete` with the network's `name` typed exactly (`deleteNetwork` in `wipe.ts`), for owners alone; settings also tell the page today's usage (`data-usage`, the API's `getUsage`); removing a member or leaving calls the network agent's `kick` once the directory has let them go; each answers 404 to anyone who isn't the network's member, as for a network that doesn't exist, and opening one marks it the member's last. It also owns `/agents/network/:networkId`, a network's agent: only a WebSocket upgrade from an `APP_ORIGINS` page, signed in by one of the network's members, gets through, with the member named in the `Crossfeed-Member` header (`MEMBER_HEADER`), which the Worker always overwrites; anything else is the same 404. A launch's page is `/app/:networkId/launches/:launchId`, and its agent `/agents/launch/:networkId/:launchId`, checked as the network's are and only while the network's list has the launch (`listsLaunch`); the Worker names the member to an agent in `Crossfeed-Member` and, URI-encoded, `Crossfeed-Member-Name`. Under a launch, any member can download an approved order at `GET .../insertion-orders/:id.csv` (409 for a draft) and delete the launch with `POST .../delete` (`deleteLaunch` in `wipe.ts`), each a 404 once the network no longer lists it.
- `src/routes/api.ts`: the REST API under `/api/v1`, an `OpenAPIHono` from `@hono/zod-openapi`, so each route's zod schemas validate its request and make its part of the OpenAPI 3.1 document at `/api/v1/openapi.json`. Paths are scoped by network (`/api/v1/networks/:networkId/...`); the `caller` middleware takes one of the network's API keys in `Authorization: Bearer`, counted against `API_LIMITER`, or else a member's session, whose writes need an `APP_ORIGINS` `Origin`, and answers 404 for any network the key or member can't reach. Each route is a thin adapter over `src/operations.ts`, and `onError` answers every `Refusal` as `{ error: { code, message } }` with its code's status. There's no approve route (ADR 0002). A body that isn't only JSON, such as a roster file or pitch emails, is declared per `Content-Type` and read in the handler, which picks the upload module's reader by its type; the inbox's JSON pitches are declared by `$ref` to a registered schema and validated in the same handler, as a zod JSON schema there would refuse every other type. The inbox and pitch run routes answer 404 while `GUEST_PITCHES` is off, and the document lists them either way. Everything under `/api/v1` answers 404 while `ACCOUNTS` is off, and every answer is `no-store`.
- `src/operations.ts`: what a program can do for a network, shared by the REST API and the MCP server to come (#171). Each operation takes an `OperationContext` (`env`, the network, and the `Caller`: a member with their role, or an API key's ID) and its input, and calls the directory or the network's agent over RPC; owner-only changes check the caller here. A pitch run reads from the agent's synced state while it's the latest and from what it ended with (`getRun`) once another run or inbox replaced it; only the latest run's question and replies can change.
- `src/refusal.ts`: `Refusal`, an error with a stable code (`invalid`, `unauthorized`, `forbidden`, `not_found`, `conflict`, `too_large`, `unreadable`, `limit`, `rate_limited`) and the HTTP status of each. The agents, the roster parser, the upload module, and the operations throw it; its `code` is an own property, which workerd keeps on an error thrown across Durable Object RPC, so `refusalCode(error)` reads it on the Worker's side without parsing the message. A page still reads only the message. An agent's refusal the API must tell apart gets a code; any other error is a 500 `internal`.
- `src/auth.ts`: the session cookie, `__Host-crossfeed_member` (`setSession`, `signedIn`, which extends a session in use, `session`, the member without touching the cookie, for an agent's upgrade, whose headers can't change, and `endSession`), `jsonBody`, and the guards every accounts route shares: `accountsOn`, `sameOrigin`, which answers 403 to a write whose `Origin` isn't in `APP_ORIGINS`, and `nextPath`. Pages write with `fetch`, never an HTML form: under `Referrer-Policy: no-referrer`, Chrome sends a form POST's `Origin` as `null`, so `sameOrigin` refuses it.
- `src/directory.ts`: the only code that reads or writes D1. It makes session tokens and recovery codes, hands each out once, and keeps only their SHA-256 hashes. It also keeps networks and memberships: `createNetwork` checks the member's cap in the batch that writes the network and its owner, `openNetwork` checks a membership in the statement that marks it opened last, `renameNetwork` checks the member owns it in the statement that renames it, and `setupProgress` reads what the dashboard's checklist needs from the directory. Invites and members follow the same rule: an invite's token is kept as a hash and used in the batch that adds the membership (`joinByInvite`, or `signUp` with the token, which writes nothing unless the invite is open), and `setRole` and `removeMember` refuse, in their own statement, any change that would leave a network with no owner. API keys are `cf_live_` and 32 random bytes, kept as a SHA-256 hash with their first 12 characters as the prefix: `createApiKey` checks the owner in its `INSERT`, `revokeApiKey` in its `UPDATE`, and `apiKeyFor` finds a key in use by its secret's hash and notes its last use at most once a minute. Each change that must hold together is one statement or one `batch()`, since D1 has no interactive transactions: a challenge is taken with `DELETE ... RETURNING`, so it's used once, and a recovery code is replaced in the batch that starts the session. A session lasts 30 days from its last use, and a use extends it at most once a minute. The daily cron purges expired sessions, challenges, and invites. `wipes` lists the agent instances to wipe: `noteWipe` before a wipe, `wipeDone` once it succeeds, and `wipesDue` for the cron; `dropNetwork` deletes a network, checking its owner, in the batch that notes a wipe for each of its instances. A member's own account: `renameMember`, `memberPasskeys`, `addPasskey`, `removePasskey` (never the last, in one statement), `newRecoveryCode`, `signOutEverywhere`, `openSessions`, `accountNetworks` (with whether they're each one's only owner), and `deleteMember`, refused in its own statement while they're any network's only owner; their passkeys, sessions, and memberships cascade, and what they made in a network is kept, made by no one.
- `src/wipe.ts`: deleting a launch (`deleteLaunch`): its wipe is noted in the directory, the network's list lets go of it (`dropLaunch`), so its page, agent, and export answer 404, then its agent is wiped with `destroy`, which closes its open pages with 4410, "This launch was deleted." Deleting a network (`deleteNetwork`): `networkInstances` lists every agent instance it has, its launches' and its own, the one place a new kind joins (such as a network's own Qloo gateway), and `dropNetwork` deletes its directory rows and notes their wipes in one batch, so its pages, agents, and API answer 404; then the network's agent lets go (`letGo`), closing its open pages with 4410, "This network was deleted.", and naming any launch planned since its list was read, which is noted too; then each is wiped, launches first, closing their pages the same way. `WIPERS` says how each binding is wiped. A wipe that fails stays noted, and the daily cron's `retryWipes` tries it again once it's a minute old, crossing off instead a launch the network still lists while the network is still in the directory, whose deletion stopped before the list let go of it.
- `src/health.ts`: the daily health check the cron runs. A new check logs its own `health_check` line through `report`.
- `migrations/`: the D1 directory's schema, one SQL file per migration, made with `bunx wrangler d1 migrations create DB <name>`. `0001_directory.sql` holds every directory table: members, passkeys, sessions, challenges, networks, memberships, invites, API keys, and the agent instances still to wipe. Never edit an applied migration; add a new one.
- `src/network-agent.ts`: `NetworkAgent`, a signed-in network's agent (ADR 0001), named by the network's ID. It extends `CrossfeedAgent`, opens empty, with no sample network and its guide dismissed, keeps `launches` and `checklistDismissed` in its synced state, and tags each connection `member:<id>` from `MEMBER_HEADER`. `dismissChecklist` reads that tag, and `kick(memberId)` closes every connection with it, the network's own and each of its launches', with close code 4403, which the client takes as final. `createLaunch` plans a launch, named or from comps, on its own agent and lists it, newest first; each launch's agent then reports its row (`LaunchSummary`) with `reportLaunch`, and a run asks `rosterForLaunch` for the roster, the CPM, and the evidence records the roster cites, refused while a show is still pending. After each settled change to the roster, it tells every launch how the roster now stands (`rosterKey`, sent to `noteNetworkRoster`, and kept in its storage so waking up sends nothing new), so a launch says when it differs from its latest run's copy (`rosterChanged`). `dropLaunch` takes a deleted launch off the list, and `letGo` closes every page as the network is deleted. It refuses what only a launch or the demo does (`startLaunch`, `editInsertionOrder`, `approveInsertionOrder`, `clearSample`, `markGuide`, `dismissGuide`), so it never runs a launch; its inbox's pitch runs keep `answer` and `getRun`. Only a connection that names its member can approve a reply, which records who approved it (`approvedBy`). It offers `startFromSample`, which starts an empty roster from the sample network's shows, their figures labelled sample and the CPM left alone, and its imports keep the shows already on the roster as they were settled (`keepsSettledShows`), updating only the figures the file brings and looking up only new shows and failed lookups. Every Qloo call and model run it makes counts against the per-visitor limits as `network:<id>` (`limitKey`), whichever member makes it, or none.
- `src/launch-agent.ts`: `LaunchAgent`, a launch's agent, named `<networkId>:<launchId>` (`launchAgentName`). It holds the launch, its runs, rankings, and insertion orders, opens on no sample network, and refuses roster, inbox, and guide actions. As a run starts, `startLaunch` takes the network's roster and CPM (`networkRoster`, a `CrossfeedAgent` hook that the demo leaves empty) and copies the evidence records the roster cites into its own log under new call numbers, each marked `copiedFrom` the network's call, never `replayed`, and never with the sample marker, so a launch never stores or replays the sample run. After each change to its row's status or summary (`onStateChanged`), it reports it to the network, trying a failed report again. Each run on its run list records who started it (`startedBy`, from the member's name on the connection). Its Qloo calls and model runs count as its network's (`networkLimitKey`).
- `src/agent.ts`: `CrossfeedAgent`. Its synced `State` type and its `@callable` actions are the client protocol. `startLaunch` returns at once and runs the Claude tool loop in the background, writing a progress note per tool call. When a run ends, the agent keeps the state it ended with, which `getRun` returns. A completed sample launch run answered with the sample answers, on the unchanged sample with nothing the visitor typed, is also kept in the gateway, and while Qloo can't be called, `startLaunch` replays it instead of running, or stops any other run. The replay copies whatever state the stored run holds, except the session's own `inbox` and `runs`; a new session-level field that a launch run doesn't own joins `inbox` in `keepSampleRun`. `limitKey()` is the one place it picks who a Qloo call or model run counts against: a demo session's visitor, and a network's or launch's agent's `network:<id>`. `member()` reads the member a call's connection carries, the `member:<id>` tag (`MEMBER_TAG`) a network's agent gives it, or null. `approveReply` needs a connection, so the Worker's own calls, and the API through them, can never approve (ADR 0002).
- `src/limits.ts`: the run limits, shared by the agent and the UI.
- `src/claude.ts`: the model settings for every agent turn. Change them only with the TRD's model settings.
- `src/prompt.ts`: the frozen system prompt. Its launch steps are in the PRD's order; a tool ticket fills its own step's `instruction`, and an empty step stays out of the prompt.
- `src/tools/`: one file per tool, registered in `src/tools/index.ts`. A tool has a strict definition, the progress note it shows, and `run`, which reaches Qloo through `context.qloo` and returns an error that says what to do next.
- `src/gateway.ts`: `QlooGateway`, the only code that calls Qloo. It also keeps the stored sample run, and `health()` says whether Qloo can be called: not once the day's cap is reached, nor for five minutes after a request fails after its retries, unless one succeeds since. Each method returns its data or error together with an evidence record. Every request goes through `request`, which sends GET parameters in the query string and POST ones as a JSON body of flat dotted keys, serves the shared cache, enforces the daily cap, paces and limits requests to 3 in flight, and retries; a new endpoint goes through it too. A call can skip the cache or read only from it, as the health check does. It also keeps the per-visitor daily counters, sign-ups among them (`admitSignup`, against `SIGNUP_VISITOR_DAILY_CAP`), and `usage(visitor)` reads a visitor's or a network's Qloo calls and model runs today against their limits.
- `src/evidence.ts`: the evidence record's shape. Fill its fields; don't reshape it.
- `src/resolve.ts`: deciding whether a search result is the named entity: a roster show by name, a pitched work by title, then its author or year.
- `src/demographics.ts`: the demographic check's derived values and its thresholds, built from one demographics call: the launch profile and each finalist's mismatches in words. Read `state.demographics`.
- `src/order.ts`: the insertion order's pricing, shared by the agent and the UI's live totals: slot values from downloads and CPM, the gaps a missing figure leaves, the line checks, and the CSV export. The `draft_insertion_order` tool stores the run's draft; the `editInsertionOrder` and `approveInsertionOrder` actions are the programmer's alone, and `GET /api/insertion-orders/:id.csv` (the demo's) and `GET /app/:networkId/launches/:launchId/insertion-orders/:id.csv` (a launch's) call the agent's `exportInsertionOrder` and answer with `csvDownload`. Approval needs the page's connection, so no RPC caller can approve (ADR 0002); on a launch's agent the connection must carry a member, and the order records their name and the time (`approvedBy`, `approvedAt`) until it returns to draft.
- `src/fit.ts`: the fit ranking's derived values, built from one ranking call: which roster shows are scorable, fit rank, band, leading comp, finalists, and each other show's reason for not being scored. Later tickets read `state.ranking` for finalists and leading comps. It also builds each pitch list, one per work type, which `rank_pitches` puts in `state.booking.lists`.
- `src/roster.ts`: reading an imported roster, pasted names or a CSV, into rows, and saying which figures it brings.
- `src/upload.ts`: turning uploaded files into what the agent takes, for the browser and the API alike: `readRosterUpload` reads one `.csv` or `.txt` file into roster text and its format, and refuses another type, more than one file, an empty file, or one over `MAX_UPLOAD_BYTES` (5 MB) before reading it. `readPitchUpload` reads `.eml` files (with `postal-mime`, from their bytes, so each part keeps its charset), an `.mbox` export, split into its emails, or a `.txt` split on lines of dashes, into pitches of sender, subject, and plain-text body, HTML-only mail as its text, and refuses another type, an empty or oversized file, or a file with no pitch in it. `loadInbox({ pitches })` takes its result. Each refusal is a `Refusal`, `too_large` for the size and `unreadable` for the rest. The API wraps a request body as an `Upload` named by its `Content-Type`; a body that sends `Content-Length` is sized by it, so an oversized one is refused unread, and one that doesn't is read first.
- `src/sample.ts`: the sample network a new session opens on, read from `src/sample-network.json`, with its suggested answers to the run's questions.
- `src/inbox.ts`: the inbox's types, reading the sample inbox, pasted pitches, or uploaded pitches into rows (an uploaded pitch with no text or over `MAX_PITCH_CHARS` is skipped and named in `inbox.skipped`, the rest load), and reading the past guests a pitch run ranks against. `loadInbox` returns at once and reads the pitches in the background, five at a time.
- `src/extract.ts`: the pitch reader, one structured-output call per pitch. Single model calls beside the agent loop, such as the topic baseline, use `structured` from `src/claude.ts`.
- `src/topic.ts`: the topic baseline, one structured-output call per run that `startLaunch` starts beside the agent loop, cached in the agent by a hash of its request, and the topic moves `withMoves` works out from it and the fit chart, whichever lands last.
- `src/client/`: the React island. `main.tsx` renders `Account.tsx`'s sign-in page (`data-page="sign-in"`, with `data-next`) or its new network page (`data-page="new-network"`), `Dashboard.tsx` (`data-page="dashboard"`), `Launch.tsx` (`data-page="launch"`, `App.tsx`'s `Workspace` with the network, its roster read-only), `Roster.tsx` (`data-page="network-roster"`), `NetworkInbox.tsx` (`data-page="network-inbox"`), or `Settings.tsx` (`data-page="settings"`), each told the network, the member's role, and its links by data attributes; or it passes the server's `data-page`, `data-agent-path`, and `data-roster-link` to `App.tsx`, which renders the roster page or `Inbox.tsx`. The pages take their agent's path and their links to other pages as props rather than naming them; the insertion order's CSV link is `exportHref`, given by `App.tsx` from `links.orders`: a launch's page gets it from `data-orders-link`, and the demo keeps its own route. `controls.tsx` holds the shared form pieces, such as `useAction`, `PickOne`, `send`, which posts JSON to a Worker route with the page's `Origin`, and `useFileDrop` and `DropCue`, a page-wide file drop and its cue, which the roster and inbox forms share (mount one per page), and `ShownOnce`, a new invite link or API key shown once to copy. `Dashboard.tsx` also holds `useNetwork`, a network page's agent connection, and `LostAccess`, what a network page shows once its agent closes the connection for good, as when the member is removed: a network page renders it when `agent.connectionError` is set; `Account.tsx` also holds the invite page (`data-page="invite"`, with `data-member-name` when someone is signed in). `Roster.tsx` is a network's roster page, built from `App.tsx`'s roster pieces (`RosterImport`, `RosterTable`, `ShowEditor`, `RosterCheck`, and `useEvidence`); `RosterImport` takes a file from its picker or dropped anywhere on the page, on the demo too. `NetworkInbox.tsx` is a network's inbox page: `InboxWorkspace` from `App.tsx`, the demo's inbox page on any agent, whose load form in `Inbox.tsx` takes pitch files from its picker or dropped anywhere on the page. `AccountPage.tsx` is the account page (`data-page="account"`), in the settings' grammar, reusing `RecoveryCode` from `Account.tsx` for a new recovery code. `Settings.tsx` lays out the settings' modules, one file each under `settings/` (`Network.tsx`, `Members.tsx` with its invite links, `ApiKeys.tsx`, an owner's keys, `Usage.tsx`, today's usage against the caps, and `DangerZone.tsx`, an owner's deletion of the network): a new module is its own file there and one line in `Settings`, and shows itself read-only to a member when only an owner can change it. `App.tsx` lays out the chart column and the rail; add rail modules as `<section className="mod">` inside `.rail`. The agent's open question is the exception: it comes before the chart column in `.main`, and the grid sets it atop the rail, so a single column, below 960px, reaches it before the chart. In one column the roster section also moves, after the rail (`useOneColumn`). It renders from `shown`, the latest state or an earlier run's while one is viewed; render a run's results from `shown` so an earlier run shows its own, and hide editing controls while `viewing` is set. `InsertionOrder.tsx` is the rail's insertion order module. `Guide.tsx` is the rail's guide through the sample launch: a step the page alone sees, such as opening a why-it-moved line, calls `markGuide`. `states.tsx` holds the empty, loading, slow, failed, missed, and error states: put a state's words in a `StateLine` rather than styling your own, and name slow calls with `SlowCalls`. `Evidence.tsx` is the rail's evidence module: a cited call number is a `button.call` that opens its record, fetched with `getEvidence`. Label Qloo data with `<Source of="qloo" />` and agent text with `<Source of="agent" />` from `Source.tsx`, wherever they appear.
- `src/style.css`: the tokens and components from [DESIGN.md](/docs/DESIGN.md).
